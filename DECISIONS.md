# DECISIONS.md — журнал решений и преодолённых проблем

Правила ведения (глобальный `~/AGENTS.md`): каждая запись — уникальный
стабильный идентификатор `D-NNN` (сквозная нумерация, номера не
переиспользуются). Записи создаются по мере решения проблем; на них
ссылаются из коммитов, ревью и комментариев к задачам вида `(D-NNN)`.
Формат: суть проблемы → принятое решение → ссылки (коммиты, задачи,
документация). Первичные записи D-001…D-021 заполнены ретроспективно по
истории коммитов.

## Записи

### D-029 — первое bulk-ревью кодовой базы (hy4-flash-free), поток находок в цикл задач
Дата: 2026-11-16.
Проблема: кодовая база выросла до ~140k строк Go без сквозного ревью;
нужен систематический аудит качества.
Решение: проведено первое bulk-ревью по 19 стадиям (~5–12k строк, без
пересечений по файлам) моделью `opencode-go/hy4-flash-free` через
opencode-cli (все стадии — с первой попытки, таймаутов/лимитов не было).
Итог: 0×P0, 3×P1, 35×P2, 45×P3 (83 находки; P1 — гонка D7 в ingest
ApplyDelete, вечный PEL в queue, маскировка регресса canary в
crawlerctl). Консолидация: дедупликация, приоритизация, группировка по
доменам. Находки P1/P2 + дешёвые P3 → 19 задач цикла T-286…T-304 (TODO);
P3-идеи → INBOX T-305…T-314. Спорные находки dns (SERVFAIL-эскалация —
осознанный компромисс) — реализовывать config-gated, дефолт сохраняет
текущее поведение.
Ссылки: `tmp/review/hy4bulk/00-consolidated.md` и отчёты стадий `NN-*.md`
(gitignored); доска LaravelDomains; базлайн на момент ревью — 86186b5.

### D-001 — статус задач не коммитится в git
Дата: 2026-10-16.
Проблема: отдельные статусные коммиты («[в работе]» и т.п.) замусоривали
историю и ломали принцип «одна задача — один коммит».
Решение: статус живёт вне git (тогда — в плане задач, теперь — на доске
Todoist, см. D-021); в git — только содержательные коммиты с `(T-0NN)`.
Ссылки: c604a30; AGENTS.md «Commits».

### D-002 — цикл только через feature-ветки и worktree, линейная история
Дата: 2026-10-17…18.
Проблема: работа в `master` напрямую и merge-коммиты (прецедент —
01800a7) усложняли параллельную работу и историю; зомби-сабагенты
оставляли висящие worktree.
Решение: каждая задача — ветка `t-NNN` в отдельном worktree
`~/worktrees/laravel-domains/<t-NNN>`; в `master` только служебные коммиты;
слияние линейное (rebase + `--ff-only`, protection «Require linear
history»); принудительный останов сабагента — `opencode session delete`
после отбора worktree.
Ссылки: 81d30d6, bb3e973, 01800a7 (прецедент); AGENTS.md «Branches and
worktrees», «Linear master history», «Parallel execution».

### D-003 — OOM Redis не сжигает попытки задач (инцидент 22.10.2026)
Дата: 2026-10-23.
Проблема: OOM-окно Redis (легаси-пачки q:dns 620 МиБ при временном
maxmemory 900M) дало 5507 задач в q:dead — публикации результатов
падали, попытки сгорали; первоначальная гипотеза (рендер-тарпиты) не
подтвердилась.
Решение: ошибки публикации при OOM — InfraError с фьюзом и повторной
пробой записи, попытка не сжигается; XTRIM легаси-очередей и возврат
бюджетов памяти (575 МиБ освобождено); сигнатура масс-смертей q:dead в
runbooks §2.6; MemoryHigh=850M + алерты/метрики OOM юнитов.
Ссылки: 0e574bc (RCA), 41b7a47, 63151d1, cc7d29f, a6e8770; T-149…T-156;
docs/runbooks §2.6, §11.1.

### D-004 — мягкий потолок кучи http-worker вместо ожидания cgroup-OOM

### D-006 — ревью при исчерпанных квотах ревьюеров
Дата: 2026-10-24…31.
Проблема: периодически все доступные ревьюеры оказывались на лимитах
(T-161, T-164, T-197, T-214) — ревью срывалось или заменялось

### D-009 — живой контур проверки формы вместо 6000 сокетов на запрос
Дата: 2026-11-03.
Проблема: checker открывал до 6000 fd на запрос (резолверы), CLI
`crawlerctl check` тоже; риск исчерпания fd и нестабильность под
нагрузкой.
Решение: долгоживущий контур checker.Runtime: ленивая сборка одна на
сервис, цепь резолверов LiveUDPPoolSize=16 (48 fd на сервис), общий
Fetcher с общими limitState, один render.Manager с ленивыми поколениями;
семафор web.live_concurrency=4 с быстрым 503 busy + Retry-After
(перегруз не пишется в web_checks); Close контура идемпотентен.
Ссылки: 203efa6; T-220.

### D-010 — атомарный reserve в login-лимитере дашборда
Дата: 2026-11-03.

закрыта тестом PartialWindowExpiry); остаточный риск — nginx limit_req.
Ссылки: 44dc3c1; T-231; docs/services.md.

### D-028 — T-283: живучесть при рестарте движка — ожидание в менеджере, гейт клеймов, гейт/алерты не трогать
Дата: 2026-11-16.
Проблема: три интерпретационных развилки. (1) Где ждать движок — в

alert). Логика гейта не менялась. (3) RecoverLoop получает

наблюдаемый рестарт движка; для локального chromium включает плановые

сериализации: проход перезаписывает те же строки crawler_counters, в

access» на горячих строках, регресс против несуществующего дефекта.

### D-054 — T-310: восстановление watch после переполнения буфера fsnotify (ErrEventOverflow → сброс кэша watched + немедленный проход)

Контекст: при переполнении буфера событий fsnotify часть событий теряется
в ядре (в канал приходят только ErrEventOverflow), среди них может быть

само, а карта watched пакета internal/watch запись сохраняет — и
addWatch, доверяющий карте, больше никогда не переустановит watch

горутине-владельце run (как handleEvent) — без гонок. Чужие ошибки

поведение, только Warn. Наблюдаемость: отдельный greppable Warn

ID движется только новыми выдачами — до следующего XREADGROUP он неподвижен,
а побитые XACK (ProcessingAttempt — Ack на каждую запись) уменьшают pending,
не двигая ID. Batch дольше окна (15 мин) → firing с диагнозом «the consumer
is not reading» и шагом триажа «a worker restart» — диагноз неверен, а
слепой рестарт выкинул бы in-flight работу обратно в redelivery.

Оценка вариантов ТЗ:

(а) считать freeze по depth без Pending (только undelivered-часть,
min(lag, XLEN)) — отклонён. (i) False positive не устраняется там, где
важно: при оставшемся недоставленном фоне (lag > 0 — типичное состояние
рабочей очереди) живой медленный воркер всё равно даёт неподвижный ID —
firing остаётся; «лечится» только полностью раздатый случай (lag = 0).
(ii) False negative ровно на сценариях-основателях алерта: финальная
стадия яда T-159 и мёртвый consumer с полностью раздатой очередью — это
в точности lag = 0 + pending > 0 + неподвижный ID («XREADGROUP returns
no entries», шапка streamgroups.go) — исключение pending ослепляет алерт
именно там (глубину такого состояния пинирует TestGroupDepth — кейс
«lag 0 — a zero increment», backpressure_test.go; замороженность с
pending > 0 покрыта новыми тестами T-313). (iii) Ломается
инвариант единой формулы глубины (gate / crawlerctl status /
crawler_queue_depth / строка «Queues» отчёта — «an observation has no
right to diverge from the gate», docs/redis.md): появляется второе
понятие «есть ли работа».

(б) триггер не менять, уточнить диагноз по доле pending — принято.
Pending из XINFO GROUPs всегда точен (шапка backpressure.go) и бесплатен
при том же чтении: StreamGroupState получил поле Pending (Depth−Pending =
undelivered-часть). Строка firing для группы с pending > 0 добавляет
«, N unacknowledged», а общий суффикс становится дифференциальным: без
unacknowledged — классический текст дословно («the consumer is not
reading … a worker restart»); при наличии — «deliveries are not
advancing … a live worker may be processing it — check the pending
trend/XPENDING idle before a restart; a crashed consumer — the worker
unit log and q:dead, the T-159 poison». Сам firing сохранён: ≥15 мин без
ни одной новой выдачи в системе, где «batches in seconds» (spec 3.3), —
сигнал, достойный взгляда, независимо от класса причины; меняется не
чувствительность, а направление триажа.

Рассмотренное и отклонённое расширение: сброс окна при убывающем pending
(побитые XACK живого воркера различались бы уже в триггере) — разводит
понятие «неподвижности» (ID против depth), имеет дыры (полностью
проваливающийся batch не ack'ает ни одной записи — pending стоит) и
выходит за два варианта ТЗ; тренд pending оставлен триажу (шаги — в
docs/operations.md; счётчик unacknowledged — в тексте алерта).

Регрессии: TestAlertsQueueFreezeIssuedBatch — сценарий находки (выданный
batch: pending = depth, ID неподвижен, между проходами pending убывает) →
firing с дифференциальным суффиксом и счётчиком unacknowledged, БЕЗ
«the consumer is not reading»; чистый недоставленный фон — классический
текст дословно; TestRedisStreamGroups проверяет проводку Pending.
Существующие тесты alertstate (Pending = 0) не изменены.

Ревью-раунд (deepseek-v4.1-flash, первое звено цепочки; отчёт
tmp/review/42-t313.md): VERDICT FINDINGS, 0×P0/P1/P2, 5×P3; ядро

### D-065 — T-323: предупреждение (не запрет) при dns.fallback.escalate_qps > 1% dns.max_qps — метод validateWarnings + slog.Warn в build

Дата: 2026-11-17.

Проблема (идея P3 ревью T-300): диапазон escalate_qps валиден (0 или
(0..100000]), но бюджет эскалации — лимитер, ОТДЕЛЬНЫЙ от max_qps: проход
резервов едет на одном трафик-токене цикла «локальный → резервы»
(LimitResolver над FallbackResolver, internal/dnsclient/fallback.go),
т.е. нагрузка SERVFAIL-шторма на публичные резолверы ограничена только
escalate_qps и ложится СВЕРХ запланированной скорости. Значение выше ~1%
max_qps незаметно для владельца съедает заметную долю DNS-бюджета;
хочется предупреждение при валидации конфига, не запрет (большая доля —
легитимный осознанный выбор, например малый dev max_qps).

Решения:

(а) Механизм предупреждения. Валидация (Config.Validate) возвращает
только error и чиста — механизма warn в пакете нет; прецедент проекта —
Warn логгера на потребителе (cmd/scheduler о весах зон). Принято: чистый

тестируется напрямую), а вывод — slog.Warn в build (load.go), после
успешной Validate: дефолтный логгер пишет в stderr — та же поверхность,

(log.Fatalf в cmd/*). Сигнатура Load/Validate не меняется (20+ callers),
конфиг остаётся валидным, предупреждение видно в каждом сервисе и
crawlerctl при загрузке.

(б) Порог — ровно 1%, строгое >. Обоснование: документированная пара
дефолтов «100 ≈ 1% от 10000» (комментарии config.go и
dnsclient.DefaultEscalateQPS) — порог делает заявленный интент
проверяемым: дефолты (и любая пара ровно 1%, напр. 20/2000) молчат,
выше — Warn. Форма вычисления limit = max_qps × escalateQPSWarnPercent
(/100, одна корректно-округлённая операция): граница точна и для целых,
и для «однодесятичных» пар (100 из 10000, 0.03 из 3 — покрыто тестом);
формы 0.01×max_qps чураемся из-за drift на не-round значениях.

(в) Эффективные значения: escalate_qps = 0 → дефолт 100 (как

config→dnsclient→config; пара закреплена пин-тестом
TestDefaultEscalateQPSSyncedWithConfig в dnsclient (там импорт config
возможен) и литералом 100 в TestDefault пакета config). max_qps всегда
> 0 у валидного конфига; guard maxQPS > 0 защищает прямые вызовы метода
с невалидным конфигом (NaN также молчит — его раньше отклоняет
Validate). Предупреждение считается независимо от escalate_rcodes
(стиль monitor.alerts: потолок осмыслен до включения), но при
выключенной эскалации сообщение несёт хвост «escalate_rcodes is off —

только с включённой эскалацией (NewFallbackResolver), сообщение не
должно утверждать нагрузку, которой ещё нет (находка ревью P3).

Тесты: TestValidateWarningsEscalateQPSBudget — таблица (дефолты 100/10000
молчат; ровно 1% явно, 20/2000 и 0.03/3 — молчат; 100.5/10000, 25.5/2000

### D-067 — T-312: детерминированные negative-wait проверки BackpressureGate — индикатор старта публикации (Warn гейта) перед окнами ожидания

Дата: 2026-11-17.

Проблема (P3-6 bulk-ревью hy4, стадия 18 e2e-tests):
TestResilience_BackpressureGate проверял блокировку гейта отсутствием
результата за time.After 250/150 мс. Окно ставило на то, что горутина
издателя вообще успеет запланироваться: на перегруженном раннере
ошибочно «разблокирующая» реализация не давала результата в окне не
потому, что ждёт, а потому, что ещё не стартовала — assert «went
through without waiting» ложно молчал (ложно-зелёный прогон при
регрессии). Позитивной проверки «публикация началась и висит» не было.

Решения:

(а) Индикатор старта — готовое прод-поведение, без правок прод-кода:
AwaitCapacity (internal/queue/backpressure.go) при первом «закрытом»
заходе пишет ровно один Warn «publication paused: queue depth at
threshold» (флаг waited — не спамит на ретраях). Одна запись доказывает
сразу три вещи: горутина запланирована, глубина прочитана из Redis,
глубина на пороге — публикация НАЧАЛАСЬ и висит в гейте. Захват —
gatePauseLog (slog.Handler, atomic.Int64) в BackpressureOptions.Log
(логгер приватен для экземпляра гейта; считаются только Warn-записи —
будущий Error-сайт гейта не надует индикатор); ожидание —
waitGatePaused, poll 2 мс с дедлайном 5 с (стиль waitPendingIdle).
Сломанный «неблокирующий» гейт не оставляет записи — детерминированный
FAIL индикатора вместо ложно-зелёного окна.

(б) Порядок проверок: ОБА negative-wait (250 мс на пороге; 150 мс до
отмены ctx) идут строго после индикатора; окно меряет «висит, будучи
начатой», а не «горутина успела стартовать». База счётчика снимается
перед каждым запуском горутины, ожидание — base+1 (дельта фазы, не
абсолют: будущий Warn раньше по тесту не превращает ожидание в no-op,
тихо не возвращая флак — P2-1 ревью). Ассерты не ослаблены: оба Fatalf
«went through without waiting» сохранены.

(в) Два усиления детерминизма: waitStillBlocked после истечения окна
делает непустую (non-blocking) перепроверку канала — завершение,
пришедшее одновременно с таймером, не теряется из-за случайности select
(оба кейса готовы — Go выбирает случайно); streamLen == watermark
проверяется ПОКА гейт держит (в стрим ничего не добавилось) и ПЕРЕД
второй гейтированной публикацией после refill (расхождение установки
диагностируется как её собственное, а не «гейт не встал на паузу» —
P3-2 ревью).

Верификация в worktree: make test (пакет test/integration компилируется
