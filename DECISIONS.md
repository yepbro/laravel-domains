# DECISIONS.md — журнал решений и преодолённых проблем

Правила ведения (глобальный `~/AGENTS.md`): каждая запись — уникальный
стабильный идентификатор `D-NNN` (сквозная нумерация, номера не
переиспользуются). Записи создаются по мере решения проблем; на них
ссылаются из коммитов, ревью и комментариев к задачам вида `(D-NNN)`.
Формат: суть проблемы → принятое решение → ссылки (коммиты, задачи,
документация). Первичные записи D-001…D-021 заполнены ретроспективно по
истории коммитов.

## Записи

### D-001 — статус задач не коммитится в git
Дата: 2026-10-16.
Проблема: отдельные статусные коммиты («[в работе]» и т.п.) замусоривали
историю и ломали принцип «одна задача — один коммит».
Решение: статус живёт вне git (тогда — в плане задач, теперь — на доске
Todoist, см. D-021); в git — только содержательные коммиты с `(T-0NN)`.
Ссылки: c604a30; AGENTS.md «Commits».

### D-002 — цикл только через feature-ветки и worktree, линейная история
Дата: 2026-10-17…18.
Проблема: работа в `master` напрямую и merge-коммиты (прецедент —
01800a7) усложняли параллельную работу и историю; зомби-сабагенты
оставляли висящие worktree.
Решение: каждая задача — ветка `t-NNN` в отдельном worktree
`~/worktrees/laravel-domains/<t-NNN>`; в `master` только служебные коммиты;
слияние линейное (rebase + `--ff-only`, protection «Require linear
history»); принудительный останов сабагента — `opencode session delete`
после отбора worktree.
Ссылки: 81d30d6, bb3e973, 01800a7 (прецедент); AGENTS.md «Branches and
worktrees», «Linear master history», «Parallel execution».

### D-003 — OOM Redis не сжигает попытки задач (инцидент 22.10.2026)
Дата: 2026-10-23.
Проблема: OOM-окно Redis (легаси-пачки q:dns 620 МиБ при временном
maxmemory 900M) дало 5507 задач в q:dead — публикации результатов
падали, попытки сгорали; первоначальная гипотеза (рендер-тарпиты) не
подтвердилась.
Решение: ошибки публикации при OOM — InfraError с фьюзом и повторной
пробой записи, попытка не сжигается; XTRIM легаси-очередей и возврат
бюджетов памяти (575 МиБ освобождено); сигнатура масс-смертей q:dead в
runbooks §2.6; MemoryHigh=850M + алерты/метрики OOM юнитов.
Ссылки: 0e574bc (RCA), 41b7a47, 63151d1, cc7d29f, a6e8770; T-149…T-156;
docs/runbooks §2.6, §11.1.

### D-004 — мягкий потолок кучи http-worker вместо ожидания cgroup-OOM
Дата: 2026-10-24.
Проблема: пики памяти слота (тела ответов) доводили юнит до cgroup-OOM;
профилирование показало, что удержания тел уже нет (ранний Put, T-147), но
потолок нужен.
Решение: `http.mem_limit` (SetMemoryLimit, GC возвращает страницы),
гигиена буфера после ToUTF8, метрики inflight-слотов/тел; возврат 256
слотов — операционно по замеру после деплоя.
Ссылки: b1460ae; T-163; docs/configuration.md.

### D-005 — single-flight тяжёлых дашборд-запросов
Дата: 2026-10-24.
Проблема: тиковые Backlog/ZoneStats наваливались друг на друга под
нагрузкой, мешая OLTP-фронту.
Решение: single-flight (пропуск накопившегося тика + Warn), интервалы
backlog 30с→300с и zone_stats 60с→300с, кэш status.Cache TTL 60с,
метрики pass_seconds/skipped_ticks.
Ссылки: a2da05b; T-161.

### D-006 — ревью при исчерпанных квотах ревьюеров
Дата: 2026-10-24…31.
Проблема: периодически все доступные ревьюеры оказывались на лимитах
(T-161, T-164, T-197, T-214) — ревью срывалось или заменялось
самопроверкой.
Решение: формализованная цепочка ревьюеров с фолбэками (deepseek →
cursor grok → glm → kimi), один раунд на задачу; при недоступности всех —
ревью не проводится, факт фиксируется в отчёте и коммите; компенсация —
расширенной самопроверкой диффа.
Ссылки: f089656, a2da05b, b2dc950, 5e433a8; AGENTS.md «Review scheme».

### D-007 — keyset-пачки зон по фактическим id в zones collapse
Дата: 2026-10-29.
Проблема: батчирование окнами глобального id-пространства (послед.
42 млн, домены зоны разрежены) давало почти пустые пачки — боевая зона
5g.in: 726 батчей, перенос 1290 зон оценивался в десятки часов; найдено
на продуктиве при T-198 (перенос остановлен на 4-й зоне).
Решение: keyset-пачки LIMIT batch по id > последнего перенесённого из
фактических moving_ids, замкнутые границы [min, max] пачки; боевые
оценки — десятки пачек на зону.
Ссылки: 269f6a6; T-196, T-198.

### D-008 — дедлок пост-проверок zones collapse при малом пуле
Дата: 2026-11-02.
Проблема: пул CLI 2 соединения; transfer-соединение удерживалось до
возврата Run, PostChecks открывал второй Query при непотреблённом
однострочном агрегате → спрос 3 при пуле 2 → вечный Acquire (idle in
ClientRead, futex).
Решение: хелперы (zonesLeftCount/orphansCounts) с `rows.Close()` до
следующего запроса — по прецедентам zoneLeft/FetchLaravelStats/
VerifyCounters; интеграционный тест TestZonesCollapse_SmallPoolDeadlock
(красный 31.8с → PASS 1.6с).
Ссылки: 35e6628; T-217.

### D-009 — живой контур проверки формы вместо 6000 сокетов на запрос
Дата: 2026-11-03.
Проблема: checker открывал до 6000 fd на запрос (резолверы), CLI
`crawlerctl check` тоже; риск исчерпания fd и нестабильность под
нагрузкой.
Решение: долгоживущий контур checker.Runtime: ленивая сборка одна на
сервис, цепь резолверов LiveUDPPoolSize=16 (48 fd на сервис), общий
Fetcher с общими limitState, один render.Manager с ленивыми поколениями;
семафор web.live_concurrency=4 с быстрым 503 busy + Retry-After
(перегруз не пишется в web_checks); Close контура идемпотентен.
Ссылки: 203efa6; T-220.

### D-010 — атомарный reserve в login-лимитере дашборда
Дата: 2026-11-03.
Проблема: check-then-act гонка лимитера: параллельная пачка с одного IP
проходила 10 Verify вместо 5 — KDF жгла CPU (распределённый CPU-DoS).
Решение: `loginLimiter.reserve(ip)` — инкремент и проверка лимита под
одним мьютексом, 429 до verifyCredentials; success → reset; истёкшее окно
сбрасывается безусловно (P1-регрессию первого варианта поймало ревью,
закрыта тестом PartialWindowExpiry); остаточный риск — nginx limit_req.
Ссылки: 44dc3c1; T-231; docs/services.md.

### D-011 — деплой прода с ветки production
Дата: 2026-11-06.
Проблема: деплой с `master` деплоил незавершённую разработку; healthcheck
падал на юнитах, сознательно отключённых оператором.
Решение: `production` — движущийся ff-указатель на коммит из истории
`master` (коммиты только в master, релиз — ff-пуш, откаты — revert в
master + ff); healthcheck/откат пропускают юниты disable/mask, не роняя
деплой.
Ссылки: 98a0699, bdf1a8c; T-135; AGENTS.md «Deploy», docs/ci-cd.md.

### D-012 — прикладной ретрай 40P01 и разнос транзакций в retry-пути
Дата: 2026-11-07.
Проблема: дедлоки счётчиков (40P01) в retry-пути: инверсия блокировок в
RetryOnce — retryRequeue/retryFinalize в одной транзакции с чтением;
плюс периодические 40P01 в горячих путях записи.
Решение: retryRequeue/retryFinalize в отдельных транзакциях; прикладной
ретрай internal/db RetryDeadlock в RecordAndPublish/RecordEpisode/
retryDecide; дренаж терпит 3 пачки; метрика crawler_db_deadlock_retried_total.
Ссылки: 15ff3a3, 2ff07b9; T-268.

### D-013 — поведенческая логика как явные таблицы решений (FSM-волна)
Дата: 2026-11-07…08.
Проблема: рассыпанные флаги и условия статусов/жизненных циклов давали
асимметрии между воркерами и немотивированные ветки — их нельзя было

Снимки поведения до/после идентичны — специфицировали без смены
поведения. Политика закреплена в AGENTS.md (TZ-fsm.md).
Ссылки: a72128f, 86da8c6, a4a4713, e151052, 155224e, 05464b5, c9cdfb7;

### D-016 — OOM-цикл PG: закрепление планов курсорных выборок + гейт сканов
Дата: 2026-11-08…09.

### D-024 — ревью-артефакты в tmp/review проекта; дедуп коммит-дисциплины; сервисные коммиты — в корневом
Дата: 2026-11-16.

расширен: упавшая после мерджа проверка чинится отдельным сервисным
коммитом в main-ветке с номером задачи в сообщении (второе исключение
из «один коммит на задачу»), проектный ссылается на него.
Ограничение: tmp/ основного дерева вычищается air при make up* (D-025);
безопасность tmp/review/ обеспечивается тем, что ревью задач идёт в
воркри, где make up* запрещён; для артефактов в основном дереве
(bulk-ревью) выбор var/review против смены tmp_dir открыт оператору.

«Bulk code review and fixes», «Branches and worktrees», «Tests»,
«Commits»; глобальный ~/AGENTS.md Workflow, Temporary files (вне репо);
D-023 (первичный проход дедупликации).

### D-026 — moli v1.1.25: взрыв памяти — одна страница hh.ru; блокер абсолютен
Дата: 2026-11-16.
Проблема: взрыв памяти moli v1.1.25 (до ~2 GB за секунды, OOM) не
локализовался по гипотезам H-A/H-B/H-C; миграция и ретест блокированы
без триггера.
Решение: репро-лестница нашла детерминированный одиночный триггер —
одна CDP-навигация на https://hh.ru/ (даже сырая: без Fetch-перехвата и

`--http-max-response-size` не гасит, chromium 156 держит ту же страницу
в ~0.5 GiB (дефект moli-специфичен). Компенсаций нет:
restart_every_pages бессилен (одна страница = килл); живучесть — только
restart-политика + ретраи воркера (T-283). Каждый будущий ретест moli
включает hh.ru как canary-URL; skip-list/запасной движок для hh.ru —
направление, не запланировано. Upstream-репро одной строкой: одна
навигация на hh.ru → ~2 GB за 8–18 с → memcg kill.

### D-027 — T-285: per-engine skip-list — карта по движкам, substring-семантика, chromium-ключ запрещён
Дата: 2026-11-16.
Проблема: карточка T-285 задаёт «per-engine список паттернов» (ключ
`render.engine_skip_patterns`), но не фиксирует форму ключа, семантику
паттернов и поведение списков при engine=chromium — три
интерпретационных развилки.
Решение: (1) форма — карта `движок → список паттернов`
(`engine_skip_patterns: {moli: [hh.ru]}`): список движка активен ТОЛЬКО
при этом `render.engine` (воркер получает срез своего движка от врайринга
cmd/render-worker — переключение движка переключает и активный список,
без второй ручки); плоский список отклонён — он протекал бы между
движками при смене engine. (2) Семантика паттерна — substring финального
URL задачи: детерминированно, объяснимо оператору, поддерживает и хост
(hh.ru), и путь (/heavy/report); ложное срабатывание (суперстрока-хост)
стоит только доработку в chromium, не ошибку детекции. (3) Ключи — только
moli|lightpanda (валидация): chromium — терминальный движок фолбэка
(воркер B), скип на нём финализировал бы страницы, которые нечему
переработать; defense-in-depth — матчер дополнительно не матчит при
engine=chromium. Причина финализации/публикации — «engine-skip» в словаре
taskFinalizeReason; скип срабатывает с первой доставки (совпадение
детерминировано по URL — аргумент детерминизма класса cert T-159);
счётчик ошибок стейджа скип не считает (навигации не было — это
маршрутное решение, не ошибка рендера).
Ссылки: T-285; T-238 (publishFallback), T-239 (gate/budget); D-026;
docs/render.md «The per-engine URL skip-list»;
internal/renderworker/engineskip_test.go.
