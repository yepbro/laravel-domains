# Техническое задание: суточный счётчик проверок done_today

Версия: 1.1 (по итогам разбора лога медленных запросов боя 2026-10-24 —
первый запрос журнала; лог: `log_min_duration_statement = 3000`, T-177).
Дополнение к [`TZ_incremental_counters.md`](./TZ_incremental_counters.md)
(ТЗИ) — пересмотр её §13.7 («окна темпа не инкрементируются») на базе
живого замера: посыл «цена пропорциональна окну, индексы обслуживают»
не подтвердился для суточного окна.

Версия 1.1: хранение перенесено из отдельной таблицы `domain_checks_daily`
в landed-таблицу `crawler_counters` (T-175, миграция 000015, коммит
708aa81 — «будущие счётчики этого класса не плодят новых таблиц»);
отдельная миграция не нужна вовсе.

## 1. Сегодняшнее состояние и источник

Запрос `throughputSQL` (`internal/status/status.go:81`), секция темпа
дашборда (ТЗД §5.2): `done_today` — скалярный подзапрос

```sql
(SELECT count(*) FROM domains WHERE last_checked_at = current_date) AS done_today
```

Вызывается `status.Cache.Throughput` (TTL 60 с, T-161) циклом снимков
дашборда (T-129) — реально ~1 раз/мин — и `crawlerctl status`.

Статистика боя (журнал 24.10 09:39–12:20 UTC): 96 срабатываний порога
3 с; min 5,7 с / медиана 15,2 с / max 51,2 с.

## 2. Диагноз (EXPLAIN ANALYZE на боевой БД)

План **правильный** — Index Only Scan `domains_default_last_checked_at_idx`
(миграция 0014, T-171), `Index Cond: last_checked_at = CURRENT_DATE`.
Медленность — два множителя:

1. **Heap Fetches = 676 230 на 815 тыс. записей окна (83%)**. Index-only
   scan требует проверки heap-видимости для строк, чьи страницы не имеют
   бита all-visible. Окно `current_date` состоит из строк, обновлённых
   сегодня, — их страницы принципиально «грязные» до вакуума, который
   от них всегда отстаёт. 148 тыс. буферов (≈1,1 ГБ) за выполнение.
2. **Цена растёт к вечеру**: окно накапливает проверки за сутки (815 тыс.
   к 12:21 UTC; при живом конвейере ≈1,5–2 млн к концу дня) — вместе с
   числом heap fetches. Медиана 15 с — сериальное выполнение того, что
   в EXPLAIN с 2 parallel workers заняло 2,8 с: пул dashboard работает
   с `max_parallel_workers_per_gather = 0` (хук `db.NoParallelGather`,
   T-171 — осознанно, чтобы агрегаты не отбирали ядра у конвейера).

Часовые окна того же запроса (`results_hour`/`rendered_hour` по
`subdomain_results`) — 0,07 мс, здоровы: окно маленькое и индекс
`subdomain_results_checked_idx` отрабатывает как задумано.

Вывод: суточное окно по живым строкам структурно дорого — свежесть
строк и дешевизна подсчёта конфликтуют. Счётчик с инкрементами и
реконсиляцией разрывает конфликт (та же схема, что у T-175 для
render_pending и у ТЗИ для состояний конвейера).

## 3. Целевое состояние

1. `done_today` читается из `crawler_counters` — точечный Lookup по PK
   (микросекунды), полный проход `domains` из пути чтения исчезает.
2. Счётчик инкрементируется в тех же транзакциях, что и запись
   результата проверки (`httpworker/record.go`), — дельта бесплатна.
3. Авторитет — реконсиляция: пересчёт живым агрегатом; по возможности —
   FILTER-позицией совмещённого прохода ТЗИ (T-178: строки `domains` и
   так сканируются целиком, `last_checked_at = current_date` добавляется
   к существующим FILTER-колонкам — дополнительная цена нуля).
4. `elapsed_sec` (скаляр `now()`), `results_hour`, `rendered_hour`
   остаются живыми подзапросами — они дёшевы (§2).

## 4. Хранение: строка в crawler_counters, без миграции

Счётчик суток — строка `crawler_counters` (таблица T-175, миграция
000015, в бою после деплоя 708aa81 — на 24.10 прод на миграции 14):

| `name` | `value` |
|---|---|
| `checks:YYYY-MM-DD` (текущие сутки, вычисляет БД: `'checks:' \|\| to_char(current_date, 'YYYY-MM-DD')`) | число записей результатов с начала суток |

- Тот же ключевой паттерн, что у T-175 (`render_pending`), в рамках его
  проектного решения «таблица-счётчик общего вида — не плодят новых
  таблиц»; **новой миграции нет** — DDL не требуется.
- Ротация суток не создаёт работы: в 00:00 инкремент создаёт строку
  нового дня, вчерашняя остаётся историей (365 строк/год — пренебрежимо;
  потенциальный потребитель — суточные графики темпа, вне рамок).
- Имя дня формирует БД (`current_date`) — таймзона согласована с `now()`
  записи `last_checked_at` (T-058).
- До первой записи суток строки нет — читатель даёт `coalesce(…, 0)`
  (§7): часы простоя конвейера показывают честный ноль.
- Зависимость: реализация после деплоя T-175 (000015) и T-178 (000016 —
  колонка `crawler_counters.updated_at`, её пишут инкремент и
  реконсиляция); до них строку мог бы создать только бэкфилл — его
  нет (§10.4).
- Продолжение T-182 (TZ_slow_dns_share): рядом живёт вторая суточная
  строка `temp_error:YYYY-MM-DD` — числитель доли temp_error алерта
  T-080 (знаменатель — строка `checks:` этого ТЗ). Инкремент — той же
  транзакцией записи результата, только у temp_error-итогов;
  реконсиляция — FILTER-колонкой `status = temp_error` того же окна.

## 5. Инкременты

Владелец — `httpworker/record.go`, транзакция записи результата домена:
после `recordDomainSQL` вторым оператором

```sql
INSERT INTO crawler_counters (name, value)
VALUES ('checks:' || to_char(current_date, 'YYYY-MM-DD'), $1)
ON CONFLICT (name) DO UPDATE
    SET value = crawler_counters.value + EXCLUDED.value
```

где `$1` — `RowsAffected` батча `recordDomainSQL` (не число доменов
пачки доставки: дубль-доставка с `RowsAffected = 0` не даёт дельты —
ТЗИ §6.1.3).

### 5.1. Семантика расхождения с живым count (принять)

Живой `count(*)` считает домены, чья последняя проверка сегодня:
повторная проверка того же домена в те же сутки (temp_error-ретрай)
не растит число. Инкремент считает события записи — ретрай даёт +1.
Уточнение по фактической схеме (ревью T-179): дубль-доставки q:http —
тоже события записи (+1 каждая: охраны `check_state <> done` у
`recordDomainSQL` нет и не должно быть — повтор обязан
переопубликовать q:analyze); кроме того, окно `last_checked_at`
включает DNS-терминальные завершения (not_delegated и пр.), эпизода
HTTP не имеющие, — инкременты их не считают. Суммарное расхождение —
разница потоков «события записи HTTP» против «домены дня всех веток»,
восстанавливается реконсиляцией (§6); для gauge «темп работы» с
freshness 5 мин разница несущественна (доля DNS-only завершений и
повторов одного окна мала против накопленного значения суток).
Инвариант: реконсиляция сходится к живому агрегату, дрейф —
наблюдаемая метрика (§8).

## 6. Реконсиляция

Периодический проход monitor: `value` строки текущего дня :=
живой агрегат `count(*) … WHERE last_checked_at = current_date`,
до перезаписи читается прежнее значение, `|старое − новое|` — дрейф
(§8). До перезаписи строки нет — вставка со значением агрегата.

Размещение:

- при реализованном T-178 (совмещённый проход `ZoneStatsOnce`) —
  FILTER-позицией того же скана `domains` (цена нуля, период
  `zone_stats_interval`);
- до T-178 — временный часовой проход monitor той же семантики
  (собственный цикл по образцу `renderdebt.go` T-175; удаляется при
  деплое T-178). Час свежести для gauge темпа достаточен: между
  проходами точность держат инкременты.

## 7. Читатели

`throughputSQL` (`internal/status/status.go`): подзапрос `done_today`
заменяется на

```sql
(SELECT coalesce(value, 0) FROM crawler_counters
  WHERE name = 'checks:' || to_char(current_date, 'YYYY-MM-DD')) AS done_today
```

(`coalesce` — NULL-безопасность до первой записи суток, §4).
`status.Cache.Throughput` (TTL 60 с) не меняется — кэширует дешёвое
чтение (ТЗИ §8.6). `crawlerctl status` получает то же чтение без правок
выше по стеку. Тесты текста SQL (`status_test.go`) обновить.

## 8. Метрики и наблюдаемость

- Gauge дашборда `throughput.done_today` — имя/семантика без изменений
  (теперь «события записей результата за сутки» — §5.1, расхождение
  документировано здесь).
- Дрейф дневного счётчика — метрика по образцу T-175 (его алерт
  десинка `crawler_counters`):Warn при ненулевом дрейфе после стартового
  прохода; при реализованном T-178 — позиция `crawler_counters_drift`
  (метка `daily:checks`, ТЗИ §11).

## 9. Тестирование и приёмка

1. Юнит: текст нового `throughputSQL` (точный контракт); инкремент —
   параметры/`ON CONFLICT`/`RowsAffected = 0` без дельты; реконсиляция —
   upsert строки дня и расчёт дрейфа (по стилю ТЗИ §12.1, T-175).
2. Интеграция (`test/integration`): после эпизода конвейера
   `crawler_counters.checks:<день>` = числу записанных результатов;
   повторный эпизод одного домена (дубль-доставка) — дельта не двоится;
   смена суток эмулируется фиксированной датой — строка нового дня.
3. Приёмка: в журнале боевого сервера (порог 3 с, T-177) исчезают
   срабатывания `done_today` в сутки активного конвейера; `EXPLAIN`
   нового `throughputSQL` — точечные планы без скана `domains`;
   `crawlerctl status` показывает темп, сходный с до/после.

## 10. Принятые решения и отклонённые варианты

1. **Инкрементальный счётчик вместо живого окна — пересмотр ТЗИ §13.7**
   на базе замера §2: «не окупается» опиралось на цену ∝ окну; замер
   показал константу heap-fetch (83% окна, ≈1,1 ГБ чтений, 15 с медиана
   при выключенном параллелизме пула), меняющую баланс.
2. **Суточная гранулярность, не часовая**: часовые окна остались дёшевы
   (0,07 мс) — их не трогаем; дорогое именно календарное окно суток.
3. **Хранение — строка в `crawler_counters` (T-175), не новая таблица**:
   landed-прецедент 708aa81 прямо позиционирует таблицу общего вида
   («будущие счётчики этого класса не плодят новых таблиц»); отдельная
   таблица `domain_checks_daily` из версии 1.0 снята — исчезает и
   миграция (номер следующей свободной миграции остаётся за ТЗИ/T-178,
   чья §5 номера не фиксирует).
4. **История по дням сохраняется** (строка на сутки): бесплатно,
   потенциальный потребитель — суточные графики темпа; очистки не
   требует (365 строк/год).
5. Отклонено **«только поднять TTL»**: снижает частоту, не цену;
   темп дашборда теряет живость без нужды.
6. Отклонён **агрессивный vacuum ради all-visible**: помогает лишь
   хвосту окна — строки сегодня обновлены, их страницы «грязные» по
   определению; вакуум от свежих строк отстаёт всегда.
7. Отклонено **вернуть parallel gather пулу dashboard**: откат T-171 —
   агрегаты снова отбирают ядра у конвейера; счётчик решает без CPU.
8. Отклонён **бэкфилл первой строки**: до первой проверки суток честный
   ноль (`coalesce`, §7); прецедент T-175 с бэкфиллом миграции здесь не
   нужен — ретроспективных «сегодняшних» проверок до деплоя не возникает
   (инкремент начинается с первой записи).

## 11. Этапность

2. Читатель `throughputSQL` (§7), кэш без изменений, тесты текста.
3. Реконсиляция: временный часовой проход monitor (§6) с метрикой
   дрейфа (§8); при деплое T-178 — перенос FILTER-позицией в его
   совмещённый проход, временный цикл удаляется.
4. Документация: `docs/schema.md` (строка счётчика), `docs/services.md`
