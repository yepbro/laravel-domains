# Техническое задание: строка «Очереди» отчёта нагрузки — бэклог групп вместо сырого XLEN

Версия: 1.0. Задача T-188, этап 29. Источник — расхождение цифр,
найденное оператором 2026-10-25 (разбор боя в `tasks.md`, этап 29).

---

## 1. Сегодняшнее поведение

Строка «📬 Очереди» отчёта нагрузки (T-173) печатает **сырой XLEN**
каждого стрима — общее число записей в Redis Stream, включая уже
доставленные и подтверждённые (XACK), но ещё не срезанные XTRIM MINID
(T-141). Источник — `RedisQueues.Queues`
(`internal/monitor/load.go`, тип `QueueStat{Len, Read}`):

```go
length, err := s.RDB.XLen(ctx, stream).Result()   // Len = XLEN
...
if groups, err := s.RDB.XInfoGroups(ctx, stream).Result(); err == nil {
    for _, g := range groups {                    // Read = max entries-read
        if g.EntriesRead > st.Read { st.Read = g.EntriesRead }
    }
}
```

Формат строки — `formatLoadReport` (там же): `Len` сейчас + дельта `Len`
за окно (±N) + темп доставок из дельты `Read` (N/с).

Остальные потребители того же понятия считают иначе — **бэклог групп
потребления** `min(lag, XLEN) + pending` по всем группам (формула гейта
`BackpressureGate.Len`, `internal/queue/backpressure.go`):

| Потребитель | Формула |
|---|---|
| `crawlerctl status` (T-079, `internal/status`) | гейт: min(lag, XLEN) + pending |
| метрика `crawler_queue_depth` (воркеры, T-077) | гейт (тот же источник) |
| алерт замороженной очереди T-162 (`RedisStreamGroups`) | гейт |
| строка «Рендер-долг … лаг» (T-175) | гейт |
| **строка «📬 Очереди» отчёта нагрузки** | **XLEN — расходится** |

## 2. Диагноз (живой замер боя 2026-10-25 ~13:25 MSK)

Прод 155.212.174.88, ревизия c791ef5. Морозка 24.10 остановила
`crawler-scheduler`, а с ним TrimLoop (T-141) — подтверждённая история
перестала срезаться, XLEN накопил ~17 ч необрезанного хвоста:

| Стрим | Отчёт (XLEN) | XINFO GROUPS: lag + pending | `crawlerctl status` |
|---|---|---|---|
| q:dns | 2 | 0 + 0 | 0 |
| q:http | 952 | 0 + 0 | 0 |
| q:render | 136 500 | 27 409 + 120 | 27 580 |
| q:analyze | 71 784 (+654 за окно) | 0 + 1 | 0 |
| q:dead | 1 441 | групп нет | 1 441 |

Последствия для оператора:

- q:render завышен в ~5 раз (136,5 тыс. против бэклога 27,5 тыс.);
- q:analyze показывает **фантомный рост** (+654 за окно, 1.1/с доставок):
  анализатор успевает за потоком (lag 0), копится подтверждённая
  история — «очередь растёт» при пустом бэклоге;
- строка «Рендер-долг: … лаг 27 893» в том же отчёте противоречит
  строке «Очереди» (136 500) для одного и того же стрима.

Замечание: в норме (scheduler поднят) XLEN сходится к бэклогу с
точностью окна `redis.trim_interval`, но консистентность отчёта не
должна зависеть от работы обрезки.

## 3. Целевая семантика

`QueueStat.Len` становится глубиной бэклога стрима — ровно как
`BackpressureGate.Len`:

1. **Группы есть**: `Len = Σ по группам (min(lag, XLEN) + pending)`;
   `lag = −1` (неопределён, Redis < 7.0 после обрезки недоставленного,
   кламп T-168) — вклад только `pending`.
2. **Стрим есть, групп нет** — `Len = XLEN` (как у гейта: ни одна запись
   не доставлена, накопление без потребителя обязано быть видно;
   «территория» алерта T-162).
3. **Стрима нет** (no such key) — `{0, 0}` (как сейчас).
4. **q:dead** — всегда XLEN: групп у карантина нет по построению,
   глубина — инвентарь оператора (та же семантика у
   `DeadDepthMetrics` T-154 и `crawlerctl status`).
5. `Read` (темп доставок) — max `entries-read` по группам, без изменений.

Дельта ±N за окно становится ростом/дренажем **реального бэклога**
(сегодня — мусорная дельта длины стрима). Пример после правки:
`q:analyze 0 (±0, 1.1/с)` — доставки идут, очередь пуста.

## 4. Изменения в коде

`internal/monitor/load.go`, `RedisQueues.Queues` (≈ строки 402–448):

- метод уже зовёт и `XLen`, и `XInfoGroups` — новых вызовов Redis нет:
  бэклог считается в том же цикле по уже прочитанным `groups` и `xlen`;
- для п. 3 семантики XLEN читается и когда групп нет (сейчас читается
  всегда — сохранить);
- **формулу не дублировать**: выделить общий расчёт
  `depth(groups, xlen)` и пользоваться им здесь и в
  `RedisStreamGroups.StreamGroups` (`streamgroups.go`) — формулы гейта,
  алертов и отчёта не имеют права разъехаться (инвариант из шапки
  streamgroups.go: «источник обязан соглашаться…»);
- обновить док-комментарий `RedisQueues` (сейчас «поверх XLEN + XINFO
  GROUPS») и комментарий блока «Очереди» в `LoadReportLoop` (≈ 653).

`formatLoadReport` не меняется (печатает `Len` как есть).
