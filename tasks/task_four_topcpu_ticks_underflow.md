# Техническое задание: топ-CPU отчёта нагрузки — андерфлоу тиков при рестарте процессов

Версия: 1.0. Задача T-189, этап 29. Источник — боевой отчёт нагрузки
2026-10-25 (прод 155.212.174.88, ревизия c791ef5).

---

## 1. Симптом

Строка «🧮 Топ CPU» отчёта нагрузки (T-173):

```
🧮 Топ CPU: postgres 310613997334638.2я, headless-shell 0.8я, render-worker 0.1я
```

«Ядер» у postgres — 3.1·10¹⁴ при 4 ядрах на хосте. Соседний (за ~10 мин)
отчёт был корректен: `postgres 0.6я`. В том же окне у postgres сменилось
число процессов: 18 → 16 (агрегат по имени в «Топ память») — процесс
перезапускался (recycling соединений/рестарт части процессов БД).

## 2. Диагноз

`internal/monitor/load.go`:

- `ProcAgg.Ticks uint64` (≈ 93–95) — сумма тиков CPU (utime+stime) всех
  процессов **имени**; снапшот `Load` суммирует по имени (≈ 342);
- дельта окна в `LoadReportLoop` (≈ 643–651):

```go
if dt := agg.Ticks - prev.ticks[name]; dt > 0 {   // uint64!
    procCPU[name] = float64(dt) / perCore
}
```

`agg.Ticks − prev.ticks[name]` — **беззнаковое вычитание**: после
рестарта процессов имени сумма тиков по имени падает (новые процессы
стартуют с малыми utime+stime), `dt` андерфлоуится к ≈ 1.8·10¹⁹,
защита `dt > 0` пропускает мусор, деление на `perCore` (тики одного
ядра за окно, ~10⁴–10⁵) даёт ~10¹⁴ «ядер». Числа симптома совпадают
по порядку величины.

Тот же класс проблемы невозможен для `cpuDelta` (/proc/stat, monotonный
счётчик ядра) — страдает только агрегат по имени процесса.

## 3. Решение

Перед вычитанием сравнивать, дельту считать только у монотонно
выросших имён — рестартованное за окно имя честно пропускается
(ни 0, ни мусора):

```go
for name, agg := range st.Procs {
    if agg.Ticks <= prev.ticks[name] {
        continue // рестарт/исчез процессов имени: тики немонотонны — окно пропущено
    }
    procCPU[name] = float64(agg.Ticks-prev.ticks[name]) / perCore
}
```

Отвергнуто: кламп значения сверху числом ядер — лечит симптом и прячет
причину; хранение отдельных PID — усложнение без пользы оператору
(топ по именам).

## 4. Тесты

`internal/monitor/load_test.go`:

- продолжение `TestLoadReportLoop_OnePass` (или отдельный кейс
  `TestLoadReportLoop_ProcRestart`): первый проход — postgres Ticks
  100 000; второй — postgres Ticks 1 000 (рестарт) при живых прочих
  именах: postgres **отсутствует** в топ-CPU, прочие имена корректны,
  мусорных значений (> числа ядер × разумный запас) нет;
- регресс на формат: значение топа не уходит в 10¹⁴ (пример
  фикстуры — `%s %.1fя` из симптома).

## 5. Критерии приёмки

1. `make test`, `make lint` — зелёные.
2. На dev-стеке рестарт postgres между проходами отчёта не порождает
   мусорных строк топа (имя просто исчезает из топа на одно окно).
