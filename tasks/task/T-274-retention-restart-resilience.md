# Задача T-274: устойчивость retention к рестартам — конфиг-ключ потолка выборки + персистентный курсор дренажа

Версия: 1.0. Этап 44. Приоритет: P1 (прямое следствие P0-хотфикса T-273).
Источники: расследование T-273 (варианты B и C —
[`prod-reports/2026-11-10-005208-t271-research.md`](../../prod-reports/2026-11-10-005208-t271-research.md)),
прод-факты 10–11.11.2026 ([итог дренажа](../../prod-reports/2026-11-11-000550-final-drain.md),
runbook [`docs/operations.md`](../../docs/operations.md) §4.6 и журнал §5).

## 1. Проблема

- Курсор дренажа retention живёт в памяти процесса http-worker; каждый рестарт
  сбрасывает его в ноль — «catch-up-круг: старт процесса…»
  (`internal/content/retention.go:540-545`).
- Первый проход после рестарта обязан обойти «чистый префикс» истории
  subdomain_results (предикат «есть что чистить» не в индексе — heap-визит
  каждой строки): замеры прода — **~60 мин на idle** (проход 4, ночь 10–11.11,
  впритык к потолку), **>60 мин под полным фронтом** (проходы 1–3 не влезли
  в 3600 с, `retention_errors_total` = 3).
- `SelectTimeout` — константа кода 3600 с (`DefaultRetentionSelectTimeout`,
  `internal/content/retention.go:152`), конфиг-ручки нет — сменить потолок
  без деплоя невозможно.
- Рестарты происходят чаще, чем казалось: каждый деплой, плюс внеплановые
  (внешний power-cycle виртуалки 11.11 11:03 — гипервизор/панель хостинга,
  ACPI-poweroff + старт; потенциальные OOM-килл процесса, обслуживание
  хостинга). После каждого — часовая прогулка по префиксу с лотереей
  таймаута; проигрыш = retention стоит до спокойного окна (инцидент,
  сутки разбора 10–11.11).

## 2. Решение (вариант B + C-курсор из расследования; БЕЗ частичного индекса)

### R1. Конфиг-ключи потолков выборки

- `content.retention_select_timeout` — новый ключ в семействе
  `retention_*` (`internal/config/config.go:554-569`), **дефолт 7200 с**
  (удвоенный запас обхода префикса под нагрузкой; сейчас — константа 3600 с).
- `render.late_select_timeout` — аналогичная ручка для позднего переиздателя
  (`internal/httpworker/renderlate.go:109-121`), дефолт остаётся 300 с
  (выборка переиздателя адаптивная и быстрая — ручка на всякий случай).
- Проводка в `cmd/http-worker/main.go`: значения из конфига в
  `RetentionOptions.SelectTimeout` / `LateOptions.SelectTimeout`; пустое
  или нулевое значение — дефолт (текущая семантика `withDefaults`
  сохраняется).

### R2. Персистентный курсор дренажа retention

- Курсор (`checked_at` + `retentionKey{zone_id, domain_id, subdomain_id,
  variant}`) сохраняется в БД **в транзакции коммита каждой пачки**;
  частота — сотни записей за проход (155 за 16 ч) — нагрузка ничтожна.
- Хранение: **миграция** — компактная таблица состояния (одна строка,
  upsert). НЕ `crawler_counters` (композитный ключ не лезет в числовое
  значение). Конкретный дизайн — на усмотрение исполнителя; критерии:
  атомарность с коммитом пачки, отсутствие блокировок на пути горячего
  фронта.
- Старт процесса: курсор читается из БД; отсутствие/некорректность
  (например, отметка в будущем) — нынешнее поведение (ноль → полный
  catch-up).
- **Важно**: существующие причины принудительного сброса на catch-up-круг
  (снятие рендер-долга, переполнение списка ретраев, fallback-сутки —
  комментарий `retention.go:540-545`) обязаны чистить и персистентное
  состояние, иначе сброс не сработает.
- Семантика интерлоков и пропусков не меняется.

### R3. Тесты

- Проводка конфига: ключ распарсен, применяется; отсутствие — дефолт.
- Курсор: round-trip (коммит пачки → состояние сохранено); **главный тест —
  «рестарт»** (новый цикл читает состояние) → дренаж продолжает с курсора,
  а не с нуля; принудительный сброс чистит состояние; корявое состояние →
  старт с нуля.
- Тест T-273 «catch-up с нулевого курсора укладывается в SelectTimeout»
  остаётся зелёным (поведение без сохранённого состояния не меняется).

### R4. Документация

- `docs/content.md`: новые ключи, персистентный курсор, поведение
  рестартов (штраф отменяется).
- `docs/operations.md` §4.6: убрать предупреждение «каждый рестарт
  http-worker = новый catch-up» (после T-274 рестарт продолжает с курсора);
  журнал §5 — заметка о закрытии риска.
- `deploy.md` §5 — если там перечислены ключи конфига, дополнить.

## 3. Критерии приёмки

1. `make test` + `make test-race` (content и httpworker входят в RACE_PKGS)
   + `make lint` — зелёные; `make test-integration` — **обязателен**
   (добавляется миграция).
2. Тест «рестарт продолжает с персистентного курсора» — зелёный.
3. Конфиг-ключи работают (тест проводки); дефолт retention — 7200 с.
4. Документация обновлена.

## 4. Вне скоупа

- Частичный индекс по предикату «есть что чистить» (C-индекс) — отдельное
  решение после замера write-усиления (ломает HOT, отвергнуто в
  T-201/T-104). Если персистентного курсора + 7200 с окажется достаточно —
  не нужен вовсе.
- F2 (бюджет памяти PG), разбор q:dead — отдельные задачи.

## 5. План деплоя (для основной сессии/оператора)

- Первый деплой T-274 сам выполняет один последний полный catch-up
  (сохранённого курсора ещё нет): деплой в спокойном окне ЛИБО под
  присмотром — потолок 7200 с даёт высокие шансы и под нагрузкой
  (idle-обход ~60 мин, под фронтом — до ~2 ч).
- Верификация: первый проход завершается (INFO «проход retention контента»
  с итогами); **следующий** рестарт http-worker (штатный деплой) — дренаж
  продолжает с курсора: проходы короткие, чистый префикс не обходится,
  `retention_errors_total` не растёт.

## 7. Реализация (заметки исполнителя)

- **Таблица состояния** — `retention_drain_cursor` (миграция 000020):
  одна строка (`id smallint PK CHECK (id = 1)`), колонки курсора
  `(checked_at, zone_id, domain_id, subdomain_id, variant)` + `updated_at`
  для диагностики. Не `crawler_counters` (композитный ключ не лезет в
  bigint); отдельная таблица вместо generic key-value — типизированные
  колонки без jsonb.
- **Атомарность с пачкой**: upsert исполняется в tx `retentionPurge`
  последним оператором до Commit — позиция не опережает зафиксированную
  чистку; сбой пачки (включая сбой самого upsert'а) откатывает всё.
  Пачка с отложенными защитой строками позицию в БД НЕ двигает
  (`len(batch)==len(selected)`, ревью P1): список ретраев
  неперсистентен, его потеря при рестарте восполняется перечитыванием
  защитного окна; in-memory курсор двигается как раньше (зонд возвращает
  ключи в пределах жизни процесса). Зонд ретраев и точечный дренаж
  домена (T-187) курсор не двигают (`retentionPurge(..., nil)`).
- **Принудительные круги** (снятие рендер-долга, переполнение списка
  ретраев, fallback-сутки) удаляют строку DELETE'ом в МОМЕНТ ПЛАНА
  (`planCircle`, ревью P2): рестарт в окне между планом и применением
  (≤ интервала) попадает в полный catch-up с нуля; сохранение позиции
  подавлено до применения круга (иначе пачки того же прохода воскресили
  бы строку). Сбой отражения плана — Warn без ошибки прохода
  (деградация к продолжению со старой позиции — дороже, без потери).
- **Старт цикла** (`RetentionLoop`): чтение
  `retentionLoadCursor`; отсутствие строки/нулевая отметка — нулевой
  курсор (прежнее поведение); отметка в будущем (допуск 1 мин на
  расхождение часов) — Warn + старт с нуля; сбой чтения — Warn + старт
  с нуля. Таблицы нет (42P01, БД до 000020) — Info один раз на процесс,
  персистентность выключается (в т.ч. при первом сбое upsert'а посреди
  работы) — деградация к поведению T-273, не поломка (стиль
  errRetentionNoCounterTable).
- **RetentionOnce** (runbooks T-167 путь А) персистентное состояние не
  читает и не пишет: владелец состояния — цикл http-worker,
  изолированный дренаж не должен двигать/откатывать его позицию
  (идемпотентная чистка с нуля безопасна и без состояния).
- **Конфиг**: `content.retention_select_timeout` (дефолт 2 ч в
  `Default()` и константе `DefaultRetentionSelectTimeout` 3600→7200 с;
  дублирование дефолта — устоявшийся паттерн retention-ключей, config
  не импортирует пакеты сервисов), `render.late_select_timeout`
  (дефолт 300 с). Оба: 0 — дефолт кода (`withDefaults`), коридор
  валидации 1m..24h; env `CRAWLER_CONTENT_RETENTION_SELECT_TIMEOUT` /
  `CRAWLER_RENDER_LATE_SELECT_TIMEOUT`.
- **Тесты**: юнит — round-trip в tx пачки, сбой upsert'а откатывает
  пачку, позиция не двигается за отложенные строки (полная/частичная
  отложка + восстановление «рестартом»), план круга чистит строку в
  момент плана и подавляет сохранения (переполнение списка), сбой
  отражения плана — Warn, круг сбрасывает строку и переписывает её
  круговыми пачками, ГЛАВНЫЙ «рестарт продолжает с курсора»
  (RetentionLoop №2 первой выборкой стартует от сохранённой позиции),
  некорректное состояние → ноль, 42P01 → работа без персистентности
  (старт и посреди работы), RetentionOnce не трогает состояние;
  интеграционный `TestContent_RetentionCursorRestart` (живая PG: цикл 1
  → строка курсора → «рестарт» → запись позади курсора не посещается,
  впереди — чистится; RetentionOnce добирает позади — потери нет) +
  контракт одной строки (CHECK id=1).
