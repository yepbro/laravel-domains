# Техническое задание: страховочный проход переанализа — курсор по времени вместо полного скана

Версия: 1.0 (по итогам разбора лога медленных запросов окна после
деплоя 2026-10-25 12:37 MSK — запись №12 журнала; лог:
`log_min_duration_statement = 3000`, T-177). Класс болезни — тот же,
что у дренажа retention (T-185): проход без индекса по фильтруемой
колонке вытаптывает таблицу с нуля каждый тик, хотя множество
кандидатов — горстка свежих хвостов.

---

## 1. Сегодняшнее состояние и источник

Запрос `reanalyzeSelectSQL` (`internal/analyzer/reanalyze.go:89`):

```sql
SELECT r.zone_id, r.domain_id, r.subdomain_id, r.variant,
       d.label || '.' || z.name
FROM subdomain_results AS r
JOIN domains AS d ON d.zone_id = r.zone_id AND d.id = r.domain_id
JOIN zones AS z ON z.id = r.zone_id
WHERE r.rules_version IS DISTINCT FROM $1::int4
  AND d.status <> $2::int2
  AND ($3::int2 IS NULL OR r.zone_id = $3)
  AND (r.zone_id, r.domain_id, r.subdomain_id, r.variant)
      > ($4::int2, $5::int8, $6::int2, $7::int2)
ORDER BY r.zone_id, r.domain_id, r.subdomain_id, r.variant
LIMIT $8
```

($1 = версия правил, $8 = 5000 — DefaultReanalyzeBatch.) Вызывается
часовой тик `ReanalyzeLoop` (DefaultReanalyzeInterval) через
`ReanalyzeOnce` — **каждый проход с нулевым курсором** (resultKey{});
полный дренаж `ReanalyzeDrain` (смена правил, Subscribe T-068;
`crawlerctl reanalyze`) ходит тем же SQL пачками с PK-курсором.

Статистика окна 25.10 09:38–13:15 UTC: 3 срабатывания порога 3 с
(10:37:36, 11:37:36, 12:37:36 — ровно часовой тик), 18,2–24,9 с;
пачки крошечные: selected = 56 и 206 (журнал analyzer «проход
переанализа»). Стоимость не зависит от результата: чтобы найти
горсть устаревших, проход перечитывает таблицу целиком.

## 2. Диагноз (EXPLAIN ANALYZE на боевой БД, 25.10)

`subdomain_results`: ≈4,8 млн строк, приток ≈3 млн/сут (T-185).

| Вариант | План | Время | Просмотрено впустую | Буферы |
|---|---|---|---|---|
| как в бою (курсор с нуля) | Parallel **Seq Scan** `subdomain_results` + фильтр `rules_version` | **19 880 мс** | 4 822 000 | 441 782 (≈3,4 ГБ, чтения 423 тыс. / 3,3 ГБ), dirty 1198 |
| курсор по времени (окно 2 ч, проба) | Bitmap Index Scan `subdomain_results_checked_idx` + Heap + Sort | 3 028 мс | 132 000 (окно) | 87 210 |
| целевой режим (живой курсор ~1 ч) | тот же | **≈300–1000 мс** | окно часа | ~окно |

1. **Планировщик прав, форма доступа ошибочна в корне**: `rules_version`
   не индексирован сознательно (HOT-инвариант: апдейты анализа —
   миллионы/сутки; класс T-104/T-175), PK-курсор с нуля не отсекает
   ничего — seq scan по 4,8 млн строк оптимален для планировщика и
   разумен только для полного дренажа.
2. **Множество кандидатов тика — свежий срез**: строки устаревают
   двумя путями — новые эпизоды (INSERT с `rules_version` NULL,
   T-058; свежий `checked_at`) и смена правил (полный дренаж по
   Subscribe). Хвосты тика (56/206) — свежие записи, чей анализ
   отстал/потерялся; всё устаревшее-старое вычищается дренажом при
   предыдущей смене правил.
3. **Стоимость растёт линейно с таблицей** (приток 3 млн/сут): сегодня
   20 с/час, через месяц — минуты;.dirty-страницы (hint bits, 1198)
   добавляют WAL.
4. Время-курсор ложится на готовый `subdomain_results_checked_idx`
   (T-171): окно часа ≈ 15 тыс. строк, heap-визиты ради
   `rules_version` — доля секунды.

## 3. Целевое состояние

1. Часовой тик читает только свежий срез (от живого курсора): доли
   секунды, стоимость не зависит от размера таблицы.
2. Полный дренаж при смене правил и `crawlerctl reanalyze` — без
   изменений (PK-порядок, редкий, осознанно полный).
3. HOT-инвариант не тронут: индекс по `rules_version` не появляется.

## 4. Изменения

### 4.1. Курсор тика по времени

`ReanalyzeLoop` хранит курсор между проходами (в состоянии цикла,
образец `retentionCursor` retentiondrain.go T-185):

```sql
WHERE r.rules_version IS DISTINCT FROM $1::int4
  AND d.status <> $2::int2
  AND ($3::int2 IS NULL OR r.zone_id = $3)
  AND (r.checked_at, r.zone_id, r.domain_id, r.subdomain_id, r.variant)
      > ($4, $5::int2, $6::int8, $7::int2, $8::int2)
ORDER BY r.checked_at, r.zone_id, r.domain_id, r.subdomain_id, r.variant
LIMIT $9
```

- композитный ключ (время + PK) — детерминированные пачки и корректная
  пагинация (row-value по тому же ключу);
- план: индекс `subdomain_results_checked_idx` (T-171) режет окно,
  сортировка пачки — в памяти (тысячи строк);
- курсор продвигается за последнюю строку непустой пачки; пустая
  пачка — окно исчерпано, курсор ждёт следующего тика.

### 4.2. Якорь старта — ограниченное окно, не эпоха

Старт цикла и восстановление после сбоя — курсор
`now() - DefaultReanalyzeLookback` (24 ч, константа с обоснованием в
комментарии): страховка тика обслуживает свежие потери; всё старше
либо проанализировано, либо территория полного дренажа при следующей
смене правил. Остаточный класс (потерянное старше 24 ч без смены
правил) недостижим в модели (`rules_version` меняется только записью
анализа или сменой правил; новый эпизод даёт свежий `checked_at`) и
подстрахован наблюдаемостью q:dead/q:analyze (T-162) —
задокументировать.

### 4.3. Полный дренаж — без изменений

`ReanalyzeDrain` (Subscribe при смене правил, `crawlerctl reanalyze`)
остаётся на PK-курсоре с нуля: редкий, обязан пройти всё множество;
его стоимость (один полный проход на смену правил) осознанна.
Разделение форм зафиксировать в комментарии SQL: PK-форма — дренаж,
время-форма — тик.

### 4.4. Зависимости

T-171 (индекс `subdomain_results_checked_idx`). Миграций нет.

## 5. Риски и границы

1. Bitmap+heap окна часа под I/O-штормом — секунды (замер §2, проба
   2ч дала 3 с под текущей нагрузкой); контроль — журнал T-177;
   шторм лечится T-191.
2. Тик и дренаж одновременно (смена правил во время тика) — оба
   идемпотентны на уровне «выборка+публикация» (правило T-071:
   после фиксации новой rules_version строка не отбирается),
   пересечение пачек безопасно.
3. Lookback 24 ч и темп тика 1 ч: свежая потеря подбирается не
   позже lookback+тик — для страховки (основной путь — немедленная
   публикация record.go и Subscribe) достаточно.

## 6. Принятые решения и отклонённые варианты

1. **Время-курсор** — прецедент T-185 (retention): та же пара
   «неиндексируемый фильтр × свежий срез», то же решение; замер
   20×–60× на текущих данных, независимость от роста таблицы.
2. Отклонён **индекс по `rules_version`** (в т.ч. частичный):
   HOT-инвариант `subdomain_results` — апдейты анализа миллионы/сут
   стали бы non-HOT (класс T-104/T-175/T-182).
3. Отклонена **EXISTS-проба перед пачкой** («дёшево проверить
   пустоту»): доказательство пустоты — тот же полный скан.
4. Отклонено **расширение интервала тика** (час → сутки): лечит
   частоту, не стоимость прохода, и деградирует свежесть страховки;
   после §4.1 не нужно.
5. Отклонена ** персистентность курсора в БД** (crawler_counters):
   якорь lookback §4.2 делает потерю курсора дешёвой (одно окно
   24 ч), состояние цикла в процессе достаточно (стиль T-185 —
   курсор в состоянии цикла, круг с якоря).

## 7. Тестирование и приёмка

1. Юнит: SQL-контракт время-формы (композитный курсор, ORDER BY,
   LIMIT); PK-форма дренажа не изменилась; цикл с фейком — курсор
   живёт между проходами, продвигается пачкой, пустая пачка не
   двигает; якорь старта = now−lookback.
2. Интеграция: свежая строка без анализа подбирается тиком и
   публикуется; проанализированная не отбирается; смена правил —
   дренаж с нуля находит старое (вне lookback); повторный тик не
   переизбирает.
3. Приёмка: записи `reanalyzeSelectSQL`-тика исчезают из журнала
   медленных (дренаж при смене правил — остаётся, осознанно);
   журнал analyzer «проход переанализа» — прежние числа; `make
   test` + `make test-integration` зелёные.
