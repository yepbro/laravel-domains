# Техническое задание: возврат истёкших lease — пачка PK-пробами и курсор дренажа вместо двойного скана диапазона

Версия: 1.0 (по итогам разбора лога медленных запросов окна после
деплоя 3bffc62 — 2026-10-25 18:16 → 10-26 03:05 UTC, запрос №3 по
суммарному времени БД; лог: `log_min_duration_statement = 3000`, T-177,
локальная копия `tmp/pg_slow_after_3bffc62.log`). Класс болезни — тот же
«мёртвый префикс + перепрочтение пройденного», что у
[`TZ_slow_render_requeue.md`](./TZ_slow_render_requeue.md) (T-181) и
ретраев ([`TZ_slow_temp_error_retry.md`](./TZ_slow_temp_error_retry.md),
T-191), но здесь множитель — сам план UPDATE-стороны.

---

## 1. Сегодняшнее состояние и источник

Оператор `leaseUpdateSQL` (`internal/scheduler/lease.go:103`): один
CTE-оператор «выборка пачки истёкших аренд + UPDATE + дельты счётчиков
зон» (T-029/T-178): CTE `b` — до `LeaseBatch` (5000) строк
`check_state = 1, queued_at < now() − lease` по индексу
`domains_lease_idx (queued_at, zone_id, id) WHERE check_state = 1`
(миграция 000008, T-104), `upd` — перевод в pending с guard-перепроверкой
отбора на момент блокировки строки (гонки с воркерами), `zc` — дельты
`zones`. Вызывается `LeaseOnce` ← дренаж `LeaseWatch` (цикл lease/2 =
15 мин; пачки повторяются, пока проходят целиком).

Статистика окна после 3bffc62 (8,8 ч): **75 событий** порога 3 с
(каждая штормовая пачка), медиана **8,1 с**, max **111 с**, Σ1288 с —
7 % медленного времени БД. Журнал scheduler: дренажи возвращают
1–67 тыс. доменов (полуночный шторм суточной перепроверки + ретраи
temp_error: 21:20 UTC дренаж 25.10 перевёл 104 297 доменов); каждая
пачка 5000 — отдельный оператор, каждый со своим сканом.

## 2. Диагноз (EXPLAIN на боевой БД, 26.10)

1. **UPDATE-сторона читает весь истёкший диапазон, а не пачку.** План:
   `Update → Nested Loop`, внешняя сторона — Index Scan
   `domains_default_queued_at_zone_id_id_idx` с условием
   `queued_at < now() − 30m` **без LIMIT**, внутренняя — подзапрос `b`
   (LIMIT 5000); соединение — Join Filter по (zone_id, id). Guard-условия
   внешней стороны (check_state/status/queued_at) планировщик закрывает
   тем же lease-индексом, PK-пробы не выбирает. Итог: за пачку истёкший
   диапазон сканируется **дважды** (b + upd), стоимость пачки ∝ размеру
   диапазона, а не пачки. `WITH b AS MATERIALIZED` план не меняет —
   проверено на бою.
2. **Мёртвый префикс индекса между вакуумами.** Замер 26.10 ~06:40 UTC:
   SELECT-часть с `actual rows=0` (возвратить нечего) — **15 928
   буферов, 10 212 чтений ≈ 80 МБ, I/O 11,4 с**: за полчаса до замера
   штормовой дренаж перевёл десятки тысяч аренд; их индексные записи
   мертвы до вакуума, но сканируются — `status` в индексе нет, каждая
   запись требует heap-визита. Размер lease-индекса по партициям —
   **273 МБ при 996 живых записях** (`check_state = 1` на момент
   замера). Каждая пачка каждого дренажа начинает скан **с начала
   индекса** — 14 пачек штормового дренажа 14 раз перечитывают один
   префикс.
3. **Автовакуум префикс чистит редко**: порог
   `autovacuum_vacuum_scale_factor 0.02` × 42,3 млн строк
   `domains_default` ≈ 846 тыс. мёртвых; суточная волна перепроверки
   (~1,5–2 млн enqueue→возврат/запись) даёт 2–3 вакуума в сутки —
   между ними префикс копится до ~миллиона записей (десятки секунд
   холостого скана за пачку).
4. `deleted`-домены дорожку не создают: `check_state = 1 AND status = 6`
   — 0 строк (замер); доля не-находок среди истёкших отсутствует.
   Дорожка — только мёртвые версии возвращённых/записанных аренд.

## 3. Целевое состояние

1. UPDATE-сторона — точечные PK-пробы по пачке (не скан диапазона):
   стоимость перевода ∝ пачке, а не размеру истёкшего диапазона;
   guard-перепроверки (check_state/status/queued_at на момент
   блокировки) сохраняются — защита от гонок с воркерами та же.
2. Мёртвый префикс читается **один раз за жизнь процесса**, а не каждой
   пачкой: курсор дренажа `(queued_at, zone_id, id)` в состоянии
   `LeaseWatch` (прецеденты — время-курсоры T-185/T-193).
3. Атомарность «выборка = перевод» сохраняется: обе операции в одной
   транзакции (сегодня даёт один оператор).
4. HOT-инвариант не тронут: индексов новых нет, `status` в индексы не
   попадает.

## 4. Изменения

### 4.1. Выборка пачки с курсором

```sql
SELECT zone_id, id FROM domains
WHERE check_state = 1 AND status <> 6
  AND queued_at < COALESCE($1::timestamptz, now()) - make_interval(secs => $2)
  AND (queued_at, zone_id, id) > ($3::timestamptz, $4::int2, $5::int8)
ORDER BY queued_at, zone_id, id LIMIT $6
```

- композитный курсор (ключ индекса целиком) — детерминированные пачки,
  пагинация без пропусков/повторов; NULL-курсор (старт) — как сегодня,
  с начала индекса;
- корректность движения: всё с ключом ≤ курсора уже возвращено
  (истёкшесть зависит только от queued_at — при равном queued_at у
  строк одинаковая судьба; неистёкшие на момент прохода лежат правее
  порога, значит правее курсора, и состарятся впереди него); повторная
  постановка домена пишет свежий `queued_at` — правее порога и курсора;
  `deleted`-строки левее курсора перепрыгиваются навсегда — их и не
  должно возвращать (комментарий lease.go, ТЗ 13.1);
- рестарт процесса сбрасывает курсор — стартовый полный дренаж
  сохраняется (T-012/T-029), идемпотентность проходов не меняется.

### 4.2. Перевод пачки PK-пробами

```sql
WITH upd AS (UPDATE domains AS t
  SET check_state = $1, queued_at = NULL
  FROM unnest($2::int2[], $3::int8[]) AS u(zone_id, id)
  WHERE t.zone_id = u.zone_id AND t.id = u.id
    AND t.check_state = 1 AND t.status <> 6
    AND t.queued_at < COALESCE($4::timestamptz, now()) - make_interval(secs => $5)
  RETURNING t.zone_id),
zc AS (UPDATE zones AS z SET domains_queued = z.domains_queued - c.n,
       domains_pending = z.domains_pending + c.n
       FROM (SELECT zone_id, count(*) AS n FROM upd GROUP BY zone_id) AS c
       WHERE z.id = c.zone_id)
SELECT zone_id FROM upd
```

- форма — пакетный UPDATE проекта (`db.Update`-стиль, T-028): planner
  ведёт от `unnest` и пробирует `domains` по PK — альтернативного
  lease-скана на стороне UPDATE больше нет;
- guard-фильтры (check_state/status/queued_at) — те же, после блокировки
  строки: семантика гонок («воркер записал результат между выборкой и
  блокировкой — не возвращать») не меняется; счёт дренажа — по
  `RETURNING` (строки, переведённые именно этим проходом);
- литералы check_state/status в тексте через `model.*` — как сегодня
  (предикат частичного индекса обязан быть доказуем для SELECT-стороны).

### 4.3. Транзакция и курсор дренажа

- `LeaseOnce` выполняет SELECT + UPDATE в одной транзакции (`pool.Begin`,
  образец `renderSelectPending` T-181): атомарность эквивалентна
  сегодняшнему одному оператору; `LeaseBatch` не растёт.
- `LeaseWatch` хранит курсор между пачками и дренажами (поле состояния
  цикла, стиль `retentionCursor` T-185): курсор = композитный ключ
  последней строки переведённой пачки; пустая пачка не двигает.
- Пул scheduler уже под `LockTimeout(30s)` (T-192) и `NoParallelGather`
  (T-171) — новые операторы наследуют обе сессии.

### 4.4. Зависимости

Миграций нет, схема/индексы не меняются. `db.DB` достаточно
(точечные операторы; `Begin` — через интерфейс пула, как T-181).

## 5. Риски и границы

1. **Хвост префикса за курсором при рестарте** читается заново (стартовый
   дренаж) — осознанно: потеря курсора дешевле полного прохода
   (философия T-193 §6.5); при живом процессе префикс не перечитывается.
2. **Курсор и параллельный второй scheduler**: сегодня невозможен
   (один экземпляр юнита); guard-перепроверки делают пересечение пачек
   безопасным даже при появлении.
3. Мёртвый префикс остаётся фактом партиции до вакуума — задача не
   лечит bloat (глобальные настройки осознанно не трогаются), а убирает
   его повторное чтение из горячего пути.

## 6. Принятые решения и отклонённые варианты

1. **Два оператора вместо одного** — единственный способ убрать
   lease-скан со стороны UPDATE: guard-предикаты дают планировщику
   индексный путь, `AS MATERIALIZED` и перестановки join его не меняют
   (замер §2.1). Транзакция возвращает атомарность.
2. **Курсор дренажа** вместо «терпеть префикс»: прецедент T-185/T-193;
   в шторме экономия кратно больше (14 пачек × префикс → 1 × префикс).
3. Отклонён **частичный индекс с `status`** — HOT-инвариант `domains`
   (класс T-104/T-175).
4. Отклонены **per-table настройки автоваукуума** `domains_default` —
   правило проекта: настройки только глобальным конфигом, партиции
   создаются динамически (docs/db.md).
5. Отклонено **повышение `autovacuum_vacuum_scale_factor` глобально** —
   форсирование вакуума всех таблиц ради одного индекса меняет нагрузку
   всего кластера (I/O-голод и так фактор всех находок окна).

## 7. Тестирование и приёмка

1. Юнит: SQL-контракты (тексты SELECT с курсором и UPDATE с unnest+guard,
   литералы model.*); `LeaseOnce` на фейке — пара операторов в одной
   транзакции, счёт по RETURNING, пустая пачка не двигает курсор,
   guard отсеял записанный воркером результат; `LeaseWatch` — курсор
   живёт между пачками/дренажами, рестарт сбрасывает (нулевой курсор).
2. Интеграция (`test/integration`): зрелая аренда возвращается,
   повторный проход — 0; запись результата между выборкой и переводом —
   не возвращается (гонка); курсор не пропускает состарившиеся позже
   записи (малый lease, два прохода с паузой); дельты `zones` сходятся с
   T-178-реконсиляцией.
3. Приёмка: записи возврата lease в журнале медленных (T-177) —
   единичные (первый проход после старта на большом префиксе);
   штормовой дренаж десятков тысяч аренд — единицы минут вместо
   десятков; `make test` + `make test-integration` зелёные.
