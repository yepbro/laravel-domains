# Техническое задание: доля temp_error на суточных счётчиках — dnsShareSQL без скана окна

Версия: 1.0 (по итогам разбора лога медленных запросов боя 2026-10-24 —
запрос №6 журнала; лог: `log_min_duration_statement = 3000`, T-177).
Продолжение [`TZ_slow_done_today.md`](./TZ_slow_done_today.md) (T-179):
та же пара «календарное окно суток × свежие строки», тот же класс
решения — суточные счётчики в `crawler_counters`.

---

## 1. Сегодняшнее состояние и источник

Запрос `dnsShareSQL` (`internal/monitor/alerts.go:336`):

```sql
SELECT count(*) FILTER (WHERE status = $1), count(*)
FROM domains WHERE last_checked_at >= current_date
```

($1 = 5, `model.StatusTempError`.) Вызывается `evalDNS` — алерт T-080
«доля temp_error среди проверок текущих суток» (гистерезис
включение/удержание, минимум образцов `AlertDNSMinSamples`), цикл
`AlertsLoop` monitor каждые 5 мин.

Статистика боя (журнал 24.10 09:43–12:19 UTC): 33 срабатывания порога
3 с (каждая оценка алерта), медиана **27,7 с**, min 14,1 с, max 110,7 с.

## 2. Диагноз (EXPLAIN ANALYZE на боевой БД, 24.10)

- План правильный: Parallel Index Scan
  `domains_default_last_checked_at_idx`, `Index Cond:
  last_checked_at >= CURRENT_DATE` — индекс T-171 отрабатывает; окно —
  те же 815 тыс. строк, что у `done_today` (к вечеру ≈1,5–2 млн).
- Но это **Index Scan, а не Index Only**: колонка `status` в индексе
  отсутствует → обязательное посещение heap каждой строки окна.
  308 тыс. буферов (≈2,4 ГБ), из них **170 тыс. чтений** (1,3 ГБ
  I/O, 12,2 с).
- Пул monitor — `max_parallel_workers_per_gather = 0` (хук
  `NoParallelGather`, T-171): сериально ≈14–15 с (совпадает с min
  лога 14,1 с; медиана/max — под конкурирующей нагрузкой).
- Посыл комментария `dnsShareSQL` «страницы сегодняшних проверок самые
  горячие, в shared_buffers» не выдержал масштаба: окно суток —
  1–2 ГБ разбросанных heap-страниц против shared_buffers 2 ГБ в смеси
  с конвейером; каждая оценка алерта — перевыгрузка гигабайта с NVMe.

## 3. Целевое состояние

1. `evalDNS` читает **два точечных значения** `crawler_counters` —
   числитель и знаменатель доли; скан окна суток из цикла алертов
   исчезает.
2. Числитель — новая строка `temp_error:YYYY-MM-DD`; знаменатель —
   строка `checks:YYYY-MM-DD` (T-179). Инкременты — в тех же
   транзакциях записи результата (`httpworker/record.go`), авторитет —
   реконсиляция T-179 (проход monitor).
3. Семантика доли: **события записей результата** за сутки вместо
   «доменов в статусе temp_error сейчас» (расхождение — §5.1 ТЗ
   T-179: ретрай, закрывший ошибку, остаётся в истории событий) — для
   алерта темпа честнее; пороги/гистерезис не меняются.

## 4. Строки счётчиков

| `name` | `value` | кто пишет |
|---|---|---|
| `checks:YYYY-MM-DD` | записи результатов за сутки | T-179 (уже спроектирован) |
| `temp_error:YYYY-MM-DD` | из них со статусом temp_error | эта задача |

Сутки/таймзона/ротация/отсутствие строки до первой записи — идентично
ТЗ T-179 §4 (та же таблица `crawler_counters` T-175, миграции нет).

## 5. Инкременты

`httpworker/record.go`, та же транзакция и тот же оператор-паттерн,
что у T-179 §5 (`INSERT … ON CONFLICT (name) DO UPDATE SET value =
crawler_counters.value + EXCLUDED.value`), вторая строка:

```sql
INSERT INTO crawler_counters (name, value)
VALUES ('temp_error:' || to_char(current_date, 'YYYY-MM-DD'), $1)
ON CONFLICT (name) DO UPDATE
    SET value = crawler_counters.value + EXCLUDED.value
```

где `$1` — число записей батча с вердиктом temp_error (Go-счёт по
данным батча до записи). Дубль-доставка даёт лишнее событие в числителе
и знаменателе одновременно — доля устойчива, абсолюты чинит
реконсиляция (T-179 §5.1).

## 6. Реконсиляция

Проход T-179 (до T-178 — временный часовой цикл monitor; после —
FILTER-позиции совмещённого прохода ТЗИ) пересчитывает **обе** строки
одним агрегатом по уже сканируемым строкам:

```sql
SELECT count(*), count(*) FILTER (WHERE status = 5)
FROM domains WHERE last_checked_at >= current_date
```

(до перезаписи читаются прежние значения, дрейф обеих строк — метрика
T-179 §8). До первого прохода после полуночи строки нет — честный ноль.

## 7. Читатель (алерт)

`evalDNS`: вместо `dnsShareSQL` — точечное чтение двух строк
(`SELECT name, value FROM crawler_counters WHERE name IN ($1, $2)`,
сутки вычисляет БД):

- нет строки `checks:` (или 0) и `total < AlertDNSMinSamples` →
  `NotMeasured` (прежняя семантика минимума образцов);
- `share = temp/total`, гистерезис `AlertDNSFireShare`/
  `AlertDNSRecoverShare` и формат detail — без изменений.

`dnsShareSQL` удаляется (вместе с юнит-фикстурой alertShare);
частота цикла алертов не меняется.

## 8. Тестирование и приёмка

1. Юнит: SQL-контракты инкремента §5 и чтения §7; тексты без
   `dnsShareSQL`; evalDNS на фейках: NotMeasured при пустом счётчике,
   firing/удержание по порогам, семантика detail сохранена.
2. Интеграция: эпизод с temp_error-результатами — числитель/знаменатель
   растут; повторный эпизод без temp_error — числитель не растёт;
   реконсиляция сходится к живому агрегату.
3. Приёмка: в журнале боевого сервера записи `dnsShareSQL` исчезают;
   тестовое срабатывание алерта (порог T-162) приходит как раньше;
   `make test` + `make test-integration` зелёные.

## 9. Принятые решения и отклонённые варианты

1. **Счётчики суток, продолжение T-179** — общий класс с `done_today`:
   календарное окно по свежим строкам структурно дорого (heap-визиты
   строки окна — `status` в индексе быть не может), счётчик разрывает
   конфликт; знаменатель уже спроектирован.
2. Отклонён **индекс с `status`** (ключ или предикат — включая
   частичный `WHERE status = 5`): статус меняется на каждом результате
   (десятки млн/сутки) — попадание в индекс ломает HOT-инвариант
   (класс `flags`/T-175, docs/schema.md).
3. Отклонено **«оценивать реже»** (5 → 15–30 мин): смягчает частоту,
   каждая оценка остаётся 15–110 с I/O; не решает.
4. Отклонён **parallel gather пулу monitor**: откат T-171 (агрегаты
   отбирают ядра у конвейера); точечные чтения дешевле.
5. Семантика «события, а не состояние» принята сознательно (§3):
   доля устойчива к дублям доставки, ретраи остаются в знаменателе
   истории; живой агрегат возвращается реконсиляцией.
