Дополнительные ТЗ этапов: [`TZ_dashboard.md`](./TZ_dashboard.md) —

## Как работать с файлом

- Задачи пронумерованы `T-001…T-206` и упорядочены по выполнению (сверху вниз).
- Статус задачи — метка в квадратных скобках, меняется редактированием:
  - `[новая]` — задача не начата;
  - `[в работе]` — задача выполняется;
  - `[сделана]` — задача завершена; по завершении волны строка задачи
    переносится в архив [`tasks_done.md`](./tasks_done.md) — здесь остаются
    только незавершённые задачи.
- Пример: `- **T-001** [в работе] — …`
- Внутри этапа задачи по возможности выполняются параллельно; между этапами — последовательно.
- Отступление от порядка этапов ТЗ §12: **хранилище контента** (этап 4, архив)
  реализовано до HTTP-этапа, т.к. `http-worker` сохраняет контент через
  `ContentStore` (ТЗ §5.5, §5.7).

## Этап 30. Зоны только верхнего уровня (TLD-only) (2026-10-26)

Источник: 2LD-зоны по списку Mozilla PSL (`5g.in`, `co.in`, … — реестры
добавляют их сами, PSL вшит в golang.org/x/net) дробят справочник
`zones`, статистику и партиции, а полный дамп `.in` невозможно принять
через `incoming/in/` — каждая строка под 2LD-суффиксом отвергается
`wrong_zone` (`domainLabel`, internal/ingest/validate.go). Решение
(обсуждение 26.10): зона — последняя метка имени (TLD), label — всё
остальное (составной label — норма); каталоги `incoming/<tld>/`;
многоуровневые каталоги — только allowlist `ingest.allowed_zone_paths`
(тестовые зоны testbed); данные существующих 2LD-зон сворачиваются
командой `crawlerctl zones collapse` в окне обслуживания. Отменяет
семантику ТЗ 5.2 п. 5 (публичный суффикс по PSL) — управляет дополнение
[`TZ_tld_only_zones.md`](./TZ_tld_only_zones.md).

- **T-194** [сделана] — P1, `internal/idn`: зона — последняя метка имени
  (TLD-only): `Normalize` режет ASCII-имя по последней точке (зона =
  TLD, label = префикс), вызов и импорт
  `golang.org/x/net/publicsuffix` удалить; `ErrNumericZone` (последняя
  метка из цифр — даты выгрузок, IPv4-литералы) и `ErrNoLabel` (голый
  TLD) сохранить; докстринги пакета/`Result` — без отсылок к PSL.
  Сознательные смены контракта: голые суффиксы (`github.io`, `co.in`)
  становятся валидными доменами (мусор без фильтра — ТЗ §12.6),
  `example.co.uk` → зона `uk`, label `example.co`. Критерий: корпус
  T-010 и юнит-тесты держат таблицу §4.2 ТЗ целиком; `make test`/
  `make lint` зелёные. ТЗ:
  [`TZ_tld_only_zones.md`](./TZ_tld_only_zones.md).

- **T-195** [сделана] — P1, `internal/ingest` + `internal/config`:
  каталоги зон только TLD + allowlist: `incoming/<tld>/add|delete/` —
  рабочий путь (полный дамп `.in` одним файлом); многоуровневый каталог
  — ошибка уровня файла (`failed/`, T-021), кроме нового
  `ingest.allowed_zone_paths` (дефолт пусто; валидация `NormalizeZone`
  + минимум одна точка, дедуп при загрузке); `domainLabel` структурно
  не меняется; тексты валидации `zone_weights`/
  `requeue_deprioritized_zones` — имена TLD (убрать «составные —
  co.uk»). Критерий: `example.5g.in` в `incoming/in/` принимается
  (label `example.5g`, бывший `wrong_zone`); `crawl.test` из allowlist
  работает, без allowlist — `failed/`; тесты ingest/config зелёные. ТЗ:
  [`TZ_tld_only_zones.md`](./TZ_tld_only_zones.md).

- **T-196** [новая] — P1, `crawlerctl zones collapse` — перенос данных
  2LD→TLD: dry-run по умолчанию, `--apply`/`--skip-reconcile`/
  `--force`; по каждой зоне (§7 ТЗ): ensure TLD-зоны и партиций
  (`create_zone_partitions`), батчи `UPDATE` с row movement (domains с
  доклейкой `label || '.' || префикс`, subdomain_results,
  laravel_domains, laravel_findings, laravel_history), `ingest_files`
  перепривязать к TLD с разруливанием дедупа `(zone_id, action,
  sha256)`, дроп партиций 2LD, `DELETE zones`, реконсиляция счётчиков;
  идемпотентно и возобновляемо; allowlist-зоны не сворачиваются;
  предусловие — нет `check_state = 1`. Критерий: интеграционный тест на
  сидированной схеме (перенос всех шести таблиц, конфликт дедупа, no-op
  повтором, продолжение после сбоя на середине, пост-проверки §7.5);
  `make test-integration` зелёный. ТЗ:
  [`TZ_tld_only_zones.md`](./TZ_tld_only_zones.md).

- **T-197** [новая] — P2, документация и testbed волны TLD-only:
  docs/schema.md (§«Обработка имени» — зона TLD), docs/incoming-files.md
  (каталоги `incoming/<tld>/`, allowlist), docs/configuration.md и
  config.example.yaml (`allowed_zone_paths`, комментарии весов — TLD),
  docs/runbooks.md (окно сворачивания зон §8 ТЗ), конфиг testbed —
  `allowed_zone_paths: [crawl.test]`. Критерий: ревью документации;
  сценарии testbed (ingest→check в зоне `crawl.test`) проходят. ТЗ:
  [`TZ_tld_only_zones.md`](./TZ_tld_only_zones.md).

- **T-198** [новая] — P1, окно обслуживания: сворачивание 2LD-зон
  продуктивной БД по runbook §8 ТЗ: бэкап → стоп источников (ingest,
  scheduler) → дрейн `q:dns`/`q:http`/`q:analyze`/`q:render` → стоп
  воркеров → `crawlerctl zones collapse --apply` → пост-проверки §7.5 и
  спот-чек `domain_info('example.5g.in')` → зона `in` → `VACUUM
  (ANALYZE)` доменных таблиц → выкат сборки с T-194…T-197 → старт и
  контроль реконсиляции. Откат — только восстановление бэкапа (перенос
  необратим, ТЗ §12.5). Критерий: пост-проверки зелёные; справочник
  `zones` без многоуровневых зон; повторная доставка дампа `.in` в
  `incoming/in/` принимается одним файлом. ТЗ:
  [`TZ_tld_only_zones.md`](./TZ_tld_only_zones.md).

## Этап 31. Медленные запросы PostgreSQL — окно после деплоя 3bffc62 (2026-10-26)

Источник: журнал медленных запросов боевого сервера (T-177,
`log_min_duration_statement = 3000`), окно строго после последнего
деплоя `3bffc62` — 2026-10-25 18:16 → 10-26 03:05 UTC (8,8 ч; волна
T-191/T-192/T-193 деплоена именно в нём): 1053 оператора, 25 видов,
≈4,9 ч суммарного времени БД; локальная копия
`tmp/pg_slow_after_3bffc62.log` (вне git). Контекст: CPU-голод
(PSI some avg300 ≈ 80 %), полуночный шторм 00:00–02:30 UTC (суточная
перепроверка + созревание когорты temp_error 24.10 — дренаж 21:20 UTC
перевёл 104 297 доменов). Итоги волны T-191…T-193 подтверждены:
retrySelect 150 → 10 событий, reanalyze-тик 18–25 → 5–12 с,
renderRequeue 137 → 1, конвой блокировок не повторился (459 ожиданий,
все ≤1,1 с — T-192 работает). Этап закрывает остатки: контрольные
точки этапа 27 (throughputSQL, enqueue/dispatch — «замер после
T-191») сработали, новые статьи — lease-возврат и применение NRD-фида.

- **T-199** [сделана] — P2, реконсиляция зон реже —
  `monitor.zone_stats_interval` 5 → 30 мин: решение оператора по ТЗИ
  §7.1 (разредить после приработки волны по замеру дрейфа); замер
  окна — реконсиляция единственный полный проход `domains`, 48 %
  медленного времени БД (100 событий, med 39 с, max 501 с при проходе
  раз в 5 мин). Дефолт кода (`DefaultZoneStatsInterval`) + комментарий,
  `config.example.yaml`, docs (configuration.md, deploy.md §4.5 —
  инструкция развёртывания, упоминания operations.md/disks.md/
  runbooks.md), тест дефолта. Прод — операционно 26.10 (журнал работ
  operations.md §5): config.yaml + restart monitor. Следствия
  зафиксировать в docs: цикл алертов теперь 30 мин (коридор ТЗ 5.9),
  порог остановки прогресса `AlertStallFactor × интервал` растёт
  25 мин → 2,5 ч. Критерий: записи реконсиляции в журнале медленных
  ≤ 2/ч; дрейф счётчиков в стационаре 0 (метрика ТЗИ §11).
- **T-200** [сделана] — P1, возврат истёкших lease — запрос №3 окна
  (75 событий, med 8,1 с, max 111 с, 7 % времени). Диагноз: план
  UPDATE-стороны сканирует весь истёкший диапазон lease-индекса без
  LIMIT (Nested Loop, двойное чтение диапазона за пачку; AS MATERIALIZED
  план не меняет) + мёртвый префикс `domains_lease_idx` между вакуумами
  (273 МБ индекса при ~1 тыс. живых записей; проход с нулём строк —
  10 тыс. чтений; автовакуум 0,02 × 42,3 млн ≈ 846 тыс. — префикс
  копится до ~млн записей). Решение: SELECT пачки + UPDATE … FROM
  unnest PK-пробами с guard-перепроверками в одной транзакции + курсор
  дренажа (queued_at, zone_id, id) в состоянии LeaseWatch (стиль
  T-185/T-193). ТЗ: [`TZ_slow_lease_return.md`](./TZ_slow_lease_return.md).
- **T-201** [сделана] — P2, retention — остаточная медленность время-формы
  T-185 (SELECT 38 событий med 13,8 с / UPDATE-очистка 37 med 12,1 с).
  Диагноз (EXPLAIN ANALYZE): окно старения 84 тыс. строк/ч (оценка ТЗ
  T-185 была 15 тыс.), ~70 тыс. heap-визитов + 22 тыс. PK-проб domains
  на пачку — необходимый минимум формы при HOT-инварианте; главный
  множитель — I/O-голод; проход собирает 2 параллельных воркера на
  голодном CPU того же сервиса. Решение: `db.NoParallelGather` пулу
  http-worker (продление T-171 на четвёртый сервис) + контрольный
  замер после аппаратного расширения рендера; SQL/индексы не меняются.
  ТЗ: [`TZ_slow_retention_residual.md`](./TZ_slow_retention_residual.md).
- **T-202** [сделана] — P1, retry temp_error — кейс «счётчик большой,
  зрелых мало» (10 событий med 51 с, max 239 с после фикса T-191):
  guard по `status_temp_error` (543 тыс.) не отличает зрелых кандидатов
  (`check_state = 2 AND last_checked_at < now − 24 ч`) от незрелых —
  при малой плотности зрелых seq-скан без раннего останова вычитывает
  все 42,3 млн строк ежечасным тиком. Решение (семья ТЗИ T-178 /
  T-179/T-182): счётчик зрелых — часовые корзины («зреет через 24 ч»:
  инкремент корзины now+24ч при записи temp_error-результата,
  декремент при ретрае), guard пускает тяжёлый SELECT только при
  ненулевых зрелых корзинах; реконсиляция — FILTER-позицией прохода
  реконсиляции. Критерий: записи retrySelectSQL в журнале — только в
  часы живого дренажа зрелых (пачки полные, ранний останов).
- **T-203** [сделана] — P1, throughputSQL — контрольная точка этапа 27
  сработала: после T-191 медиана 6,0 с > 3 с (108 событий; часовые
  подзапросы `results_hour`/`rendered_hour` — index-only по свежим
  страницам деградирует heap-fetch'ами). Решение предписано там же:
  часовые корзины `crawler_counters` — расширение ТЗИ T-179/T-182
  (инкремент в транзакции записи результата `httpworker/record.go`,
  читатель — точечные строки, реконсиляция FILTER-позицией прохода
  реконсиляции). Критерий: throughputSQL уходит из журнала медленных;
  значения корзин сходятся с живым count (реконсиляция).
- **T-204** [сделана] — P2, reanalyze-тик — время-форма T-193 дороже
  оценки ТЗ (5–12 с стабильно, 86–94 с в полуночном шторме против
  0,3–1 с): bitmap+heap прохода часа (84 тыс. строк) + JOIN
  domains/zones по каждой строке окна — критерий приёмки T-193
  («записи тика исчезают из журнала») не достигнут. Кандидаты: guard
  по счётчику неанализированных хвостов (инкремент при записи
  результата без анализа / декремент при публикации анализа) либо
  облегчение JOIN (имя зоны домножается только непустой пачке);
  выбрать по замеру EXPLAIN. Критерий: тик < 3 с в стационаре.
- **T-205** [сделана] — P1, применение NRD-фида — один оператор
  INSERT…SELECT ~470 тыс. строк (63 с 24.10, 200 с 25.10; прошлые
  окна разбора 20:33 UTC не покрывали — находка новая). Оба варианта:
  (а) чанкинг `apply_add` — пачки по `ingest.batch_size` (50 тыс.)
  курсором по PK staging `(batch_id, line_no)` в одной транзакции,
  дельты `zones` — одним итоговым оператором по накопленным счётчикам
  пачек (атомарность и идемпотентность T-018 сохраняются);
  (б) cron 20:33 → 05:33 UTC — вне вечернего голода CPU и полуночного
  шторма перепроверки (день источника закрыт >9 ч — контракт
  deploy/nrd/README соблюдён); прод-часть операционно 26.10 (журнал
  работ), репо — `deploy/nrd/crawler-nrd.cron` + README + deploy.md
  §4.9. Критерий: применение дня — пачки <3 с каждая в журнале
  медленных, итоговый оператор зон — точечный; следующий NRD-день
  применяется без записей >3 с.
- **T-206** [сделана] — P2, отвязать цикл алертов от периода реконсиляции —
  собственный интервал с прежней частотой (решение оператора 26.10).
  Сегодня цикл алертов monitor следует `monitor.zone_stats_interval`
  (T-161, «одна пара циклов»), который T-199 разредил до 30 мин — окна
  детекции, заданные в проходах, удлинились: `queue_dead` 15 → 90 мин,
  `memory_high`/`render_debt` 10 → 60 мин, порог остановки прогресса
  `AlertStallFactor × интервал` 25 мин → 2,5 ч; выборка PSI (окно
  30 мин) стала равна периоду прохода. Решение: отдельное поле
  `monitor.alerts_interval` (дефолт 5 мин — прежняя частота, коридор
  по образцу zone_stats_interval), цикл алертов тикает им,
  реконсиляция остаётся 30 мин; обновить комментарии/docs (deploy.md
  §4.5 — следствие из T-199 снимается, services.md — окна алертов
  обратно в прежних минутах, configuration.md — новое поле).
  Критерий: оценка алертов каждые 5 мин при 30-минутной
  реконсиляции; окна детекции возвращены к прежним значениям.
  Не входит в текущую волну этапа 31 (её закрывают T-199/T-205):
  подхватывается следующим циклом задач по общим правилам AGENT.md.
