# Декомпозиция ТЗ «Сервис массовой проверки доменов и поиска сайтов на Laravel»

Источник: [`TZ_domain_crawler.md`](./TZ_domain_crawler.md) (версия 1.1).

## Как работать с файлом

- Задачи пронумерованы `T-001…T-095` и упорядочены по выполнению (сверху вниз).
- Статус задачи — метка в квадратных скобках, меняется редактированием:
  - `[новая]` — задача не начата;
  - `[в работе]` — задача выполняется;
  - `[сделана]` — задача завершена.
- Пример: `- **T-001** [в работе] — …`
- Внутри этапа задачи по возможности выполняются параллельно; между этапами — последовательно.
- Отступление от порядка этапов ТЗ §12: **хранилище контента** (этап 4 ниже) реализуется до HTTP-этапа, т.к. `http-worker` сохраняет контент через `ContentStore` (ТЗ §5.5, §5.7).

## Этап 1. Ingest — приём файлов (ТЗ §5.1)

- **T-013** [сделана] — Пакет `internal/watch`: наблюдение `incoming/` — fsnotify (create/write; рекурсивно: watch новых каталогов `<зона>/add|delete` добавляется на лету) + периодический полный обход как страховка (новая опция `ingest.scan_interval` 10ms..1h, по умолчанию 30 с, env `CRAWLER_INGEST_SCAN_INTERVAL`, стиль T-006); готовность — стабильность размера и mtime `stable_seconds` (10 с из §5.10), событие записи начинает окно заново даже при неизменной сигнатуре (грубый mtime ФС); выдаются только регулярные `*.txt` — `*.tmp`/`*.part`, скрытые файлы/каталоги и архив `processed/`/`failed/` верхнего уровня игнорируются (переименование в `*.txt` = событие создания готового имени); канал готовых файлов с буфером — backpressure блокировкой без потерь, повторная выдача исключена in-memory по пути+размеру+mtime (новый файл по тому же пути выдаётся снова; постоянная идемпотентность — ingest_files, T-021); отсутствующий каталог создаётся, исчезнувший восстанавливается обходом; логика стабильности — отдельный трекер с заглушаемым временем; тесты: трекер на фейковых часах + быстрый наблюдатель на реальном fsnotify (рост файла, tmp/part/скрытые, страховочный опрос, новые каталоги, backpressure, отмена, удаление до стабильности); `cmd/ingest` подключён через `OnRun` — логирует готовые файлы (точка интеграции T-014+). ТЗ: §5.1, §5.10.
- **T-014** [сделана] — Пакет `internal/ingest`: `ParsePath` — разбор пути готового файла относительно incoming `<зона>/add|delete/*.txt` → `{Zone (punycode), ZoneUnicode, Action, Path}`: ровно три компонента (лишняя вложенность/нет add/delete/абсолютный путь/выход за incoming — ошибка), каталог операции строго `add|delete` в нижнем регистре (структура ТЗ 5.1 фиксирована, регистр ФС Linux точен), имя `*.txt` без учёта регистра — как фильтр готовности watch, чтобы приём разбирал всё выданное; зона — `idn.NormalizeZone` (составные `co.uk` допустимы, PSL не требуется), unicode- и punycode-каталог дают одну зону без дублей (§11.4 п. 1); ошибки типизированы `*ingest.PathError` (structure/not_txt/zone, зона — обёртка `*idn.Error` с классом для failed-отчёта). Справочник зон: маленький интерфейс `ZoneStore` (ZoneByName/CreateZone, дубль имени — не ошибка) + `EnsureZone` — найти по punycode-имени, иначе создать автоматически при первом файле: `is_active = true` (в SQL — явно), `name` — punycode, `name_unicode` — unicode-форма для отображения, для ASCII-зон NULL (§5.2 п. 7); SQL-реализация `SQLZoneStore` поверх `internal/db` (`INSERT … ON CONFLICT (name) DO NOTHING RETURNING …`, без строки — повторный SELECT: конкурентные создания одной зоны сходятся в одну строку), юнит-тесты: EnsureZone/ParsePath на фейках, SQL — точный текст и параметры на фейковом pgx-пуле без БД; сборка конвейера ingest (watch→ParsePath→EnsureZone→парсер) — поздняя задача. ТЗ: §5.1, §5.2 (пп. 6–7), §11.4 (п. 1).
- **T-015** [сделана] — Потоковый построчный парсер файлов (новый пакет `internal/ingest`, parser.go): `Parse(io.Reader, Options{OnLine, OnReject}) → (Stats, error)` — Line с номером физической строки (нужен rejected-логу T-016 и отчёту T-021) и счётчики Total/Skipped/Rejected/Data (инвариант Total = Skipped+Rejected+Data); концы строк `\n`/`\r`/`\r\n` (пара CRLF не делится, CR на краю окна дочитывается), BOM — снимается только в начале файла (в середине остаётся в данных — его убирает маппинг UTS-46 в idn.Normalize), пустые строки и комментарии по первому значимому символу `#`, крайние пробелы сняты (unicode.IsSpace — тот же предикат, что idn.cleanup; внутренние остаются — их снимает нормализация, ТЗ 5.2 п. 1); невалидный UTF-8 и строка длиннее `MaxLineLen` = 1024 байт (выведено из ТЗ 5.2 п. 4: 253 октета punycode ≤ ~1012 байт UTF-8) — построчные отклонения (Reason `invalid_utf8`/`line_len`, сырой текст ≤255 байт), разбор продолжается, файл не считается ошибочным; память константна (ТЗ 3.5): окно чтения 64 КиБ + накопитель одной строки ≤ MaxLineLen, длинный мусор не буферизуется; собственный сканер вместо bufio.Scanner (у того ErrTooLong невосстановим); тесты по §11.1 (пустой, комментарии, CRLF, BOM, пустые, длинная, битый UTF-8, без завершающего перевода) + white-box границы окна (окна 3–64 байт) + short reads + тест памяти на генераторе io.Reader ~40 МиБ (живая куча за 24 МиБ не выходит, счётчики сходятся). ТЗ: §5.1, §3.5, §11.1.
- **T-016** [сделана] — Валидация строк: строка должна быть полным именем домена из зоны, указанной в пути; отклонение невалидных имён и слишком длинных; запись в лог `rejected` с причиной; порог доли ошибок на файл из конфига. - **T-025** [сделана] — Надёжность очереди (новые `internal/queue/reliab.go` + `reliab_test.go`; точечные правки redisq.go/redisq_test.go/queue.go — применение дефолта MAXLEN, док-комментарии, обосновано ниже). MAXLEN: T-024 уже применял `RedisOptions.MaxLen` в единственном `RedisQueue.Publish` (через него идут все XADD) — пробела не было; T-025 добавил политику дефолтов `DefaultStreamMaxLen` (0 в опциях → предел стрима, явное значение перекрывает все стримы; «не обрезать» не предусмотрен — ТЗ 4.2 требует MAXLEN на каждом стриме, а источник истины PostgreSQL: усечённая необработанной задача восстановима планировщиком по lease, ТЗ 3.4/5.3): q:dns 10 000 (записи — пачки до scheduler.batch_size=5000 доменов ≈ до ~250 КБ; глубина реалистично десятки, 10 000 пачек = 50 млн доменов «в полёте», память ограничена ГБ), q:http/q:render/q:analyze 1 000 000 (штучные ~100–200 Б ≈ 150–200 МБ на стрим, на порядок выше порога backpressure 100 000), q:dead 100 000 (поток редок, ручному разбору нужна история); усечение MAXLEN ~ режет прежде всего подтверждённую историю — без него стримы растут неограниченно (350 млн доменов × несколько стримов). Порядок XACK-после-БД оформлен хелпером `Processing(ctx, q, group, delivery, process)`: Ack недостижим раньше безошибочного завершения process; ошибка обработки — без XACK (запись вернётся повторной доставкой), ошибка XACK — возврат (результат уже в БД, повторная обработка идемпотентна, ТЗ 3.4). Возврат зависших — `Reliab` (NewReliab(rdb, q, ReliabOptions)) `.Claim(ctx, stream, group, consumer, minIdle, n)` через XAUTOCLAIM: ТЗ 4.2 называет XAUTOCLAIM прямо, go-redis v9.23 поддерживает полностью; одна атомарная команда фильтрует PEL по простою, перезакрепляет и вычищает из PEL усечённые MAXLEN записи (приходят с пустым телом — пропускаются), тогда как XPENDING+XCLAIM — два раунда с окном гонки и XCLAIM без idle-фильтра. Счётчик попыток — deliveries-счётчик PEL самой записи (поле RetryCount ответа XPENDING EXTENDED, читается после клейма диапазоном id..id ровно по вернувшимся записям — XAUTOCLAIM счётчик не возвращает; чтение без побочных эффектов, гонки с другими восстановителями безопасны): тело записи стрима immutable (счётчик в теле = перепубликации и дубли записей), отдельные ключи-счётчики не нужны, счётчик переживает рестарты воркеров; запись = задача (task_id в теле) → счётчик per task_id; граница MaxAttempts (дефолт `DefaultMaxAttempts`=3, ТЗ 4.2): counter == MaxAttempts — ещё в работу (итого до 3 обработок: первая доставка + клеймы), counter > MaxAttempts — Claim сам переводит в q:dead: публикация Dead (task_id из тела, payload без изменений, reason — исчерпание лимита: воркеры ошибки обработки очереди не сообщают) до XACK исходной записи (сбой XACK оставит запись в pending и даст дубль Dead на следующем проходе — дубль предпочтительнее потери), после XACK сообщение покидает pending; записи, покинувшие PEL между командами (подтверждены), пропускаются; запись вне форматов пакета (без task_id) — ошибка для оператора, не молчаливый перевод; `DefaultClaimMinIdle`=5m (запас над таймаутами этапов ТЗ 5.5/5.6), minIdle 0 в Claim → опция. Конфиг (стиль T-006): redis-секция `maxlen` (0 — дефолты по стримам, иначе 1000..100000000; env CRAWLER_REDIS_MAXLEN), `max_attempts` (3, 1..100 — минимум 1: ноль доставок означал бы q:dead до первой обработки; env CRAWLER_REDIS_MAX_ATTEMPTS), `claim_min_idle` (5m, >0; env CRAWLER_REDIS_CLAIM_MIN_IDLE) + config.example.yaml + docs/configuration.md. Юнит-тесты без живого Redis (фабрик New*Result у XAUTOCLAIM/XPENDING go-redis не имеет — значения задаются SetVal/SetErr заготовленных команд): аргументы XADD MAXLEN ~ по всем стримам (дефолты и явный предел), XAUTOCLAIM (стрим/группа/потребитель/MINIDLE/Start 0-0/Count) и XPENDING (диапазон id..id, Count 1), счётчик на границе (доставки 1/3 — в работу, 4 — q:dead), формат Dead + порядок Dead→XACK исходного стрима, сбой публикации Dead — без XACK, сбой XACK — Dead опубликован, Processing (ack только после успешной «записи в БД», без ack при ошибке обработки, ошибка XACK, nil-обработчик), пропуски усечённых/покинувших PEL, ошибки XAUTOCLAIM/XPENDING, плохие аргументы; идентификаторы reliab/Reliab/Claim/Processing/MaxAttempts без коллизий с T-024/T-026. - **T-065** [новая] — Управление ресурсами Chromium: перезапуск каждые N страниц и при превышении порога памяти; cgroup `MemoryMax` ≈ 2 ГБ; запуск под отдельным непривилегированным пользователем. ТЗ: §5.6, §3.2, §9, §10.1.
- **T-066** [новая] — Переполнение очереди рендера: домены получают флаг `render_pending` и дорабатываются позже; рендер не задерживает остальные этапы. ТЗ: §5.6, §7.
- **T-067** [новая] — Замена сырого HTML на итоговый DOM в хранилище, `rendered = true` в результате, публикация в `q:analyze`. ТЗ: §5.6, §5.7.

## Этап 7. Анализатор Laravel (ТЗ §5.8)

- **T-068** [новая] — Пакет `internal/rules`: загрузка YAML-правил из каталога конфига, структура правила (`id`, target: cookie имя/значение, заголовок, regex по HTML, meta-тег; `weight` 0..1; `ver_min`/`ver_max`), перезагрузка по `SIGHUP`, `rules_version` как хэш набора. ТЗ: §5.8, §5.10.
- **T-069** [новая] — Движок матчинга по целям (cookie, заголовки, HTML, meta) с ограничениями размера/времени на недоверенном контенте; сбор краткого свидетельства (evidence) по каждому срабатыванию. ТЗ: §5.8, §9.
- **T-070** [новая] — Расчёт score по «noisy-OR» (`1 − Π(1 − wᵢ)`); диапазон версий как пересечение `[ver_min, ver_max]` сработавших правил; фиксация конфликта при пустом пересечении. ТЗ: §5.8, §11.1.
- **T-071** [новая] — Запись `laravel_findings`: все срабатывания любого правила независимо от порога, `is_laravel = score ≥ порога` (по умолчанию 0.6); нет срабатываний — строка не пишется. ТЗ: §5.8, §6.1, §13.1.
- **T-072** [новая] — Агрегация на уровне домена в `laravel_domains`: максимальный score, объединённый диапазон версий, `found_on_mask`, `rules_version`. ТЗ: §5.8, §6.1.
- **T-073** [новая] — Набор YAML-правил Laravel по документации и реальным образцам заказчика (`testdata/laravel-samples`): версионные границы (vite/mix, inertia, livewire, cookies и т. д.). ТЗ: §5.8, §13.1, §13.3.
- **T-074** [новая] — Переанализ: фоновая задача находит записи с устаревшим `rules_version` и ставит их в `q:analyze` без повторного скачивания; команда `crawlerctl reanalyze [--zone …]`. ТЗ: §5.8, §11.4 (п. 4).
- **T-075** [новая] — Юнит-тесты движка правил: score, пересечение диапазонов, конфликты; прогон по корпусу образцов Laravel (с ожидаемыми `is_laravel` и диапазонами) и негативным образцам (не-Laravel). ТЗ: §11.1, §11.4 (пп. 4, 11), §13.3.

## Этап 9. Развёртывание и тюнинг ОС (ТЗ §10, §3.2)

- **T-085** [новая] — systemd-юниты на каждый сервис: `MemoryMax` по бюджету памяти (PostgreSQL ≈ 2,5 ГБ; Redis ≤ 0,5 ГБ; Unbound ≈ 0,7 ГБ; Go-сервисы ≈ 1,3 ГБ; Chromium ≈ 2 ГБ), `Restart=on-failure`, отдельные пользователи. ТЗ: §10.1, §3.2, §11.4 (п. 7).
- **T-086** [новая] — Тюнинг PostgreSQL для NVMe и нагрузки: `random_page_cost ≈ 1.1`, `effective_io_concurrency ≥ 200`, настроенный autovacuum для партиций `domains`/`subdomain_results`, `synchronous_commit = off` для данных краулера. ТЗ: §6.3, §6 (принципы).
- **T-087** [новая] — Конфигурация Redis: `maxmemory` ≤ 0,5 ГБ, политика eviction с учётом восстанавливаемости очередей. ТЗ: §3.2, §3.4.
- **T-088** [новая] — Тюнинг ядра для одного IP: диапазон эфемерных портов, `tcp_tw_reuse`, лимиты `nofile`, `nf_conntrack`, размеры UDP-буферов для DNS. ТЗ: §10.2.
- **T-089** [новая] — Диски: отдельные каталоги/тома для PostgreSQL и пак-файлов контента; мониторинг SMART и износа NVMe (TBW). ТЗ: §10.3.
