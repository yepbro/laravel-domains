## Как работать с файлом

- Задачи пронумерованы `T-001…T-143` и упорядочены по выполнению (сверху вниз).
- Статус задачи — метка в квадратных скобках, меняется редактированием:
  - `[новая]` — задача не начата;
  - `[в работе]` — задача выполняется;
  - `[сделана]` — задача завершена; по завершении волны строка задачи
    переносится в архив [`tasks_done.md`](./tasks_done.md) — здесь остаются
    только незавершённые задачи.
- Пример: `- **T-001** [в работе] — …`
- Внутри этапа задачи по возможности выполняются параллельно; между этапами — последовательно.
- Отступление от порядка этапов ТЗ §12: **хранилище контента** (этап 4 ниже) реализуется до HTTP-этапа, т.к. `http-worker` сохраняет контент через `ContentStore` (ТЗ §5.5, §5.7).

## Этап 21. Доработки по итогам повторного замера после T-139 (2026-10-22)

Источник: повторный замер комплектом T-092 после деплоя T-139
(2026-10-22; отчёт — docs/load-measurements.md §11).

- **T-141** [в работе] — Память стримов Redis: XACK не удаляет записи — подтверждённая история копится до MAXLEN политики T-025 (q:http/q:render/q:analyze — 1M записей ≈ 350–700 MiB на стрим; q:dns — 10 000 батчей по ~237 KiB ≈ до 2.4 GiB) и переполняет бюджет Redis 512 MiB: суточный прогон T-093 встал на «OOM command not allowed» ещё **до** деплоя T-139 (публикации render/analyze падали, q:render заклинило на 792; q:dns-сток 1735 батчей = 410 MiB). Гейт планировщика q:dns = min(watermark, MAXLEN/2) = 5 000 батчей ≈ 1.2 GiB — не согласован с бюджетом. Фикс (ТЗ §4.2, дополнение 2026-10-23): освобождение подтверждённого префикса (XDEL после Ack или периодический XTRIM MINID старейшего pending группы — без потери необработанных задач), пересборка оценок MAXLEN и размера q:dns-батчей под бюджет; код-фикс + интеграционный тест на деградацию памяти. Временный костыль на сервере — юнит `t092-trimhist` (XTRIM MINID раз в 2 мин, без потери работы) и runtime-расширение Redis (maxmemory 900 MiB / cgroup 1 GiB вместо 512 MiB / 640 MiB) — снять после влития. ТЗ: §4.2, §3.2.
- **T-142** [сделана] — Рендер — следующее узкое место конвейера после T-139: потолок ≈0.6 стр/с (contexts=3 × 5.1 с/страница, замер T-092 §4) при притоке 5.4% записей HTTP-этапа — на скорости HTTP ≥40 дом/с q:render растёт на ~5–7 зап/с (повторный замер 2026-10-22: 27.9К за ~1.5 ч), гейт watermark 100К остановит публикации http-worker и задушит этап до темпа рендера ≈11 дом/с; цикл рендера сохраняет batched-барьер (в T-139 сознательно не трогался). Опции: скользящее потребление рендера по образцу T-139, подъём contexts (бюджет Chromium ≈2 ГБ, ТЗ 3.2), приёмка по памяти и скорости. ТЗ: §3.3, §5.6.
  **Соответствие ТЗ §5.6** («если очередь рендера переполнена — признак render_pending, рендер не должен задерживать остальные этапы»): текущая блокирующая публикация http-worker в q:render по watermark нарушает это требование — переполнение должно помечать записи `render_pending` без остановки HTTP-этапа. Фикс обязателен в составе задачи.
- **T-143** [сделана] — Память http-worker на задачу и бюджет юнита: замер 2026-10-22 (§11) — ~3.3 MiB anon на слот (тела в полёте ≤ max_body_bytes=2 MiB + буферы): 128 слотов = 380 MiB ≈ MemoryMax 384 MiB (мягко, oom=0), 256 слотов = 834–873 MiB при временном MemoryMax 900 MiB. Критерий §3 (avg<300, p95<350 на 256) при текущей пиковой памяти слота недостижим. Закрепить MemoryMax http-worker 900 MiB в `deploy/systemd/crawler-http-worker.service` (сейчас — set-property на сервере), пересчитать таблицу бюджета `docs/deploy.md` §2 (Go-сервисы суммарно ≈1.05 GiB < ≈1.3 GiB ТЗ 3.2 — проходит), обновить критерий приёмки в load-measurements §3 фактом (47.6 дом/с на 256 — потолок диктует смесь длительностей mean ≈5.3 с, не слоты; следующий резерв — T-142 и хвост total_timeout). Опционально (описать как направление, не реализовывать): снижение пиковой памяти слота стримингом тела. Коммит `chore:`.
