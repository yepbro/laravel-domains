# Декомпозиция ТЗ «Сервис массовой проверки доменов и поиска сайтов на Laravel»

Источник: [`TZ_domain_crawler.md`](./TZ_domain_crawler.md) (версия 1.1).

## Как работать с файлом

- Задачи пронумерованы `T-001…T-095` и упорядочены по выполнению (сверху вниз).
- Статус задачи — метка в квадратных скобках, меняется редактированием:
  - `[новая]` — задача не начата;
  - `[в работе]` — задача выполняется;
  - `[сделана]` — задача завершена.
- Пример: `- **T-001** [в работе] — …`
- Внутри этапа задачи по возможности выполняются параллельно; между этапами — последовательно.
- Отступление от порядка этапов ТЗ §12: **хранилище контента** (этап 4 ниже) реализуется до HTTP-этапа, т.к. `http-worker` сохраняет контент через `ContentStore` (ТЗ §5.5, §5.7).

## Этап 1. Ingest — приём файлов (ТЗ §5.1)

- **T-013** [сделана] — Пакет `internal/watch`: наблюдение `incoming/` — fsnotify (create/write; рекурсивно: watch новых каталогов `<зона>/add|delete` добавляется на лету) + периодический полный обход как страховка (новая опция `ingest.scan_interval` 10ms..1h, по умолчанию 30 с, env `CRAWLER_INGEST_SCAN_INTERVAL`, стиль T-006); готовность — стабильность размера и mtime `stable_seconds` (10 с из §5.10), событие записи начинает окно заново даже при неизменной сигнатуре (грубый mtime ФС); выдаются только регулярные `*.txt` — `*.tmp`/`*.part`, скрытые файлы/каталоги и архив `processed/`/`failed/` верхнего уровня игнорируются (переименование в `*.txt` = событие создания готового имени); канал готовых файлов с буфером — backpressure блокировкой без потерь, повторная выдача исключена in-memory по пути+размеру+mtime (новый файл по тому же пути выдаётся снова; постоянная идемпотентность — ingest_files, T-021); отсутствующий каталог создаётся, исчезнувший восстанавливается обходом; логика стабильности — отдельный трекер с заглушаемым временем; тесты: трекер на фейковых часах + быстрый наблюдатель на реальном fsnotify (рост файла, tmp/part/скрытые, страховочный опрос, новые каталоги, backpressure, отмена, удаление до стабильности); `cmd/ingest` подключён через `OnRun` — логирует готовые файлы (точка интеграции T-014+). ТЗ: §5.1, §5.10.
- **T-014** [сделана] — Пакет `internal/ingest`: `ParsePath` — разбор пути готового файла относительно incoming `<зона>/add|delete/*.txt` → `{Zone (punycode), ZoneUnicode, Action, Path}`: ровно три компонента (лишняя вложенность/нет add/delete/абсолютный путь/выход за incoming — ошибка), каталог операции строго `add|delete` в нижнем регистре (структура ТЗ 5.1 фиксирована, регистр ФС Linux точен), имя `*.txt` без учёта регистра — как фильтр готовности watch, чтобы приём разбирал всё выданное; зона — `idn.NormalizeZone` (составные `co.uk` допустимы, PSL не требуется), unicode- и punycode-каталог дают одну зону без дублей (§11.4 п. 1); ошибки типизированы `*ingest.PathError` (structure/not_txt/zone, зона — обёртка `*idn.Error` с классом для failed-отчёта). Справочник зон: маленький интерфейс `ZoneStore` (ZoneByName/CreateZone, дубль имени — не ошибка) + `EnsureZone` — найти по punycode-имени, иначе создать автоматически при первом файле: `is_active = true` (в SQL — явно), `name` — punycode, `name_unicode` — unicode-форма для отображения, для ASCII-зон NULL (§5.2 п. 7); SQL-реализация `SQLZoneStore` поверх `internal/db` (`INSERT … ON CONFLICT (name) DO NOTHING RETURNING …`, без строки — повторный SELECT: конкурентные создания одной зоны сходятся в одну строку), юнит-тесты: EnsureZone/ParsePath на фейках, SQL — точный текст и параметры на фейковом pgx-пуле без БД; сборка конвейера ingest (watch→ParsePath→EnsureZone→парсер) — поздняя задача. ТЗ: §5.1, §5.2 (пп. 6–7), §11.4 (п. 1).
- **T-015** [сделана] — Потоковый построчный парсер файлов (новый пакет `internal/ingest`, parser.go): `Parse(io.Reader, Options{OnLine, OnReject}) → (Stats, error)` — Line с номером физической строки (нужен rejected-логу T-016 и отчёту T-021) и счётчики Total/Skipped/Rejected/Data (инвариант Total = Skipped+Rejected+Data); концы строк `\n`/`\r`/`\r\n` (пара CRLF не делится, CR на краю окна дочитывается), BOM — снимается только в начале файла (в середине остаётся в данных — его убирает маппинг UTS-46 в idn.Normalize), пустые строки и комментарии по первому значимому символу `#`, крайние пробелы сняты (unicode.IsSpace — тот же предикат, что idn.cleanup; внутренние остаются — их снимает нормализация, ТЗ 5.2 п. 1); невалидный UTF-8 и строка длиннее `MaxLineLen` = 1024 байт (выведено из ТЗ 5.2 п. 4: 253 октета punycode ≤ ~1012 байт UTF-8) — построчные отклонения (Reason `invalid_utf8`/`line_len`, сырой текст ≤255 байт), разбор продолжается, файл не считается ошибочным; память константна (ТЗ 3.5): окно чтения 64 КиБ + накопитель одной строки ≤ MaxLineLen, длинный мусор не буферизуется; собственный сканер вместо bufio.Scanner (у того ErrTooLong невосстановим); тесты по §11.1 (пустой, комментарии, CRLF, BOM, пустые, длинная, битый UTF-8, без завершающего перевода) + white-box границы окна (окна 3–64 байт) + short reads + тест памяти на генераторе io.Reader ~40 МиБ (живая куча за 24 МиБ не выходит, счётчики сходятся). ТЗ: §5.1, §3.5, §11.1.
- **T-016** [сделана] — Валидация строк: строка должна быть полным именем домена из зоны, указанной в пути; отклонение невалидных имён и слишком длинных; запись в лог `rejected` с причиной; порог доли ошибок на файл из конфига. - **T-025** [сделана] — Надёжность очереди (новые `internal/queue/reliab.go` + `reliab_test.go`; точечные правки redisq.go/redisq_test.go/queue.go — применение дефолта MAXLEN, док-комментарии, обосновано ниже). MAXLEN: T-024 уже применял `RedisOptions.MaxLen` в единственном `RedisQueue.Publish` (через него идут все XADD) — пробела не было; T-025 добавил политику дефолтов `DefaultStreamMaxLen` (0 в опциях → предел стрима, явное значение перекрывает все стримы; «не обрезать» не предусмотрен — ТЗ 4.2 требует MAXLEN на каждом стриме, а источник истины PostgreSQL: усечённая необработанной задача восстановима планировщиком по lease, ТЗ 3.4/5.3): q:dns 10 000 (записи — пачки до scheduler.batch_size=5000 доменов ≈ до ~250 КБ; глубина реалистично десятки, 10 000 пачек = 50 млн доменов «в полёте», память ограничена ГБ), q:http/q:render/q:analyze 1 000 000 (штучные ~100–200 Б ≈ 150–200 МБ на стрим, на порядок выше порога backpressure 100 000), q:dead 100 000 (поток редок, ручному разбору нужна история); усечение MAXLEN ~ режет прежде всего подтверждённую историю — без него стримы растут неограниченно (350 млн доменов × несколько стримов). Порядок XACK-после-БД оформлен хелпером `Processing(ctx, q, group, delivery, process)`: Ack недостижим раньше безошибочного завершения process; ошибка обработки — без XACK (запись вернётся повторной доставкой), ошибка XACK — возврат (результат уже в БД, повторная обработка идемпотентна, ТЗ 3.4). Возврат зависших — `Reliab` (NewReliab(rdb, q, ReliabOptions)) `.Claim(ctx, stream, group, consumer, minIdle, n)` через XAUTOCLAIM: ТЗ 4.2 называет XAUTOCLAIM прямо, go-redis v9.23 поддерживает полностью; одна атомарная команда фильтрует PEL по простою, перезакрепляет и вычищает из PEL усечённые MAXLEN записи (приходят с пустым телом — пропускаются), тогда как XPENDING+XCLAIM — два раунда с окном гонки и XCLAIM без idle-фильтра. Счётчик попыток — deliveries-счётчик PEL самой записи (поле RetryCount ответа XPENDING EXTENDED, читается после клейма диапазоном id..id ровно по вернувшимся записям — XAUTOCLAIM счётчик не возвращает; чтение без побочных эффектов, гонки с другими восстановителями безопасны): тело записи стрима immutable (счётчик в теле = перепубликации и дубли записей), отдельные ключи-счётчики не нужны, счётчик переживает рестарты воркеров; запись = задача (task_id в теле) → счётчик per task_id; граница MaxAttempts (дефолт `DefaultMaxAttempts`=3, ТЗ 4.2): counter == MaxAttempts — ещё в работу (итого до 3 обработок: первая доставка + клеймы), counter > MaxAttempts — Claim сам переводит в q:dead: публикация Dead (task_id из тела, payload без изменений, reason — исчерпание лимита: воркеры ошибки обработки очереди не сообщают) до XACK исходной записи (сбой XACK оставит запись в pending и даст дубль Dead на следующем проходе — дубль предпочтительнее потери), после XACK сообщение покидает pending; записи, покинувшие PEL между командами (подтверждены), пропускаются; запись вне форматов пакета (без task_id) — ошибка для оператора, не молчаливый перевод; `DefaultClaimMinIdle`=5m (запас над таймаутами этапов ТЗ 5.5/5.6), minIdle 0 в Claim → опция. Конфиг (стиль T-006): redis-секция `maxlen` (0 — дефолты по стримам, иначе 1000..100000000; env CRAWLER_REDIS_MAXLEN), `max_attempts` (3, 1..100 — минимум 1: ноль доставок означал бы q:dead до первой обработки; env CRAWLER_REDIS_MAX_ATTEMPTS), `claim_min_idle` (5m, >0; env CRAWLER_REDIS_CLAIM_MIN_IDLE) + config.example.yaml + docs/configuration.md. Юнит-тесты без живого Redis (фабрик New*Result у XAUTOCLAIM/XPENDING go-redis не имеет — значения задаются SetVal/SetErr заготовленных команд): аргументы XADD MAXLEN ~ по всем стримам (дефолты и явный предел), XAUTOCLAIM (стрим/группа/потребитель/MINIDLE/Start 0-0/Count) и XPENDING (диапазон id..id, Count 1), счётчик на границе (доставки 1/3 — в работу, 4 — q:dead), формат Dead + порядок Dead→XACK исходного стрима, сбой публикации Dead — без XACK, сбой XACK — Dead опубликован, Processing (ack только после успешной «записи в БД», без ack при ошибке обработки, ошибка XACK, nil-обработчик), пропуски усечённых/покинувших PEL, ошибки XAUTOCLAIM/XPENDING, плохие аргументы; идентификаторы reliab/Reliab/Claim/Processing/MaxAttempts без коллизий с T-024/T-026. - **T-069** [сделана] — Движок матчинга по целям с ограничениями размера/времени на недоверенном контенте и свидетельствами срабатываний (доработка `internal/rules/engine.go`: Evaluate/EvaluateCtx/matchRule; срабатывает первое совпадение, обход детерминирован (cookies в порядке записи, имена заголовков сортируются — обход map в Go случайный, а переанализ обязан быть воспроизводим; у прежнего скелета свидетельства по заголовкам прыгали от запуска к запуску); сигнатура `Set.Evaluate(Page) Result` сохранена (контракт crawlerctl test-rules), добавлен `EvaluateCtx(ctx, page, Limits)` — бюджет времени через context.WithTimeout (поле EvalTimeout), ctx проверяется на входе matchRule, между правилами и между значениями cookie/заголовков, при отмене результат содержит сработавшее до отмены; свидетельство (evidence) — formats для jsonb laravel_findings.signals `[{rule, weight, evidence}]`: «cookie NAME», «cookie NAME=VALUE…», «header Name: value…», совпавший фрагмент regex (html), весь meta-тег (meta); недоверенный контент sanitируется — невалидный UTF-8 → U+FFFD (валидно ещё в памяти, не только после json.Marshal), управляющие C0/DEL → «·» (одна строка, без терминальных escape), обрезка до 64 байт ПО ГРАНИЦЕ РУНЫ (баг скелета: s[:64] рвал многобайтные руны) + «…», имя внутри свидетельства ужимается до 32 байт, чтобы враждебно длинное имя не вытесняло значение из окна; ограничения ТЗ §9 («все парсеры имеют ограничения размера и времени») — защита в глубину поверх лимитов этапов (HTTP-тело/заголовки, content.max_store_bytes): Limits{MaxHTMLBytes 2 MiB — верхняя граница рекомендации ТЗ 1–2 МБ, признаки Laravel в head-части; MaxValueBytes 64 KiB на значение cookie/заголовка — все правила по значениям якорены ^, задокументированный размен: $-якорь на сверхлимитном значении не сработает; MaxPatternBytes 4 KiB; MaxSnippetBytes 64; EvalTimeout 5 с}, нулевые Limits целиком = DefaultLimits (забыть защиту нельзя), HTML/meta обрезаются ДО матчинга; ReDoS-решение: Go regexp = RE2, матчинг линеен, катастрофического бэктрекинга нет — векторы остаются раздутый вход и раздутый паттерн, оба закрыты лимитами размера, таймаут страхует общий бюджет (одиночный матч прервать нельзя, но он линеен по ограниченному входу — отмена срабатывает за время одного матча); паттерны компилируются один раз и кэшируются (sync.Map по строке паттерна + кэш ошибок компиляции) — без кэша каждая страница платила бы компиляцию каждого правила, SIGHUP-reload (T-068) и параллельные горутины безопасны; некомпилируемый/сверхлимитный паттерн и неизвестная цель молча пропускаются (валидация при загрузке за T-068, движок подстраховывается, страница не роняется); meta-теги ищутся скользящим FindIndex без материализации всех совпадений (прежний FindAllString копировал весь HTML в string на каждом правиле) с выходом на первом сработавшем; scoring-хвост (noisyOR/версии/Contains) не тронут — перенос в score.go за T-070; юнит-тесты: все цели × match/regex, свидетельства буквальными строками, детерминизм заголовков (50 прогонов), отмена ctx до начала/между правил (детерминированный countingCtx-двойник)/внутри перебора cookies, границы лимитов (HTML ровно на границе и за ней, $-якорь за лимитом значения, meta за лимитом), паттерн сверх лимита, кривые данные (пустая страница, неизвестная цель, пустое правило), evidence: обрезка/многоточие/граница руны/контроль символов/битый UTF-8, RE2-иммунитет: (a+)+b по 8 MiB «a» завершается быстро + совпадение за 2 MiB-капом не найдено, DefaultLimits-guard (смена защитных значений ломает тест). ТЗ: §5.8, §9.
- **T-070** [сделана] — Расчёт score/версий вынесен из engine.go в новый `internal/rules/score.go` + `score_test.go` (дифф engine.go минимальный: Evaluate собирает сработавшие правила в срез и одной строкой вызывает ScoreRules — матчинг/matchRule не тронуты, T-069). `ScoreRules(matched)` — чистая функция: score «noisy-OR» `1 − Π(1 − wᵢ)` (накопление в порядке правил — бит-в-бит прежний инлайн-расчёт; ScoreFixed по весам сохранён); диапазон версий — пересечение `[ver_min, ver_max]` сработавших правил: нижняя граница = max(ver_min), верхняя = min(ver_max), правило без границы диапазон не сужает, строки границ сохраняются из правил как есть («9.x» не превращается в «9»); версии — числовые компоненты (отсутствующий = 0, «x»/«*» = +∞ «до конца мажорной ветки», числовое а не строковое сравнение «9.19» < «11»); пустое пересечение (`ver_max < ver_min`) — Conflict=true и сброс обеих границ — решение по хранению: неопределённый диапазон = ver_min/ver_max NULL в laravel_findings/laravel_domains, факт конфликта виден по обеим пустым границам; равные границы — не конфликт (диапазон из одной версии), в т. ч. равенство в разной записи «9.19» = «9.19.0»; некорректные строки версий игнорируются. Порог `is_laravel` — `Result.IsLaravel(analyzer.laravel_min_score)`: нестрогое `score ≥ порога`, неположительный порог заменяется `DefaultMinScore = 0.6` (валидация конфига допускает только (0, 1] — защита прямых вызовов с нулём). ТЗ: §5.8, §11.1, §5.10.
