# Декомпозиция ТЗ «Сервис массовой проверки доменов и поиска сайтов на Laravel»

Источник: [`TZ_domain_crawler.md`](./TZ_domain_crawler.md) (версия 1.1).

## Как работать с файлом

- Задачи пронумерованы `T-001…T-114` и упорядочены по выполнению (сверху вниз).
- Статус задачи — метка в квадратных скобках, меняется редактированием:
  - `[новая]` — задача не начата;
  - `[в работе]` — задача выполняется;
  - `[сделана]` — задача завершена; по завершении волны строка задачи
    переносится в архив [`tasks_done.md`](./tasks_done.md) — здесь остаются
    только незавершённые задачи.
- Пример: `- **T-001** [в работе] — …`
- Внутри этапа задачи по возможности выполняются параллельно; между этапами — последовательно.
- Отступление от порядка этапов ТЗ §12: **хранилище контента** (этап 4 ниже) реализуется до HTTP-этапа, т.к. `http-worker` сохраняет контент через `ContentStore` (ТЗ §5.5, §5.7).

## Этап 10. Тестирование и приёмка (ТЗ §11)

- **T-092** [новая] — Нагрузочные замеры на целевом сервере: DNS QPS, HTTP RPS, скорость рендера, расход памяти по сервисам, скорость записи в БД и хранилище; уточнение значений по умолчанию в конфиге и оценка длительности первого цикла. ТЗ: §11.3, §13.2, §3.3.
  Заблокирована (2026-10-18): нужен развёрнутый целевой сервер (§10.1, systemd-деплой T-085…T-089); замеры на dev-машине не заменяют приёмку — числа обязаны быть с боевого железа. Разблокировка: после развёртывания боевого сервера.
- **T-093** [новая] — Суточный прогон на целевом сервере в рамках бюджета памяти без срабатывания OOM-killer. ТЗ: §11.4 (п. 7), §3.2.
  Заблокирована (2026-10-18): требует целевой сервер под нагрузкой 24 ч (та же причина, что T-092); бюджет памяти закреплён юнитами T-085, проверка — фактическим прогоном. Разблокировка: вместе с T-092.
- **T-096** [сделана] — Индекс `contents (pack_id, off)`: у таблицы метаданных контента только PK по `hash` (миграция 000001), а компактификация (internal/content, CompactLoop) выбирает строки пака `WHERE pack_id = $1 ORDER BY off` и `WHERE pack_id = $1 AND refcount > 0` каждый час — без индекса это seq scan всей таблицы, стоимость растёт линейно с корпусом и конкурирует с рабочими запросами (ревью этапа 12, INFRA-05). Решение: миграция `CREATE INDEX … ON contents (pack_id, off)` (покрывает фильтр и сортировку), проверка плана EXPLAIN после наката. Сделана (2026-10-18): миграция 000007 `contents_pack_off_idx` (pack_id, off) + down `DROP INDEX IF EXISTS`, контракт TestSchema_ResultsTablesIndexes, docs/schema.md; EXPLAIN-проверка — seq scan → Index Scan (без Sort) на изолированном PG 16 с реальными миграциями проекта (dev-PG основного стека был остановлен).

## Этап 11. Доработки по итогам код-ревью (2026-10-18)

Кандидаты из финальных отчётов групп фиксов; находки ревью, не закрытые
кодом из-за смены контракта, миграций или уровня новой функциональности.

### Ingest

- **T-097** [сделана] — Идемпотентность приёма на уровне доменов, аудит (вариант D ядрa ING-P2-5; продуктовое решение 2026-10-18). Аудит всех путей подтвердил гарантии: add существующего — ON CONFLICT по (zone_id, label); delete отсутствующего/уже удалённого — UPDATE без охраны, счётчики стабильны; revive — охрана status = deleted (повтор — no-op); повторная обработка файла — свежий batch_id, применённая партия покидает staging; CleanupDeleted/refcount — строго по фактически удалённым ссылкам. Починена мелкая дыра: сбой очистки партии в ветках порога ошибок и дубля не ретраился discard'ом (отмена ctx при graceful shutdown оставляла строки в staging). Тесты: юнит internal/ingest/idempotency_test.go (повтор после потери отчёта → no-op и одна запись журнала; discard-ретраи), интеграционные test/integration/ingest_idempotency_test.go (тот же файл дважды — снимки состояния БД неизменны; цикл revive; граница контракта дедупа до T-113; CleanupOnce × 2 + refcount по полному циклу delete→очистка→revive→delete). Документация: docs/incoming-files.md §6 «Идемпотентность повторной доставки». Вход для T-113: глобальный UNIQUE(sha256) пропускает undo тем же списком (закреплено тестом TestIngest_SameContentCrossActionSkipped до смены контракта); осиротевшие партии staging после kill -9 — T-098.
- **T-113** [новая] — Ослабление файлового дедупа до точной повторной доставки: миграция `UNIQUE (ingest_files.sha256)` → `UNIQUE (zone_id, action, sha256)` (безопасна: новый ключ слабее — существующие строки нарушить его не могут), пайплайн пропускает файл только при совпадении хэша, зоны и действия; дубль с другим действием (undo-сценарий: тот же список из `add/` в `delete/`) обрабатывается. Зависит от T-097 — повторная обработка должна быть доказанно безвредна.
- **T-114** [новая] — Приёмочные тесты и документация под новую семантику: кейс T-094 «дубль sha256 delete-файла легитимен» переопределяется (undo тем же списком теперь работает и удаляет домены), docs/incoming-files.md §5, docs/schema.md. Зависит от T-113.
- **T-098** [новая] — Фоновая зачистка осиротевших партий `ingest_stage` по возрасту batch_id (страховка ING-P2-3 от kill -9/падения СУБД; UNLOGGED-таблица переживает рестарт сервиса, но не рестарт PostgreSQL). Место — вместе с CleanupDeleted.
- **T-099** [новая] — Метрика/алерт по `CleanupResult.BadHashes` (мусорные `content_hash`): сейчас только Warn в логе; при всплеске — сигнал ошибки писателя результатов (T-056).

### HTTP

- **T-100** [сделана] — Составные `Content-Encoding` («gzip, br» — остаток H-10): многослойная распаковка в порядке RFC 9110 (последняя кодировка в списке — внешний слой) с потолком распаковки на каждый слой (единый `bodyCeiling`, не произведение); Accept-Encoding составные значения не рекламирует — значение от сломанного сервера принимается оборонительно, как одиночный deflate. Классификация хвоста (Truncated/ErrDecompressTooLarge) — по итоговому декодированному потоку, семантика T-051/H-2 сохранена.
- **T-101** [сделана] — Параллельный опрос A/AAAA хостов редиректов (остаток HW-07): `DNSLookup.LookupNetIP` (internal/httpworker/worker.go) спрашивает A и AAAA двумя горутинами с общим ctx — латентность резолва max(A, AAAA), не сумма; ipv6=false — один обмен без горутин. Семантика HW-07 сохранена: сбой/отказ одного типа при валидном другом — резолв успешен адресами живого; адресов нет вовсе — первая по порядку типов ошибка обмена (детерминизм A раньше AAAA); отмена ctx — отмена; порядок адресов стабилен A затем AAAA независимо от завершения (сборка по порядку types, транспорт видит прежний порядок). Тесты: перекрытие интервалов обменов + общее время < суммы (медленный A + быстрый AAAA, фейк со сном вне мьютекса), детерминизм первой ошибки, отмена ctx, порядок вопросов множеством (прибытие к резолверу недетерминировано); docs/services.md синхронизирован.

### Очереди и планировщик

- **T-104** [сделана] — Частичные индексы фоновых проходов scheduler (S-04): миграция 000008 — `domains_lease_idx (queued_at, zone_id, id) WHERE check_state = 1` и `domains_recheck_idx (last_checked_at, zone_id, id) WHERE check_state = 2`; литералы кодов + ORDER BY по ключу индекса в lease/recheck (линейный дренаж, ранний останов LIMIT). Retry (status в предикате ломал бы HOT delete-путей) и backlog (агрегат по всей таблице) — без индекса сознательно, задокументировано.
- **T-105** [сделана] — Байтовая защита q:dead (остаток Q-05): Dead-записи публикуются без payload исходных задач — вместо тела выжимка идентификаторов предмета (`deadSubjectOf` в bury, best-effort: q:dns — размер пачки `domains` (список до ~250 КБ не переносится, домены переиздаст lease-проход; пачки многозонные — зонный идентификатор невозможен), q:http — `zone_id`/`domain_id`/`name`, q:render/q:analyze — + `subdomain_id`/`variant` (ключ строки subdomain_results)); выжимка, сделавшая запись невалидной (чужое тело: вариант вне 0/1, имя длиннее лимита), откатывается к записи без идентификаторов — Publish не отклонит, XACK состоится, «ядовитая» задача уйдёт в карантин, а не застрянет в pending (P2 ревью); worst-case q:dead снижен с ~2,5 ГБ (10 000 × 250 КБ) до ~2–3 МБ при прежнем потолке 10 000 записей — на два порядка ниже бюджета Redis 0,5 ГБ (noeviction: переполнение = отказ всего транспорта). Вариант XTRIM по байтовому бюджету (MEMORY USAGE по расписанию) отклонён как лишний цикл/сложность: записи равномерно мелкие, потолок MAXLEN уже держит байты; уменьшение потолка записей не нужно — ручному разбору нужна история. Поле `payload` сохранено в формате (omitempty) только для чтения старых записей — Decode истории не ломается, валидация: заданный payload обязан быть JSON, диапазон `subdomain_id` (model.ValidateSubdomainID). Семантика at-least-once/q:dead-доставки не менялась (форма записи и бюджет). Тесты: TestReliabClaimDeadByteGuard (пачка 2000 доменов ≈ 120 КБ → запись ≤ 512 Б, идентификаторы и размер пачки сохранены, payload нет), TestReliabClaimDeadPoisonBody (чужое тело → запись без идентификаторов, перенос и XACK идут), TestDeadSubjectOf (все стримы + чужой формат/мусор), wire-форматы/roundtrip/валидация Dead обновлены, TestDecodeDeadLegacyPayload (старые записи читаются), интеграционный сценарий T-032 переключён с побайтового payload на идентификаторы (компилируется юнит-прогоном ./test/...). Документация: docs/redis.md §3 (бюджет q:dead в байтах — форма записи вместо обрезки), docs/runbooks.md §2 (что видит оператор: идентификаторы предмета, `domains`-размер пачки, отсутствие payload у новых записей, чтение исходного сообщения XRANGE по entry_id, вычистка старых записей XTRIM), docs/configuration.md (2 места), config.example.yaml. Ревью: opencode/deepseek-v4.1-flash-free#high — P0/P1 нет; P2 (застревание чужого тела в pending) и P3 (ValidateSubdomainID, XRANGE/XTRIM в runbooks, уточнение про неформатные сообщения) исправлены, P3 о запрете payload при публикации отклонён (двойной контракт чтения/записи формата ради гипотетического продюсера; единственный продюсер bury сторожится тестом).
- **T-106** [сделана] — Источник весов зон из конфигурации (остаток S-08): `scheduler.zone_weights` — карта «имя зоны (punycode, как в справочнике zones) → вес 1..1000» внутри секции scheduler (состав секций ТЗ 5.10 не расширен новыми секциями верхнего уровня); дефолт — отсутствие карты: все веса 1, равный круговой порядок (поведение до задачи); env `CRAWLER_SCHEDULER_ZONE_WEIGHTS="com=5,org=2"` заменяет карту целиком, ключи normalize-ом к нижнему регистру (детерминированное разрешение столкновений), валидация — вес 1..1000 и синтаксис punycode-имени зоны (fail-fast; unicode-имя отвергается — справочник его не содержит). Разрешение имён в zone_id — `scheduler.ResolveZoneWeights` (один запрос `SELECT id, name FROM zones`: все зоны, не только активные — вес неактивной вступает в силу при включении без рестарта; карта вызывающего не мутирует); cmd/scheduler разрешает на старте, имена без справочника — Warn, не ошибка (зону создаёт ingest первым файлом, ТЗ 5.1 — старт планировщика раньше ingest легитимен), зона проверяется с весом 1 до рестарта; стартовый лог цикла показывает число взвешенных зон. Тесты: конфиг (YAML/env разбор и приоритет замены целиком, дефолт, валидация весов и имён, normalize регистра), scheduler (разрешение по справочнику, unknown по возрастанию, ошибки/ctx, веса из конфигурации меняют порядок слияния пачки, SQL-контракт + UNIQUE zones.name миграции 000001). Документация: docs/configuration.md (поле, переменная, тип «карта», семантика Warn/неактивных зон), config.example.yaml (пример с комментарием). ТЗ: §5.3, §5.10.
