## Как работать с файлом

- Задачи пронумерованы `T-001…T-147` и упорядочены по выполнению (сверху вниз).
- Статус задачи — метка в квадратных скобках, меняется редактированием:
  - `[новая]` — задача не начата;
  - `[в работе]` — задача выполняется;
  - `[сделана]` — задача завершена; по завершении волны строка задачи
    переносится в архив [`tasks_done.md`](./tasks_done.md) — здесь остаются
    только незавершённые задачи.
- Пример: `- **T-001** [в работе] — …`
- Внутри этапа задачи по возможности выполняются параллельно; между этапами — последовательно.
- Отступление от порядка этапов ТЗ §12: **хранилище контента** (этап 4 ниже) реализуется до HTTP-этапа, т.к. `http-worker` сохраняет контент через `ContentStore` (ТЗ §5.5, §5.7).

## Этап 22. Доработки по итогам пропитки волны 21 (2026-10-23)

Источник: пропитка после деплоя волны 21 (HTTP 28 дом/с на 192 слотах,
память 860–893 MiB при MemoryMax 900M, oom=0; стартовый пик 256 слотов
давил healthz — деплой откатывался на 192) + фоллоу-апы ревью T-141/T-143.

- **T-144** [в работе] — Дашборд: пороги глубины очередей не согласованы с эффективными после T-141. Монитор-алерт (T-080) считает порог через `queue.StreamWatermark(watermark, MAXLEN/2)`, а дашборд оперирует собственными порогами без клампа по MAXLEN — после T-141 эффективные пороги: штучные стримы `min(100000, 150000/2)=75000`, `q:dns` `min(100000, 250/2)=125` пачек, и меняются с конфигом/MAXLEN. Синхронизировать дашборд с эффективными порогами (единый источник истины — StreamWatermark), юнит-тесты на связку конфиг×MAXLEN (порог дашборда == порогу монитора).
- **T-145** [в работе] — Мягкий потолок памяти http-worker и алерты OOM/рестартов: (1) юнит `MemoryHigh=850M` — троттлинг reclaim до hard-лимита 900M (по данным §11 и пропитки: 192 слота стабильно 860–893 MiB, oom=0; стартовый всплеск 256 давил healthz); (2) monitor: предупреждение в journald + метрика по `memory.events` `oom`/`oom_kill` > 0 юнитов crawler-* и `NRestarts` > 0 (по образцу алертов T-080); (3) docs/operations.md §4.4 чек-лист — строка контроля. ТЗ: §3.2, §9 (метрики/алерты).
- **T-146** [в работе] — Dev-стек: `mem_limit` http-worker 384m в deploy/docker/compose.yaml не соответствует дефолту `task_concurrency=256` (боевой юнит поднят до 900M, T-143; паритет сознательно снят) — при реальной нагрузке в dev OOM контейнера. Поднять до 900m, проверить согласованность остальных http.*/render.contexts дефолтов между dev и боем, docs/docker.md при необходимости.
- **T-147** [в работе] — Пиковая память слота http-worker ≈3.34 MiB (тела записей-оригиналов удерживаются до конца задачи домена для дедупликации алиасов, каждое ≤ `max_body_bytes` 2 MiB, + буферы) ограничивает параллелизм: 256 слотов ≈855 MiB, стартовый пик выше (провал healthz волны 21). Снизить пик: раннее сохранение тел в content-store (Put по хэшу сразу по получении) с дедупликацией алиасов по хэшу без удержания тела в памяти (перечитывание из store только при необходимости — финализация по хэшам/ссылкам) либо другой подход с обоснованием; цель ≤1.5 MiB/слот → 256 слотов ≤450 MiB (возврат MemoryMax вниз либо 512 слотов в 900M с повторным замером скорости). Дизайн-решение зафиксировать в docs (content.md/services.md), юнит- и интеграционные тесты, приёмка — повторный замер памяти слота на бою (операционно). ТЗ: §5.5, §5.7, §3.2.
