## Как работать с файлом

- Задачи пронумерованы `T-001…T-136` и упорядочены по выполнению (сверху вниз).
- Статус задачи — метка в квадратных скобках, меняется редактированием:
  - `[новая]` — задача не начата;
  - `[в работе]` — задача выполняется;
  - `[сделана]` — задача завершена; по завершении волны строка задачи
    переносится в архив [`tasks_done.md`](./tasks_done.md) — здесь остаются
    только незавершённые задачи.
- Пример: `- **T-001** [в работе] — …`
- Внутри этапа задачи по возможности выполняются параллельно; между этапами — последовательно.
- Отступление от порядка этапов ТЗ §12: **хранилище контента** (этап 4 ниже) реализуется до HTTP-этапа, т.к. `http-worker` сохраняет контент через `ContentStore` (ТЗ §5.5, §5.7).

## Этап 10. Тестирование и приёмка (ТЗ §11)

- **T-092** [новая] — Нагрузочные замеры на целевом сервере: DNS QPS, HTTP RPS, скорость рендера, расход памяти по сервисам, скорость записи в БД и хранилище; уточнение значений по умолчанию в конфиге и оценка длительности первого цикла. ТЗ: §11.3, §13.2, §3.3.
  Разблокирована (2026-10-22): целевой сервер развёрнут (T-135, 155.212.174.88, systemd-деплой; отчёт — в архиве этапа 17); замеры на dev-машине приёмку не заменяют — числа обязаны быть с боевого железа.
- **T-093** [новая] — Суточный прогон на целевом сервере в рамках бюджета памяти без срабатывания OOM-killer. ТЗ: §11.4 (п. 7), §3.2.
  Разблокирована (2026-10-22): целевой сервер под нагрузкой доступен (T-135); бюджет памяти закреплён юнитами T-085, проверка — фактическим прогоном. Запускать вместе с T-092.

## Этап 18. Извещения Telegram для CI/CD (ТЗ §10.4)

- **T-136** [в работе] — Извещения Telegram-ботом в группу по ТЗ §10.4: создать бота и группу, завести секреты репозитория `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID`; общий шаг уведомления в `ci.yml` (провал линта/сборки → «ошибка в коде», провал test/test-rules/test-integration → «ошибка тестов») и в `deploy.yml` (успешный деплой; неуспешный, включая откат по healthcheck); формат сообщения — тип события, workflow/шаг, коммит (короткий SHA + первая строка), ссылка на ран, для деплоя — версия `git describe` и факт отката; маркер успеха/ошибки в начале; одно событие — одно сообщение, без дублей; mutation и ручные прогоны молчат. Сбой отправки не красит ран: шаг выполняется по завершении рана независимо от статуса, провал фиксируется только в логе. Приёмка: коммит с ошибкой линта → извещение «ошибка в коде»; коммит с падающим тестом → «ошибка тестов»; штатный деплой master → извещение об успехе; путь неуспешного деплоя — проверяется ревью шага (намеренно ломать прод нельзя). Обновить `docs/ci-cd.md` (секреты, принцип уведомлений). ТЗ: §10.4.
