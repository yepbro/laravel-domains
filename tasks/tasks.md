# Декомпозиция ТЗ «Сервис массовой проверки доменов и поиска сайтов на Laravel»

Источник: [`TZ_domain_crawler.md`](./TZ_domain_crawler.md) (версия 1.2).
Дополнительные ТЗ этапов: [`TZ_dashboard.md`](./TZ_dashboard.md) —
операторский веб-дашборд конвейера (этап 15).

## Как работать с файлом

- Задачи пронумерованы `T-001…T-206` и упорядочены по выполнению (сверху вниз).
- Статус задачи — метка в квадратных скобках, меняется редактированием:
  - `[новая]` — задача не начата;
  - `[в работе]` — задача выполняется;
  - `[сделана]` — задача завершена; по завершении волны строка задачи
    переносится в архив [`tasks_done.md`](./tasks_done.md) — здесь остаются
    только незавершённые задачи.
- Пример: `- **T-001** [в работе] — …`
- Внутри этапа задачи по возможности выполняются параллельно; между этапами — последовательно.
- Отступление от порядка этапов ТЗ §12: **хранилище контента** (этап 4, архив)
  реализовано до HTTP-этапа, т.к. `http-worker` сохраняет контент через
  `ContentStore` (ТЗ §5.5, §5.7).

## Этап 32. Дренаж рендер-долга после окна T-198 (2026-10-29)

Контекст: окно T-198 оставило стек без планировщика (решение оператора)
при открытом `render.queue_high_watermark: 10000` — q:render дренирует
долг `render_pending` (~966 тыс. доменов на вечер 29.10). Разгон
измерен: 2 воркера × 6 контекстов — оптимум (144/мин максимум);
8 контекстов и второй chromium (по юниту :9223, откат) хуже — узкое
место 4 vCPU. Юнит-копия chromium требует правки `ReadWritePaths`
(найдено при подключении). Установлен таймер ресайкла crawler-chromium
каждые 2 ч (remote-режим не рестартит браузер сам — деградация памяти
400→950+ МиБ и таймауты ×2; замер: ресайкл halved таймауты).

- **T-207** [сделана] — P2 (сужено оператором: только исследование,
  без фиксов), эффективность дренажа рендер-долга. Вердикты: «потеря
  половины» — ошибка единиц: 1 домен ≈ 1,85–1,92 доставки
  (published/domains = 1026/535…1265/667 по журналам прохода),
  128 доставок/мин ≈ 67–69 доменов/мин; среднее 44/мин занижено
  медленными фазами дня (морозка wm=1 до 14:07, рестарты, тюнинг
  contexts), стационар вечера — ~60/мин (−49…−71/мин). PEL чист
  (102–166 записей, idle < 10 мин, ноль провисаний) — H1 клеймы
  ~5–10 %, не половина. H2/H3 опровергнуты: флаг lifecycle корректен
  (ставит запись результата при полной q:render, снимает проход
  публикации; 8 доменов из WARN-логов — флаг снят, снятия прохода
  сходятся со счётчиком точно). H4 опровергнута: проход не горло
  (10 пачек/10 мин, стоп по full=true watermark). Вечного ядра в
  долге нет; есть вечный хвост нерендеренных строк ~10–12 % эпизодов
  (таймауты/cert/мёртвые хосты ≈ 180–220 тыс. записей) — переиздаются
  при каждом будущем эпизоде. Реальные накладные: финализации без
  рендера ~10 % доставок (тарпит 15 с слота), ретраи классов задач
  5–10 %. ETA остатка ~954 тыс.: ~12 суток. Продолжения — T-210…T-212.

- **T-210** [сделана] — P2, маркер «рендер невозможен» в строках
  `subdomain_results` (по итогам T-207): финализированные-без-рендера
  строки остаются `rendered = false` навсегда и неотличимы от «не
  пробовали» — renderq-проход переиздаёт их при каждом новом эпизоде
  домена (~180–220 тыс. записей, ~2–3 доставки + слот-время на битой
  записи за эпизод; cert-класс и NAME_NOT_RESOLVED — постоянные
  свойства хоста, ретраи бессмысленны: замер T-172 — 0 успешных).
  Решение: колонка-штамп/маркер (или паттерн rules_version) у строки,
  проставляемый финализациями тарпит/cert/класса задачи; выборка
  прохода (`renderPendingRowsSQL`: rendered = false AND final_url IS
  NOT NULL) исключает маркированные до смены контента записи.
  Критерий: повторный эпизод битого хоста не переиздаёт
  отмаркированные записи; доля таких в выборке прохода → 0;
  test/lint/integration зелёные.

- **T-211** [новая] — P3, NAME_NOT_RESOLVED → финализация с первой
  доставки (по итогам T-207): расширить список классов «финализация
  без ретраев» (образец — ERR_CERT_DATE_INVALID, T-159/T-172) ошибкой
  DNS-отказа на рендере: мёртвый хост сейчас ест 3 доставки и ~20 мин
  в PEL (замер 29.10: 252 NAME_NOT_RESOLVED + 186
  CONNECTION_REFUSED). Риск мал (DNS-отказ на рендере при живом
  HTTP-эпизоде — редкость). Критерий: класс финализируется первой
  доставкой, метрики окна показывают −2 доставки на мёртвом хосте;
  test/lint зелёные.

- **T-212** [новая] — P3, операционная: переоценить `render.contexts
  6 → 8` при работающем таймере ресайкла chromium (по итогам T-207:
  29.10 contexts=8 деградировал памятью браузера без ресайкла —
  1368 МиБ и таймауты ×3; таймер T-208 каждые 2 ч режет накопление).
  Замер A/B по 40–60 мин: темп доменов/мин (не доставок!), таймауты,
  MemoryCurrent/oom chromium, PSI. Если устойчиво > стационара 60/мин
  без деградаций — оставить 8; иначе вернуть 6. Критерий: решение
  зафиксировано в конфиге с комментарием-замером.

- **T-208** [сделана] — P3, закрепить в репозитории таймер ресайкла
  Chromium: юниты `crawler-chromium-recycle.{service,timer}` (раз в 2 ч
  рестарт `crawler-chromium`) сейчас живут только на боевом сервере
  (`/etc/systemd/`, установлены 29.10 в окне T-198) — при переустановке
  хоста потеряются. Перенести в `deploy/systemd/`, дополнить
  `docs/deploy.md` §2.2 (remote-режим не позволяет воркеру рестартить
  чужой браузер — T-065; без ресайкла chromium копит память 400→950+
  МиБ за ~2 ч и таймауты рендера удваиваются, замер 29.10: ресайкл
  halved таймауты 227→110). Содержимое — с сервера (155.212.174.88,
  `/etc/systemd/system/crawler-chromium-recycle.*`); установка на прод
  уже выполнена — после мержа сверить файлы. Критерий: юниты в
  `deploy/systemd/`, docs обновлены, `make test`/`make lint` зелёные.

- **T-209** [сделана] — P3, юнит-шаблон второго Chromium с фикс
  `ReadWritePaths`: эксперимент 29.10 (второй chromium :9223 для
  `render-worker@9109`, откат — узкое место 4 vCPU) оставил рабочий
  юнит `crawler-chromium2.service` только на сервере. Закоммитить в
  `deploy/systemd/` как шаблон на случай возврата к двум браузерам на
  расширенном железе, зафиксировав найденный дефект юнита-копии:
  `ReadWritePaths` обязан указывать каталог профиля этого инстанса
  (`chromium2`), иначе `ProtectSystem=strict` блокирует запись и
  headless-shell падает в start-limit; упомянуть в `docs/deploy.md`
  §2.2 рядом с рецептом per-instance env. На проде юнит отключён —
  после мержа состояние сервера не меняется. Критерий: юнит в
  `deploy/systemd/`, дефект и фикс описаны в комментарии юнита и
  docs/deploy.md §2.2, `make lint` зелёный.
