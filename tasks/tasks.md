## Как работать с файлом

- Задачи пронумерованы `T-001…T-189` и упорядочены по выполнению (сверху вниз).
- Статус задачи — метка в квадратных скобках, меняется редактированием:
  - `[новая]` — задача не начата;
  - `[в работе]` — задача выполняется;
  - `[сделана]` — задача завершена; по завершении волны строка задачи
    переносится в архив [`tasks_done.md`](./tasks_done.md) — здесь остаются
    только незавершённые задачи.
- Пример: `- **T-001** [в работе] — …`
- Внутри этапа задачи по возможности выполняются параллельно; между этапами — последовательно.
- Отступление от порядка этапов ТЗ §12: **хранилище контента** (этап 4 ниже) реализуется до HTTP-этапа, т.к. `http-worker` сохраняет контент через `ContentStore` (ТЗ §5.5, §5.7).

## Этап 23. Разбор очереди мёртвых q:dead — OOM Redis (2026-10-23)

Источник: разбор 5507 записей q:dead на бою (полный дамп XRANGE +
журналы, 2026-10-23 ~06:20 MSK). Корневая причина — не рендер-тарпиты
(посылка T-148 о причинах смертей опровергнута, производственная часть
остаётся): **окно OOM Redis 22.10 16:00–18:15 MSK** — `q:dns` накопил
1887 легаси-пачек эпохи batch_size 5000 (~330 КиБ, ≈620 МиБ из
временного maxmemory 900M, T-093), `noeviction` отказывал во всех XADD
(http-worker 16 953 OOM-ошибки публикации, render 1953, dns 392,
scheduler 243) → обработки завершались ошибкой публикации результата →
доставки без XACK копили попытки клеймами → q:dead. Все умершие задачи
опубликованы в окне 15:00–19:00 MSK (2786 q:http — все за час 15:00,
2685 q:render, 36 пачек q:dns), смерти растянуты на 12 ч (18:00–05:24)
медленным обходом PEL RecoverLoop (16 клейм/30 с ≈ 2.6 ч/обход);
attempts 9–11 при лимите 3 — OOM падал и на публикациях в сам q:dead.
Ночью воркеры ошибок обработки не давали — «волны смертей» это
механический дожиг той же когорты. Согласовано с оператором 2026-10-23.

- **T-149** [сделана] — Операционно, P0: дренаж q:dns — освободить 620 МиБ легаси-пачек.
