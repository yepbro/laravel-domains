# Хранилище контента: пак-файлы (ТЗ 5.7)

Внешнее (вне PostgreSQL) хранение итоговых страниц: сырой HTML пишет
http-worker, итоговый DOM — render-worker; читают анализатор и
`crawlerctl domain --content`. Реализация `internal/content`
(`PackStore`), интерфейс `ContentStore` — задача T-041, сжатие и
обучаемый словарь zstd — T-043.

## Каталог и пак-файлы

Каталог — `content.dir`. Файлы:

| Файл | Назначение |
|---|---|
| `pack-NNNNNN.pack` | пак: append-only контейнер сжатых блоков контента |
| `.packs.lock` | файл межпроцессной блокировки (flock) писателей |
| `dict.zst` | активный словарь zstd (путь — `content.zstd_dictionary`, обучается `crawlerctl dict train`) |
| `dict-NNNNNNNN.zstd` | реестр прежних словарей: архив словаря с ID `NNNNNNNN` (8 шестнадцатеричных цифр), читаемость старых паков после переобучения (T-103) |

`pack_id` — порядковый номер в имени файла (1, 2, …), монотонно растёт.
Реестр паков — само множество файлов плюс заголовок каждого (дублирует
id): отдельной таблицы `packs` в схеме нет (ТЗ 6.1), миграция не
вводилась. Новейший пак — максимальный `pack_id` в каталоге.

## Формат пака (v1)

Все целые числа — little-endian.

```
заголовок (23 байта):
  magic    [4]байта  "CDPK"
  version  u8        1
  hdrLen   u16       длина заголовка целиком (23; поля будущих версий
                     дописываются в конец — читатель v1 берёт первые
                     23 байта, неизвестный хвост игнорирует: расширение
                     заголовка не ломает читателя v1; hdrLen меньше 23 —
                     повреждение)
  packID   u32       номер пака = номер в имени файла
  maxSize  u64       порог ротации на момент создания (content.pack_size)
  dictID   u32       ID словаря zstd на момент создания (0 — без словаря)

записи до конца файла:
  len      u32       длина сжатых данных блока
  блок     [len]байт кадр zstd (CompressWithDict — словарь T-043 или без)
```

`contents.off` указывает на **начало сжатых данных** блока (после
префикса длины), `contents.len` — их длина: чтение — один `ReadAt`.
`raw_len` — размер несжатого контента; после распаковки сверяется
(детекция порчи). Префикс длины нужен сканированию пака компактификацией
(T-045); обрыв записи в середине блока оставляет недописанную запись без
метаданных — на чтение контента не влияет, сканер T-045 обязан быть
устойчив.

`dictID` в заголовке фиксирует, каким словарём сжимались блоки пака на
момент его создания (диагностика при старте — `WarnDictMismatch`;
блоки, перенесённые компактификацией, сохраняют исходное сжатие — кадр
несёт свой dictID сам). Читаемость старых кадров после переобучения
обеспечивает реестр прежних словарей — см. «Словарь и реестр прежних
словарей».

## Словарь и реестр прежних словарей (T-043/T-103)

Сжатие маленьких страниц (парковки, заглушки) заметно выгоднее с
обученным словарём: типовой шаблон кодируется один раз. Активный
словарь — один на процесс, файл по пути `content.zstd_dictionary`
(`SetDictFile` при старте); **запись** новых блоков всегда идёт активным
словарём (`CompressWithDict`), реестр в сжатии не участвует.

**Реестр прежних словарей** делает переобучение безопасным для
читаемости. `crawlerctl dict train` перед записью нового файла
архивирует прежний словарь под именем `dict-<id>.zstd` (id — dictID,
8 шестнадцатеричных цифр; атомарная запись) в каталоге активного
файла. **Чтение** (`Get` → `DecompressWithDict`) идёт кадрами: пока
кадр распаковывается активным (или каркасным беззоварным) декодером,
реестр не нужен; ошибка «unknown dictionary» включает до-регистрацию —
dictID извлекается из заголовка кадра, словарь **лениво** загружается
из `dict-<id>.zstd` и **memoизируется** на время жизни процесса
(повторные чтения не ходят в ФС). Отрицательный результат не
memoизируется: файл, положенный в реестр на живом сервисе,
подхватывается следующим чтением без рестарта. Реестр работает и без
активного файла словаря — каталог определяется путём конфигурации.

Словаря в реестре нет (файл утерян) — прежняя ошибка распаковки с
уточнённым сообщением: `zstd.ErrUnknownDictionary` внутри `ErrCorrupted`,
текст называет dictID и путь ожидаемого файла (восстановление —
runbooks.md §1).

**Время жизни и место.** Файлы реестра не устаревают и не удаляются
автоматически: по ~100 КБ на словарь (110 КиБ по умолчанию обучения),
место вручную не критично. Удалять файл можно только когда паков,
сжатых этим словарём, в хранилище больше нет (свежее хранилище, полная
замена после компактификации): автоматических копий реестр не ведёт,
удалённый файл восстановим лишь повторным обучением на том же корпусе
образцов (детерминизм даёт тот же ID) — утерянные образцы означают
утерю читаемости старых паков навсегда. Регламент переобучения —
runbooks.md §1.

**Компактификация** переносит сжатые блоки как есть, без
перекомпрессии активным словарём: кадры несут свой dictID сами,
реестра достаточно для чтения. Заголовок нового пака называет активный
словарь момента создания — внутри могут оказаться и перенесённые блоки
прежних словарей (диагностика `WarnDictMismatch` смотрит заголовок
пака, чтение кадров от него не зависит).

## Ротация

Порог — `content.pack_size` (512 МБ по умолчанию; рекомендация ТЗ 5.7:
512 МБ–1 ГБ, границы валидирует конфиг). Когда дописывание очередной
записи превысило бы порог и пак уже содержит блоки, открывается новый
пак `pack_id+1`. Первый блок пака пишется всегда, даже если он один
больше порога: `max_store_bytes` ≤ 16 МиБ, `pack_size` ≥ 1 МиБ по
валидации конфига — ротация обязана продвигаться.

## Конкурентная запись

Put из многих горутин сериализуются мьютексом позиции записи; писатели
из разных процессов (http-worker, render-worker) — `flock(LOCK_EX)` на
`.packs.lock`. Допись **всегда идёт в новейший пак каталога**: активный
пак синхронизируется с реестром под блокировкой (свежесть реестра — по
mtime каталога, меняющемуся при создании/удалении паков; дописывание
его не меняет), поэтому все паки, кроме новейшего, закрыты для записи —
предусловие компактификации (T-045). Под блокировкой:

1. новейший пак каталога определяется по кэшу mtime (создание/удаление
   паков инвалидирует кэш, дописывание — нет);
2. размер активного пака пересчитывается `stat`-ом (его мог дописать
   другой процесс);
3. при ротации новейший пак ищется по каталогу — `pack_id` нового пака
   выделяется атомарно, без коллизий имён;
4. блок дописывается одним `write` (файл открыт с `O_APPEND`) и
   синхронизируется на диск (`fsync`) — байты блока доживают до диска
   раньше строки метаданных: при потере питания durable-строка без
   байтов невозможна (PostgreSQL коммитит асинхронно,
   `synchronous_commit = off`); затем **строка
   метаданных фиксируется до снятия блокировки**: блок и его строка
   появляются атомарно относительно компактификации, удаляющей старые
   паки под той же блокировкой (T-045). Удержание flock на время запроса
   к БД — цена межпроцессного протокола; запись контента не является
   горячим путём (страницы приходят с сети медленнее коммита). Заголовок
   создаваемого пака и запись каталога о новом файле синхронизируются
   так же, до первого блока.

**Групповая фиксация (T-102).** Доставка воркера сохраняет несколько
страниц сразу, и платить fsync-на-блок за каждую расточительно: `PutBatch`
(необязательное расширение `BatchStore`) фиксирует пачку контентов одной
групповой фиксацией — дедуп-пачка одним `UPDATE … WHERE hash = ANY(…)
RETURNING`, затем под **одним** захватом мьютекса и flock: дописывание
всех блоков, **один fsync пачки**, **один пакетный INSERT** метаданных
(unnest-массивы; дубликаты хэша внутри пачки сведены в одну строку со
счётчиком ссылок — `ON CONFLICT` не может затрагивать одну строку
дважды, а `refcount = n` сохраняет семантику «каждый Put добавляет
ссылку»). Инвариант C-1 не ослаблен: fsync пачки выполняется до фиксации
любой строки пачки («байты раньше строк»; паки, закрытые ротацией внутри
пачки, синхронизируются при ротации — как у пачек компактификации
C-11), а пакетный INSERT идёт под flock, взятым до первого дописывания —
компактификация не может удалить пак незафиксированной строки пачки.
Сбой пачки атомарен (одна команда INSERT): строк либо нет, либо все на
месте; блоки сбоя — мусор для T-045; повторная доставка идемпотентна по
хэшу. Синтетический бенчмарк (`BenchmarkPut*`, `internal/content`):
построчная запись ~7 мс/контент против ~1.2 мс (пачка 8) и ~0.5 мс
(пачка 32) на локальном NVMe/ext4 — на tmpfs разница исчезает, выигрыш
именно в амортизации fsync.

Get не блокирует: паки append-only, зафиксированные смещения стабильны,
файл открывается на чтение по запросу. Исчезнувший файл (компактификация
удалила пак между чтением строки и открытием файла — строка уже
переехала) не даёт ошибки: метаданные перечитываются один раз, чтение
идёт по новому размещению. Блок, нечитаемый при живой строке
(потеря/порча байтов), отличим от отсутствующего контента: Get отвечает
`ErrCorrupted` (сентинел `store.go`), а не `ErrNotFound` и не ошибкой БД.

## Метаданные и транзакционность

Строка `contents(hash PK, pack_id, off, len, raw_len, refcount)`
(миграция 000001, ТЗ 6.1) ведётся через пул `internal/db` четырьмя
операторами:

| Операция | SQL |
|---|---|
| Put, дедуп | `UPDATE contents SET refcount = refcount + 1 WHERE hash = $1 AND refcount > 0` |
| Put, новый блок | `INSERT INTO contents (hash, pack_id, off, len, raw_len, refcount) VALUES (…) ON CONFLICT (hash) DO UPDATE SET refcount = contents.refcount + 1, pack_id = EXCLUDED.pack_id, off = EXCLUDED.off, … RETURNING (xmax = 0)` |
| PutBatch, дедуп-пачка (T-102) | `UPDATE contents SET refcount = refcount + 1 WHERE hash = ANY($1::bytea[]) AND refcount > 0 RETURNING hash` |
| PutBatch, новые блоки (T-102) | `INSERT INTO contents (…) SELECT … FROM unnest($1::bytea[], …, $6::int4[]) AS v(…) ON CONFLICT (hash) DO UPDATE SET refcount = contents.refcount + EXCLUDED.refcount, … RETURNING hash, (xmax = 0)` |
| Get | `SELECT pack_id, off, len, raw_len FROM contents WHERE hash = $1 AND refcount > 0` |
| Delete | `UPDATE contents SET refcount = refcount - 1 WHERE hash = $1 AND refcount > 0` |

Порядок записи нового контента (ТЗ 3.4, at-least-once): **спул блока в
пак (с `fsync`) → фиксация метаданных**. Краш между шагами оставляет в
паке мусорный блок без строки метаданных — он невидим (Get идёт только
по метаданным) и вычищается компактификацией (T-045). Обратное окно —
«строка durable, байтов нет» — закрыто fsync-ом блока до INSERT (и
fsync-ом заголовка/каталога при создании пака): строка, пережившая
потерю питания, всегда имеет байты на диске. Дедупликация — наоборот,
сначала `UPDATE`: живой контент не пишет байтов вовсе (`Created = false`,
контракт T-041). Пачка (`PutBatch`, T-102) идёт тем же порядком, но
одним fsync и одним пакетным INSERT на пачку (протокол — «Конкурентная
запись», групповая фиксация); `Created = false` у дедупликаций и повторов
хэша внутри пачки.

Счётчик ссылок:

- Put добавляет одну ссылку (дедуп — `UPDATE`, новый контент — `INSERT`,
  конкурентная гонка одного контента — `ON CONFLICT … refcount + 1`,
  блок проигравшего — мусор для T-045);
- Delete снимает одну; `refcount = 0` — строка остаётся «мёртвой»:
  Get её не видит, Delete отказывает (`ErrNotFound`), физическое
  освобождение места — компактификация (T-045), которая обязана удалять
  мёртвые строки вместе с блоками;
- воскрешение: Put контента с мёртвой строкой дописывает свежий блок и
  переводит размещение на него (`EXCLUDED`-поля upsert); `Created` при
  этом `false` — конфликт идёт веткой `DO UPDATE` (`RETURNING
  (xmax = 0)` различает вставку и обновление; CommandTag на
  `INSERT … ON CONFLICT` всегда `INSERT 0 1` и ветки не различает).
  Фактически байты писались — расхождение с «дедупликацией» редкое и
  влияет только на метрику доли дедупликации (ТЗ 11.4 п. 3);
- перезапись результата со сменой контента — своп ссылок `SwapRef` /
  `SwapRefTx` / `(*PackStore).SwapRef` (T-044, ТЗ 5.7, 8): атомарно
  в одной транзакции `+1` новому хэшу, затем `−1` старому (те же
  операторы, что выше). Порядок «сначала новый, потом старый» — выбор
  по ТЗ 3.4: крах между раздельно выполненными шагами оставляет лишнюю
  ссылку у старого контента (безопасно, блок остаётся живым), обратный
  порядок мог бы привести к потере живой ссылки (refcount → 0 у контента,
  на который ссылается результат, — компактификация T-045 освободила бы
  блок). Нулевой `Hash` — «нет ссылки» (NULL `content_hash`): старый
  нулевой — только `+1`, новый нулевой — только `−1`, `old == new` —
  no-op без транзакции (идемпотентность повторной доставки). Нарушение
  охраны `refcount > 0` (`RowsAffected` = 0) — ошибка целостности
  `ErrRefIntegrity` с откатом транзакции: лучше ошибиться, чем молча
  испортить счётчик. Запись `subdomain_results` выполняет http-worker
  (T-058), вызывая своп в той же транзакции (`SwapRefTx`).
- retention не-находок (T-166) — третье снятие ссылок: очистка записи
  (`content_hash` → NULL) уменьшает `refcount` той же транзакцией
  (GREATEST-охрана от минуса, как у очистки T-020), строки `contents`
  без ссылок удаляются сразу; см. «Retention контента и трим
  не-находок (T-166)».

## Запись из http-worker (T-056/T-147)

Сырой HTML итоговых страниц пишет http-worker **ранним Put** (T-147):
каждая скачанная страница уходит в `ContentStore` сразу по получении —
воркер (`internal/httpworker/worker.go`, checkScheme) прочитал тело,
привёл к UTF-8, вычислил хэш и SPA-вердикт — и сохранил байты `Put`-ом
по хэшу, после чего тело в памяти не удерживается (память слота:
метаданные + буферы `http.task_per_domain` читаемых тел; до T-147 тела
записей-оригиналов держались до конца задачи домена — ≈3.34 MiB/слот,
замер T-092 §11). Сборка сервиса (`cmd/http-worker`) открывает
`OpenPackStore` (каталог `content.dir`, лимиты секции `content`),
активирует словарь zstd (`SetDictFile`, T-043) и запускает
`DiskWatchLoop` (T-046) горутиной; хранилище передаётся и воркеру
(`Options.Store`), и сверке ссылок (`ContentSaver`,
`internal/httpworker/store.go` — вызывается в хуке `Options.OnResult`
до записи результата T-058 и XACK, ТЗ 4.2).

Дедупликация парковок и заглушек (ТЗ §8) — двухуровневая:

1. **задача домена** (T-053/T-055): кэш «итоговый URL → результат» не
   скачивает одну страницу дважды; `DetectAliases` собирает записи с
   одинаковым итоговым URL или одинаковым хэшем контента в класс
   эквивалентности — сравнение всегда идёт по хэшам, тела записям не
   нужны; контент класса хранится **один раз** — `content_hash`
   остаётся только у записи-оригинала (`StoreContent = true`);
   записи-алиасы собственной ссылки не получают: их `content_hash` —
   NULL, контент доступен через `alias_subdomain_id` оригинала;
2. **хранилище** (T-041/T-042): `Put` дедуплицирует по хэшу — одна и
   та же парковочная страница разных доменов лежит одним блоком,
   `refcount` растёт, новых байтов не пишется (`Created = false`).

Сверка ссылок ранних Put — `ContentSaver` в том же хуке: реестр Put-ов
задачи сверяется с записями результата — запись-оригинал **наследует**
свою ссылку раннего Put (строка `subdomain_results` вступает во
владение, refcount не меняется, своп при перезаписи снимет —
T-044/T-058), а ссылки, не ставшие чьей-либо строкой — свёрнутые
вариант-логикой проверки (оба протокола — один сайт), проигравшие
классы алиасов, повторные скачивания того же контента, — отпускаются
`Delete`. Запись, ссылающаяся на хэш без раннего Put, —
рассинхронизация воркера и хранилища: громкая ошибка доставки (ссылка
без счётчика сломала бы учёт `SwapRef`, T-044).

Хэш — один источник: воркер вычисляет `HashOf` над UTF-8-нормализованным
телом (T-051), ранний `Put` получает те же байты и обязан вернуть тот
же хэш (контракт T-041) — воркер сверяет возврат до отбрасывания тела,
расхождение роняет задачу сразу.

Пустое тело (`Content-Length: 0` — парковки и пустые 400/404/500) —
валидный контент с тем же контрактом (T-138): `ToUTF8` возвращает пустой
не-nil слайс, хэш пустых байтов один у всех пустых страниц — вариант-
логика, алиасы и дедупликация собирают их в один класс и один блок,
ранний Put сохраняет пустые байты как любые другие, `content_hash`
записи не гасится (до T-138 предохранитель «тело записи недоступно»
читал пустое тело как отсутствующее и снимал хэш у ~4% задач).

Цена раннего Put против групповой фиксации: по одному fsync и INSERT
метаданных на скачанную страницу вместо пачки на доставку (`PutBatch`,
T-102, http-worker больше не использует — буферизация тел до конца
задачи ради одной фиксации и держала пик памяти слота; `PutBatch`
остаётся контрактом `BatchStore` для потребителей, сохраняющих
несколько контентов сразу). Объём: ~2–4 Put на домен против прежних
~3 на сохраняемые записи плюс ~1–2 Delete свертки — SSD держит тысячи
fsync/с; влияние на скорость видно по метрикам этапа после деплоя
(docs/load-measurements.md).

Контент может не сохраниться — результат домена при этом **не
роняется** (ТЗ §8: пауза записи контента, не результатов): запись живёт
с `content_hash = NULL` и признаком `Record.ContentNotStored`, Warn
пишет воркер при получении страницы (сверка добавляет сводный Warn о
записях без контента). Причины:

| Причина | Поведение |
|---|---|
| `ErrStoreFull` — диск ниже порога `content.disk_free_percent` (T-046) или ENOSPC | контент не сохраняется; дедуп-ссылки на уже живой контент проходят и при переполнении; повторная проверка домена (recheck, T-030) сохранит страницу |
| `ErrTooLarge` — тело сверх `max_store_bytes` (ТЗ 5.5) | контент отвергается хранилищем целиком, лимит проверяет `Put` |
| обрезка `max_body_bytes` (`Record.Truncated`, T-049) | не сохраняется вовсе и без `Put`: хэш усечённых байт врал бы при дедупликации; частичность уже отмечена `Truncated`/`ErrBody` |

`content_hash` в `subdomain_results` — ссылка на `contents` (§6.1):
хэш появляется в записи только вместе с сохранённым блоком — ссылка без
счётчика ломала бы учёт (`SwapRef` T-044, фоновая очистка T-020).

Ошибки раннего `Put` другого рода (сбой БД, отмена ctx), ошибки
`Delete` свертки и рассинхронизация реестра — ошибка задачи/`OnResult`:
доставка не подтверждается, повторная доставка переиграет эпизод
(ТЗ 3.4). Повторный `Put` тех же байтов добавит лишнюю ссылку без новой
записи — утечка места в безопасную сторону (тот же выбор, что у
`SwapRef`): блок остаётся живым, данные не теряются. Ссылки попытки,
не дошедшей до свертки (крах процесса, сбой Put), — та же безопасная
утечка; свертка снимает лишние ссылки только живой попытки.

Память: тела страниц в памяти слота не удерживаются (T-147) — ранний
Put освобождает байты сразу после чтения; в задаче остаются хэши,
заголовки, цепочки и вердикты, читаемые тела ограничены
`http.task_per_domain` × `max_body_bytes` (буфер чтения
предвыделяется по Content-Length без Content-Encoding — без удвоений
`io.ReadAll`). Потолок тела — `max_body_bytes` (2 МиБ), страниц в
задаче ≤ 2 × субдомены ≤ 126 (§5.10).

## Замена контента рендером (T-067)

Итоговый DOM отрендеренных страниц пишет render-worker
(`internal/renderworker`, ТЗ 5.6 «итоговый DOM заменяет сырой HTML в
хранилище»): задача q:render указывает на строку `subdomain_results`,
DOM (те же байты формата HTML, что сериализует Chrome — T-064) кладётся
`Put`-ом в то же хранилище, затем **одной транзакцией** строка
переключается на новую ссылку (`rendered = true`, `content_hash` = хэш
DOM, итоговые URL/cookies/заголовки рендера), а старая ссылка снимается
`SwapRefTx` (T-044) — в точности своп перезаписи результата (T-058).
Открытие `OpenPackStore`, словарь и `DiskWatchLoop` — те же, что у
http-worker: паки одни на оба писателя (flock, см. «Конкурентная
запись»).

Особенности против записи HTTP-этапа:

- DOM побайтово равен сохранённому контенту строки — `Put` и своп
  пропускаются (ссылка уже есть, лишний `+1` не нужен);
- строка перезаписывается только пока её `content_hash` тот же, что
  прочитан перед рендером (оптимистическая охрана `UPDATE`):
  перепроверка домена (T-030/T-058), перезаписавшая результат, отсекает
  подмену контента чужого эпизода — ссылка `Put` снимается `Delete`,
  доставка подтверждается;
- алиасная строка (контент класса хранится у оригинала, T-055) после
  рендера получает **свою** ссылку: профили изолированы, DOM каждой
  страницы — сам по себе (класс эквивалентности — оптимизация
  HTTP-этапа, а не запрет записи владеть контентом);
- `ErrTooLarge` (DOM раздут JS сверх `max_store_bytes`) — ошибка задачи,
  строка не меняется: попытки доставки исчерпаются и задача уйдёт в
  q:dead (T-025) — оператору сигнал поднять лимит; `ErrStoreFull` —
  временное, повторная доставка дождётся места.

Повторная доставка q:render идемпотентна (ТЗ 3.4): повторный рендер
перезаписывает контент и refcount (баланс T-058), `rules_version`
сбрасывается в NULL — прошлое заключение анализатора к новому контенту
не относится, публикация q:analyze после фиксации переанализирует.

## Компактификация (T-045)

Delete и фоновая очистка (T-020) лишь помечают данные мёртвыми
(`refcount = 0`), перезаписи переводят размещения на свежие блоки, а
краш-окна записи оставляют блоки без строк — место в паках занято, но
не живое. Фоновая компактификация (`internal/content/compact.go`)
переписывает живые блоки в новые паки и удаляет старые файлы, когда
доля живых данных пака падает **строго ниже порога** — по умолчанию 50 %
(ТЗ 5.7; `DefaultCompactThreshold`, `CompactOptions.Threshold`).

**Скан** (`CompactScan`): строки `contents` пака (`pack_id`,
`refcount`) плюс обход файла по префиксам длины — живые, мёртвые и
мусорные байты/блоки, доля живых = живые байты / байты записей.
Недописанный хвост (краш записи) — мусорные байты, не блок; строка,
указывающая мимо целой записи, — ошибка (повреждение), такой пак не
компактифицируется.

**Правка одного пака** (`CompactPack`; порядок по ТЗ 3.4):

1. живые блоки переписываются в новейший пак обычным путём записи
   (пачка `appendBatch`: мьютекс + flock, `O_APPEND`, один fsync на
   пачку — исходный пак открыт один раз на проход) — старый файл не
   трогается, блоки копируются дословно (сжатые, `len`/`raw_len` в
   метаданных не меняются);
   блок, нечитаемый при копировании (потеря/порча байтов), не
   останавливает правку: его строка помечается мёртвой той же
   транзакцией (`refcount = 0`, удалить такой контент иначе нельзя —
   дедуп Put видит живую строку и байтов не пишет), пак остаётся
   компактифицируемым, а расхождение целостности собирается в ошибку
   `CompactPack` (Warn прохода). Строка, указывающая мимо целой записи
   файла, — повреждение метаданных: скан отказывается, такой пак не
   компактифицируется (ручное вмешательство);
2. транзакция — пачками по 1000 строк, короткими — переносит размещения
   живых строк на новые блоки (`UPDATE … WHERE pack_id = N AND
   refcount > 0`) и удаляет мёртвые строки пака (`DELETE … WHERE
   refcount = 0`, вместе с блоками — как требует контракт T-041/T-042);
3. файл старого пака удаляется после контроля (живых строк для пака не
   осталось, размер не менялся), unlink — под мьютексом и flock.

Краш-безопасность на каждом шаге (ТЗ 3.4):

- крах до коммита транзакций — старый пак цел и остаётся источником
  истины, скопированные блоки — мусор в новом паке, следующий проход
  переигрывает;
- крах после коммита, до удаления файла — файл состоит из одного
  мусора (живых строк для пака нет): следующий проход видит долю живых
  0 и удаляет его;
- строка, умершая между чтением и транзакцией (охрана `refcount > 0`),
  не переносится и не удаляется пачкой (читалась живой): перед удалением
  файла пака такие строки вычищает финальная зачистка мёртвых строк пака
  (`DELETE … WHERE pack_id = N AND refcount = 0`) — осиротевшие указатели
  в удалённый пак не копятся; не удалённая (крах до зачистки) строка
  невидима (Get только по `refcount > 0`), воскрешение Put допишет свежий
  блок и переведёт размещение — потери нет.

**Закрытость для записи.** Компактифицируются только паки, кроме
новейшего (проверяется под flock в том же захвате, в котором выделяются
id новых паков). Писатели дописывают исключительно в новейший пак и
фиксируют строку метаданных, не отпуская flock, поэтому множество строк
не-новейшего пака заморожено в момент появления следующего пака —
опоздавших дописываний и «подвисших» строк не бывает, а контроль перед
удалением — страховка. Из этого следует и требование к развёртыванию:
писатели и компактификация должны быть одной версии ПО (смешение
семантик блокировки при rolling deploy не поддерживается).

**Цикл** (`CompactLoop`, стиль RecheckDaily и T-020): проходы `CompactOnce`
по ticker (первый — сразу, дренаж накопленного за простой), ошибка пака
собирается в ошибку прохода — Warn, цикл продолжается; отмена ctx —
чистый `nil` (контракт OnRun, ТЗ 3.4). Интервал — час
(`DefaultCompactInterval`; ТЗ 13.2 оставляет темп на усмотрение
разработки, конфигурации пока не вынесены — как у T-020). Цикл запускает
http-worker — горутиной `OnRun`, рядом с `DiskWatchLoop` (один владелец
на хранилище; второй писатель компактификацию не запускает).

Пик места «старое + новое» проход учитывает: пак с живыми блоками не
начинает копироваться, когда свободное место уже ниже порога
`content.disk_free_percent` — копия писалась бы поверх ещё не удалённого
пака и упёрлась бы в ENOSPC на полпути; такой пак возвращается в ошибке
прохода (Warn цикла) и повторяется, когда место вернётся. Паки без живых
блоков ничего не копируют и удаляются при любом месте — это и есть путь
освобождения места на переполненном томе.

**Занятое место.** Отдельного счётчика нет: занятое хранилищем место —
сумма размеров пак-файлов каталога, после удаления старого пака она
честно уменьшается (`CompactResult.FreedBytes`, сумма прохода —
`CompactStats.FreedBytes`). Проактивный контроль места по этой же
причине читает свободное место живым `statfs`, а не копит счётчик:
ротация и компактификация немедленно отражаются в следующей проверке
(см. «Переполнение диска»).

## Retention контента и трим не-находок (T-166)

Диск без новых мощностей (решение оператора 2026-10-23: расширение тома
недоступно, S3 и архивирование отложены): рост ≈36 GiB/сут (контент
20.3 + БД 15.5, docs/load-measurements.md §12) останавливается окном
времени. Контент и тяжёлые jsonb нужны конвейеру ограниченное время —
анализатор читает тела и headers/cookies (ТЗ 5.8), рендер заменяет
контент SPA-записей (ТЗ 5.6), переанализ находок (T-074) переприменяет
правила к сохранённым страницам. Запись, остаревшая сверх
`content.retention` и не нужная более этим потребителям, освобождается;
паспорт строки (`http_status`, `final_url`, `error`, `response_ms`,
`checked_at`, `scheme`, `subdomain_id`, `variant`) остаётся всегда —
`domain_info` (ТЗ 5.11) и дашборд продолжают отвечать, «пустой» контент
легален у всех потребителей (T-056).

**Критерий отбора** (все части обязательны):

- `checked_at` старше `content.retention` (дефолт 6 ч; граница —
  `now() − interval` сервера БД, тем же `now()` пишет `checked_at`
  HTTP-эпизод, T-058);
- домен **не Laravel-находка**: нет строки `laravel_domains` (находка —
  уверенные срабатывания порога §13.1). Находки хранят контент всегда —
  доказательство и материал переанализа T-074; слабые срабатывания
  (`laravel_findings` с `is_laravel = false`) находкой не считаются;
- запись **не ждёт рендера**: домен без флага `render_pending` либо
  запись уже `rendered`. Флаг — воронка прохода доработки T-066
  (`RequeueRenderPending` перечитывает контент записей для повторного
  SPA-вердикта); `rendered = true` — рендер уже заменил контент (T-067),
  старый не нужен;
- домен не удалён (§13.1: deleted — территория фоновой очистки T-020).

**Чистка одной транзакцией** (ТЗ 3.4, инварианты refcount T-044): одним
UPDATE строка теряет и ссылку, и jsonb — `content_hash`, `headers`,
`cookies`, `tls`, `redirects`, `addrs`, `cname` → NULL; по фактически
срезанным не-NULL хэшам (агрегированно: один контент может ссылаться из
многих записей) уменьшается `contents.refcount`, строки, лишившиеся
последней ссылки, удаляются сразу — не только помечаются мёртвыми, как
у очистки T-020: retention — массовый источник мёртвых блоков, и строки
`contents` иначе копились бы до компактификации затронутых паков (пак с
долей живых ≥ порога её не запускает). Физическое место блоков в паках
возвращает часовая компактификация T-045 — purge лишь прекращает право
контента на место. Сбой на любом шаге транзакции откатывает её целиком:
срезанная без decref ссылка навсегда ломала бы учёт (краш-окна
закреплены тестами, стиль T-044).

Колонки неиндексированные (индексов на `subdomain_results`, кроме PK,
нет) — UPDATE остаётся HOT (fillfactor 85, миграция 000002), место
страниц возвращает настроенный автовактуум (docs/db.md); контроль bloat
— тот же, что у массовых переводов T-030.

**Гонки с перезаписью** (recheck T-030 переписывает строки DELETE+INSERT
со свежим `checked_at` и, возможно, тем же контентом) отсечены двойной
охраной UPDATE: повторная проверка возраста и
`content_hash IS NOT DISTINCT FROM` прочитанного (NULL корректен —
«контента нет» легален, T-056; сравнение как в renderUpdateSQL T-067).
Защищаемые сценарии согласованы с потребителями: q:analyze-доставка
очищенной записи анализирует пустой вход (не падает, база T-056),
q:render-задача отрендерит и запишет свой DOM по-честному (охрана
обновления просто не сойдётся, если контент был срезан после чтения —
потерянная работа рендера, не данные); записи доменов с флагом
`render_pending` контентом обеспечены до снятия флага.

**Интерлок q:analyze** — тайминг обязан ждать потребителей: глубина
стрима (backlog группы потребления — lag + pending, тот же источник, что
у гейта T-026) у порога означает «анализатор не успевает», записи
очереди ещё не разобраны. Проход (и каждая пачка дренажа) пропускается,
пока глубина ≥ порога `content.retention_analyze_watermark` (0 — общий
`scheduler.queue_high_watermark`); ошибка чтения глубины — тоже
пропуск (консервативно): чистить «наугад» дороже, чем отложить проход.
Пропуск виден метрикой `crawler_content_retention_skips_total` и Warn в
логе http-worker.

**Цикл** (`internal/content/retention.go`, стиль CompactLoop/CleanupDeleted):
часовой тикер `content.retention_interval`, первый проход сразу —
дренаж накопленного за простой. Проход — курсорная пагинация по PK
пачками `content.retention_batch` (рабочая вилка 10–50 тыс. строк) до
исчерпания множества или интерлока; очищенные строки выпадают из отбора,
повторные проходы идемпотентны. Запускает цикл http-worker (горутиной
`OnRun`, рядом с компактификацией T-045): сервис уже держит пул БД, гейт
глубин стримов и реестр метрик, а purge лишь «кормит» компактификацию
мёртвыми блоками; второму владельцу цикл не нужен (охраны делают
параллельный запуск безопасным, но бесполезным — как у компактификации).
`content.retention = 0` — retention выключен, цикл не поднимается.

Зафиксированные отступления (согласованы с заказчиком, T-166):

- переанализ не-находок новыми правилами невозможен: контента и
  headers/cookies после очистки нет, повторное применение правил — на
  recheck (≈6 мес);
- слабые срабатывания не защищают контент (находка — строка
  `laravel_domains`): после смены правил переанализ T-074 перепишет их
  «признаков нет» по пустому входу — история срабатываний сохраняется в
  `laravel_findings.signals` до того;
- перепроверка теряет сравнение «изменился ли сайт»: перезапись
  DELETE+INSERT (T-058) пишет результат начисто, прошлого контента для
  сравнения нет.

Разовая очистка накопленного до внедрения окна — кампания T-167
(runbook): критерии те же, отличия — уменьшенные батчи под CPU-голодом,
VACUUM (ANALYZE) затронутых партиций после прохода и контроль
компактификации при массовом orphan-блоке.

## Лимиты и переполнение диска

Два настраиваемых предела (ТЗ 5.5, 5.7, 8):

- **`content.max_store_bytes`** — лимит одного контента («макс. размер
  хранимого HTML»). Превышение — `ErrTooLarge`, контент отвергается
  целиком: воркер сохраняет результат без контента (T-056). Байты
  сравниваются до сжатия — лимит про хранимую страницу, а не про блок.
- **`content.disk_free_percent`** — порог реакции на переполнение диска
  (ТЗ 8: «сервисы приостанавливают запись контента и сигнализируют
  об этом алертом; порог настраивается»). Порог — доля свободного места
  файловой системы каталога `content.dir`, %: типовой нижний предел
  томов данных, 5 по умолчанию, диапазон (0, 95] валидирует конфиг.

Механика порога диска (`internal/content/disk.go`, T-046):

1. **Перед записью** нового блока (Put после промаха дедупликации)
   снимается `statfs` каталога контента: доля доступного места
   (`statfs.Bavail` — то, что видит непривилегированный сервис, ТЗ 10.1)
   ниже порога — Put возвращает `ErrStoreFull` («пауза записи контента»):
   блок и строка метаданных не появляются, данные не портятся. Воркер
   по этой ветке не сохраняет контент, но результат пишет — это контракт
   ТЗ 8; повтор — позже (at-least-once, ТЗ 3.4).
   Пауза не останавливает остальное: **дедуп-ссылки** на живой контент
   продолжают добавляться (байты не расходуются), **чтение** (анализатор,
   переанализ, `crawlerctl domain --content`) работает всегда.
2. **Периодически** `DiskWatchLoop` проверяет то же условие по тикеру
   (`DefaultDiskWatchInterval`, 30 с; первый проход сразу): Warn в логе
   при входе в паузу и Info при восстановлении — алерт виден оператору,
   даже когда записей нет. Сигнал фронтовой (на переходах), а не на
   каждом тике.
3. **Восстановление автоматическое**: место освободилось (компактификация
   удалила паки, ручная чистка, расширен том) — следующая проверка
   проходит, запись продолжается без перезапуска сервиса.
4. **Сигнал алерта** — типизированное событие `StoreFullEvent` в хук
   `PackOptions.OnStoreFull` (счётчик для T-080: метрики/правила алертов
   — там, сам алерт здесь не реализуется). Источники события: `put`
   (каждый остановленный Put), `enospc` (физическая запись упёрлась в
   конец диска — последняя линия обороны после порога, T-042), `watch`
   (переходы периодической проверки, включая восстановление —
   `Recovered`). Заглушки порога для тестов — интерфейс `SpaceChecker`
   (`OSStatfs` — реальная ФС).

`ENOSPC` при физической записи пака остаётся страховкой на случай,
когда место кончилось между проверками (или порог выключен нулём в
`PackOptions` — конфиг такого не допускает): ошибка маппится в
`ErrStoreFull` (T-042) и даёт событие `enospc`.

## Ошибки

- `ErrTooLarge` — контент больше `content.max_store_bytes`, отвергается
  целиком (ТЗ 5.5);
- `ErrStoreFull` — места нет: доля свободного ниже `content.disk_free_percent`
  (проактивная пауза записи, см. «Лимиты и переполнение диска») либо
  физическая запись упёрлась в `ENOSPC`;
- `ErrNotFound` — нет живой строки (не писался или все ссылки сняты).
