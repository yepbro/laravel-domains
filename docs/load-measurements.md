## 3. HTTP-этап — узкое место конвейера

Стационарный режим (все три зоны приняты, q:http у порога
`scheduler.queue_high_watermark=100000`): **≈2 домена/с** (гистограммы:
mean 1.67 с, p50 ≈ 0.3 с, хвост 20–30 с — тарпиты/парковки). В запросах:
8 959 HTTP-обменов на 3 089 задач ≈ **2.9 запроса/домен** (живые субдомены
SU-доменов в среднем apex+www), т.е. ≈6 запросов/с на этапе — при заданном
в конфиге потолке `http.max_rps=1000` (не достигался: узкое место не
транспорт). Доля записей, ушедших в рендер (SPA-эвристика): 5.4%.

Причина — не сеть и не CPU (load 1–3 из 4, PSI CPU <10%): цикл
`httpworker.Run` читает q:http окнами **`Consume=16`** доставок и
обязан дождаться завершения **всего окна** (batched barrier) перед
следующим чтением; параллелизм задач захардкожен в `Options.withDefaults`
(`Concurrency=64`, `Consume=16`, `PerDomain=8`) и **конфигом не
переопределяется** — `http.concurrency=2000` действует только на транспорт
(RPS/соединения). При хвосте длительностей 20–25 с (`total_timeout=20s`)
потолок этапа ≈ 16/25с ≈ 0.6–2 дом/с — что и наблюдается. Дополняющая
сериализация: `per_ip_limit=4` против парковочных IP (в голове q:http
у топ-IP до 8% задач — 77.223.111.x, 95.163.244.138 и др.) при FIFO-порядке
потребления (head-of-line blocking).

Связка по backpressure: q:http у watermark → dns-worker не может публиковать
задачи живых доменов → DNS-этап останавливается темпом HTTP → весь конвейер
движется со скоростью ~2–3 дом/с. Для текущего прогона (7.16 млн доменов,
~79% SU-доменов резолвятся → ~5.4 млн HTTP-задач) это ≈31 сутки только
HTTP-этапа.

**Вывод (§13.2 «уточняются нагрузочными замерами»):** значения по
умолчанию для задачного параллелизма http-этапа требуется сделать
настраиваемыми и пересмотреть — вынесено в задачу T-139 (скользящее
потребление вместо барьера + проброс `Concurrency/Consume/PerDomain`
в конфиг; цель ≥100 дом/с в бюджете памяти — тела в полёте ограничены
`max_body_bytes=2 MiB`, тарпиты тел не держат).

> **T-139 реализовано** (после замеров): цикл `httpworker.Run` перешёл на
> скользящее потребление (чтение при освобождении слота, без барьера
> окна), задачный параллелизм настраивается `http.task_concurrency`
> (дефолт 256 → расчётно ≈150 дом/с), `http.task_consume` (16),
> `http.task_per_domain` (8) — docs/configuration.md, §http. Порядок
> раскатки (память §6 снята на старом параллелизме, MemoryMax юнита
> 384 MiB не поднимался): выложить с консервативным `task_concurrency`
> (64–128) → прогнать комплект T-092 → поднять до 256 по факту памяти.
> Критерий приёмки (на шаге 256; консервативные шаги ниже арифметически
> не дают ≥100 дом/с при средней задаче 1.67 с: 64 → ≈38, 128 → ≈77):
> стационар http-worker avg < 300 MiB и max/p95 < 350 MiB (пики к
> MemoryMax 384 MiB не упираются), связывающий сигнал —
> `memory.events oom=0` и отсутствие рестартов юнита, скорость
> ≥100 дом/с (сутки наблюдения, как T-093). Повторный замер этим же
> комплектом — операционный шаг после деплоя.
>
> **Раскатка выполнена (2026-10-22, детали — §11):** шаг 128 — anon
> ≈ 380 MiB, впритык к MemoryMax 384 MiB (мягко, oom=0); шаг 256 —
> **47.6 дом/с**, anon 834–873 MiB (avg ≈ 855, окно 12 мин). Критерий
> скорости ≥100 дом/с и критерий памяти avg < 300 / p95 < 350 (выше —
> исторический, писался до замера слота) не достигнуты: факт ≈ 3.34 MiB
> anon на слот на шаге 256 (на 128 — ≈ 3.0; тела записей-оригиналов,
> каждое ≤ `max_body_bytes` 2 MiB, + буферы — типичная смесь, не верхняя
> граница), скорость же диктует смесь длительностей (mean ≈ 5.3 с),
> а не число слотов. Итог раскатки: MemoryMax юнита поднят 384 →
> 900 MiB и закреплён в юните (T-143; на сервере — персистентный drop-in
> `systemctl set-property`; после обновления файла юнита (deploy.md §4.6)
> снять его: `systemctl revert crawler-http-worker` + daemon-reload +
> `restart` — иначе drop-in продолжит перекрывать юнит; проверка:
> `systemctl show crawler-http-worker -p MemoryMax` = 943718400);
> действующий критерий памяти — oom=0, NRestarts=0, anon ≤ 900 MiB
> на 256 слотах (сутки наблюдения — T-093); Go-сервисы суммарно
> ≈ 1.0–1.15 GiB < ≈ 1.3 ГБ ТЗ 3.2. Следующие резервы скорости —
> T-142 (рендер) и хвост `total_timeout`/per-IP; направление снижения
> памяти слота — стриминг тел в content-store по мере загрузки вместо
> удержания до конца задачи (требует пересмотра схемы дедупликации
> алиасов; не реализовано).

По измеренным потолкам этапов (SU-структура зон как ориентир долей:

|---|---|---|

| DNS | ≈210 дом/с (без душения HTTP) | ≈19 суток |

Итог: при поставленных дефолтах первый цикл упирается в HTTP-этап на

вечер. Текущий прогон 7.16 млн доменов продолжается непрерывно

прогоном T-093: сэмплер продолжает писать метрики, критерий — сутки
без OOM (на момент замера — ноль событий за 50 мин стационара при

## 9. Находки для задач

- **T-138** (bug): пустое тело ответа теряет ссылку на контент —
  `httpfetch.ToUTF8` на пустом теле возвращает `UTF8=nil`, http-worker
  ставит валидный хэш пустого тела, но `Body=nil` → предохранитель
  ContentSaver гасит `content_hash` (Warn «тело записи недоступно»,
  ~4% задач; парковки и 400/404/500 с `Content-Length: 0`). Нарушен
  контракт «хэш пустого тела валиден» (дедуп/классы пустых страниц).
- **T-139** (perf): task-параллелизм http-этапа захардкожен и не
  настраивается; барьер окна 16 доставок; проброс в конфиг + скользящее
  потребление; цель ≥100 дом/с. *(Реализовано: скользящее потребление +
  `http.task_*` с дефолтами 256/16/8; повторный замер — после деплоя.)*
- **T-140** (deploy): fontconfig/шрифты для headless-shell в пакетный
  список deploy.md §4.3 (иначе краш-луп на части страниц).
- Реликт q:dead (yandex.ru/admin, render эпохи T-135) — разбор по
  runbooks §2 вручную.

### 11.1. Пост-мортем q:dead 5507 (2026-10-23)
