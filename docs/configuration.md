# Конфигурация сервисов

Единый YAML-файл + переопределение переменными окружения (ТЗ 5.10 основного
ТЗ). Пакет `internal/config`; пример файла — [`config.example.yaml`](../config.example.yaml)
в корне репозитория.

## Приоритет источников

Значение каждого параметра выбирается по цепочке:

```
переменная окружения  >  YAML-файл  >  значение по умолчанию
```

- **Пустое значение переменной считается незаданным** (перекрывать YAML
  «пустышкой» нельзя — очистите поле в самом YAML).
- Списки (`resolvers`, `subdomains`) переменная заменяет целиком.
- Все значения после наложения проходят валидацию (см. ниже); при любой
  проблеме сервис не стартует, перечисляя все ошибки сразу.

## Файл конфигурации

| Что | Как |
|---|---|
| Явный путь | переменная `CRAWLER_CONFIG` |
| Устаревшее имя | `APP_CONFIG` (используется, если `CRAWLER_CONFIG` не задана) |
| Автопоиск | если переменных нет — `config.yaml` в текущем каталоге, когда файл существует |
| Нет файла вовсе | конфигурация из значений по умолчанию + окружения (валидация всё равно обязательна: нужен `postgres.dsn`) |
| Явный путь указан, файла нет | ошибка запуска (молчаливых дефолтов не бывает) |
| Неизвестный ключ YAML | ошибка запуска (опечатки не игнорируются) |

Пример локального запуска из корня репозитория: `cp config.example.yaml config.yaml`
— файл подхватится автоматом, без переменных.

## Типы значений

| Тип | Форма в YAML | Форма в переменных | Пример |
|---|---|---|---|
| строка | YAML-строка | как есть | `/data/incoming` |
| целое | YAML-число | десятичное число | `50000` |
| булево | `true`/`false` | `strconv.ParseBool`: `true/false/1/0/T/F` | `false` |
| длительность | строка `time.ParseDuration` | та же | `5s`, `30m`, `24h`, `4380h` |
| размер | число байт или строка с единицей | та же | `2097152`, `512MB`, `1GiB` |
| вещественное | YAML-число | число с точкой | `0.6` |
| список | YAML-список | элементы через запятую, пробелы по краям обрезаются | `www,admin` |

Длительность числом (`total_timeout: 20`) — ошибка: единица измерения
была бы двусмысленной. Размеры: десятичные единицы (`KB`, `MB`, `GB`) —
степени 10³, двоичные (`KiB`, `MiB`, `GiB`) — степени 2¹⁰.

Для `subdomains` пустой элемент списка — апекс домена: в YAML это `""`,
в переменной — пустой элемент между запятыми (`CRAWLER_SUBDOMAINS=",www"`
апекс не задаёт; задаёт `",www"`). Значение переменной заменяет список
из YAML целиком — не забудьте апекс, если он нужен.

## Разделы и переменные

### `postgres`

| YAML | Переменная | Тип | По умолчанию |
|---|---|---|---|
| `dsn` | `CRAWLER_POSTGRES_DSN` | строка | — (**обязателен**) |
| `pool_size` | `CRAWLER_POSTGRES_POOL_SIZE` | целое | `20` |

`pool_size` — лимит соединений **одного сервиса** (пул `internal/db`,
T-007); рекомендация ТЗ — суммарно 20–50 соединений на все сервисы, то есть
при восьми сервисах задавайте 4–6 на сервис. Соединения открываются лениво.
Подробнее: [`db.md`](db.md).

### `redis`

| YAML | Переменная | Тип | По умолчанию |
|---|---|---|---|
| `addr` | `CRAWLER_REDIS_ADDR` | host:port | `127.0.0.1:6379` |
| `maxlen` | `CRAWLER_REDIS_MAXLEN` | целое | `0` (пределы по стримам, см. ниже) |
| `max_attempts` | `CRAWLER_REDIS_MAX_ATTEMPTS` | целое | `3` (ТЗ 4.2) |
| `claim_min_idle` | `CRAWLER_REDIS_CLAIM_MIN_IDLE` | длительность | `5m` |

`maxlen` — явный предел длины всех стримов при публикации (`XADD MAXLEN ~`,
усечение приблизительное, без точного подсчёта). `0` — пределы по стримам из
политики надёжности очереди (T-025): `q:dns` 10 000 записей (пачки до
`scheduler.batch_size` доменов), `q:http`/`q:render`/`q:analyze` 1 000 000
(штучные задачи), `q:dead` 100 000. Пределы усекают прежде всего историю
подтверждённых записей и заведомо выше порога backpressure
(`scheduler.queue_high_watermark`): неусечённая необработанной запись не
теряется бесследно — задачи восстанавливает планировщик (источник истины
PostgreSQL, ТЗ 3.4). Явный предел — 1000..100000000.

`max_attempts` — максимальное число доставок задачи (первое чтение группы +
каждый возврат зависшей записи клеймом `XAUTOCLAIM`), после чего задача
публикуется в `q:dead` для ручного разбора; счётчик ведёт Redis в pending-списке
группы. Диапазон 1..100; 1..3 — минимум одна обработка до перевода в `q:dead`.

`claim_min_idle` — сколько зависшая (прочитанная и не подтверждённая) запись
должна простоять, чтобы её забрал возвращающий в работу `XAUTOCLAIM`; больше
худшего времени обработки задачи живым воркером, иначе чужая работа
перехватывается на ходу.

### `ingest` (ТЗ 5.1)

| YAML | Переменная | Тип | По умолчанию |
|---|---|---|---|
| `dir` | `CRAWLER_INGEST_DIR` | путь | `/data/incoming` |
| `batch_size` | `CRAWLER_INGEST_BATCH_SIZE` | целое | `50000` |
| `stable_seconds` | `CRAWLER_INGEST_STABLE_SECONDS` | секунды | `10` |
| `scan_interval` | `CRAWLER_INGEST_SCAN_INTERVAL` | длительность | `30s` |
| `max_error_ratio` | `CRAWLER_INGEST_MAX_ERROR_RATIO` | число | `0.1`, диапазон (0, 1] |

`dir` — наблюдаемая папка (создаётся при отсутствии). `stable_seconds` —
сколько размер и mtime файла должны быть неизменны, чтобы ingest взял его
в обработку (дозаписываемые и временные `*.tmp`/`*.part` файлы не
берутся). `scan_interval` — период полного обхода папки как страховки к
fsnotify (T-013): подхватывает файлы, существовавшие до старта сервиса, и
компенсирует потерянные события наблюдения.

`max_error_ratio` — порог доли отклонённых строк файла (T-016, ТЗ 5.1):
строка обязана быть полным именем домена из зоны пути; невалидные имена,
чужие зоны и слишком длинные строки отклоняются в лог `rejected` с
причиной и не роняют файл — ошибочным его делает только доля отказов
строго выше порога (по умолчанию 10%: единичный мусор прощается, файл не
в той зоне или битый дамп дают долю, близкую к 1).

### `scheduler` (ТЗ 5.3)

| YAML | Переменная | Тип | По умолчанию |
|---|---|---|---|
| `recheck_interval` | `CRAWLER_SCHEDULER_RECHECK_INTERVAL` | длительность | `4380h` (≈ 6 мес.) |
| `batch_size` | `CRAWLER_SCHEDULER_BATCH_SIZE` | целое | `5000` (ТЗ 5.3: 1000–10000) |
| `queue_high_watermark` | `CRAWLER_SCHEDULER_QUEUE_HIGH_WATERMARK` | целое | `100000` (backpressure, ТЗ 4.2) |
| `lease` | `CRAWLER_SCHEDULER_LEASE` | длительность | `30m` |
| `temp_error_retry_after` | `CRAWLER_SCHEDULER_TEMP_ERROR_RETRY_AFTER` | длительность | `24h` |
| `temp_error_max_retries` | `CRAWLER_SCHEDULER_TEMP_ERROR_MAX_RETRIES` | целое | `3` (максимум повторов `temp_error` подряд, далее итоговый статус; ТЗ 5.3: N) |

`recheck_interval` — минимальный возраст последней проверки
(`domains.last_checked_at`, ТЗ 3.3), после которого домен снова ставится в
очередь: суточный проход планировщика переводит его `check_state` из
`done` в `pending` (ТЗ 5.3; повторная проверка — не чаще этого интервала,
ТЗ 11.4 п. 8). Сам суточный ритм прохода конфигом не настраивается.

`queue_high_watermark` — порог backpressure (ТЗ 4.2, 5.3): единый для всех
рабочих стримов (`q:dns`, `q:http`, `q:render`, `q:analyze`). Продюсер —
планировщик для `q:dns` (T-028) и воркеры для остальных стримов —
публикует только когда длина стрима ниже порога; при достижении порога —
пауза (1 с между проверками) и повтор, отмена контекста — чистый выход.
Длина — XLEN, все записи стрима, включая доставленные и не подтверждённые
XACK: записи не исчезают до обрезки `MAXLEN ~` (T-025), поэтому порог —
мягкое регулирование темпа (жёсткий потолок — MAXLEN). `q:dead` не
ограничивается: перенос исчерпавших попытки задач не должен блокироваться
переполнением. Порог остаётся в секции `scheduler` по месту из ТЗ 5.10
(фиксированный состав секций), хотя применяется ко всем стримам.

`lease` — срок аренды: домен в `check_state = queued` без результата
(`queued_at` старше `lease`) возвращается фоновым проходом планировщика в
`pending` для повторной постановки (ТЗ 5.3: «зависшие» задачи — гибель
воркера, потеря Redis). Проход проверяет истечение дважды за срок
(интервал `lease`/2), поэтому домен возвращается не позднее чем через
полтора срока после постановки. Удалённые домены (`status = deleted`) не
возвращаются — они исключены из цикла проверок (ТЗ 13.1).

### `dns` (ТЗ 5.4)

| YAML | Переменная | Тип | По умолчанию |
|---|---|---|---|
| `resolvers` | `CRAWLER_DNS_RESOLVERS` | список host:port | `127.0.0.1:53` (unbound) |
| `fallback_resolvers` | `CRAWLER_DNS_FALLBACK_RESOLVERS` | список host:port | `1.1.1.1:53, 9.9.9.9:53` |
| `concurrency` | `CRAWLER_DNS_CONCURRENCY` | целое | `2000` |
| `max_qps` | `CRAWLER_DNS_MAX_QPS` | целое | `10000` |
| `ipv6` | `CRAWLER_DNS_IPV6` | булево | `true` (`false` — AAAA не запрашиваются) |
| `timeout` | `CRAWLER_DNS_TIMEOUT` | длительность | `2s` |
| `tcp_timeout` | `CRAWLER_DNS_TCP_TIMEOUT` | длительность | `5s` |
| `retries` | `CRAWLER_DNS_RETRIES` | целое | `2` (диапазон 1..10) |
| `retry_delay` | `CRAWLER_DNS_RETRY_DELAY` | длительность | `200ms` |
| `udp_pool_size` | `CRAWLER_DNS_UDP_POOL_SIZE` | целое | `2000` |

`timeout`/`tcp_timeout`/`retries`/`retry_delay`/`udp_pool_size` — параметры
транспорта `internal/dnsclient` (T-034, ТЗ 5.4): `timeout` — одна
UDP-попытка обмена с резолвером; `tcp_timeout` — повтор того же вопроса
по TCP, когда ответ пришёл с флагом усечения (TC=1); `retries` — повторы
сверх первой попытки при таймауте/ошибке сети (после исчерпания
потребитель этапа фиксирует temp_error, ТЗ 5.4 п. 1); `udp_pool_size` —
пул заранее открытых подключённых UDP-сокетов к первому резолверу из
`resolvers`; по умолчанию равен `concurrency`, чтобы пул не ограничивал
плановый параллелизм.

`concurrency`/`max_qps`/`ipv6` применяет декоратор лимитов
`dnsclient.LimitResolver` (T-035, ТЗ 5.4: «ограничение параллелизма и QPS
настраивается; адаптивное снижение при росте доли таймаутов»; ТЗ 5.10):
`concurrency` — потолок одновременных обменов, `max_qps` — средний темп
(токен-ведро со всплесками до `concurrency` обменов подряд). Адаптив:
при доле таймаутов ≥ 10 % в окне последних 200 обменов оба лимита
снижаются ×0.5 (до пола base/100, но не меньше 1), при доле ≤ 2 % —
восстанавливаются ×1.25 до настроенных значений; между порогами — зона
нечувствительности. Пороги/факторы — константы `internal/dnsclient`
(дефолты выведены из свойств этапа, ТЗ числами не задаёт), снимок текущих
лимитов и счётчики — `LimitResolver.Stats()` для мониторинга (T-077).

`ipv6: false` («если на сервере нет IPv6 — AAAA-запросы отключаются
конфигом», ТЗ 5.4) — AAAA-вопросы лимитёр отвечает локально пустым
NOERROR (NODATA) без похода к резолверу и без траты лимитов: краулер без
IPv6 не проверяет AAAA-адреса и по HTTP, трафик к резолверу ниже.

`fallback_resolvers` (ТЗ 5.4: «публичные резолверы — только как fallback»)
потребляется DNS-клиентом воркера: при SERVFAIL/таймауте локального unbound
из `resolvers` запрос повторяется напрямую в резервный резолвер. Сам unbound
остаётся чисто рекурсивным: семантика `forward-zone` в unbound делает
форвардеры первичными, направления «рекурсия → форвардер» не существует
(подробнее — [`docker.md`](docker.md), раздел «Unbound»). Дефолты —
общедоступные anycast-резолверы двух независимых операторов (Cloudflare,
Quad9), как в ТЗ 5.10.

|---|---|---|---|

| `pack_size` | `CRAWLER_CONTENT_PACK_SIZE` | размер | `512MB` (рекомендация: 512 МБ–1 ГБ) |

(dev-окружение — `docs/dev-environment.md` §6); отсутствующий файл — не

словарь по идентификатору в заголовке кадра, поэтому старые записи читаются
своим (прежним) словарём, пока он зарегистрирован.

файл блокировки `.packs.lock`, словарь): формат, ротация по `pack_size` и
метаданные `contents` — [`docs/content.md`](content.md).

## Валидация

Проверяется всё сразу, ошибка перечисляет проблемы вида `секция.поле: что не так`:

- `postgres.dsn` непуст; `pool_size` 1..100;
- `redis.addr`, `dns.resolvers`, `dns.fallback_resolvers`, `monitor.listen` —
  корректные `host:port` (порт 1..65535); резолверы — хотя бы один;
  `redis.maxlen` — 0 или 1000..100000000, `redis.max_attempts` 1..100,
  `redis.claim_min_idle` положительна;
- все таймауты/интервалы положительны; `ingest.batch_size` 1..1000000,
  `ingest.stable_seconds` 1..3600, `ingest.scan_interval` 10ms..1h,
  `scheduler.batch_size` 1000..10000 (ТЗ 5.3), `queue_high_watermark` ≥ 1,
  `temp_error_max_retries` 1..100;
- `dns.concurrency`/`http.concurrency` 1..100000, `dns.max_qps` 1..1000000,
  `http.per_ip_limit` 1..64, `http.max_redirects` 0..100, `max_body_bytes` > 0;
- `dns.timeout`/`dns.tcp_timeout`/`dns.retry_delay` положительны,
  `dns.retries` 1..10 (ТЗ 5.4: ретраи обязательны), `dns.udp_pool_size`
  1..100000;
- `http.user_agent` непуст;
- `render.contexts` 1..16, `restart_every_pages` 1..1000000,
  `remote_url` (если задан) — корректный URL;
- `content.pack_size` 1 MiB..8 GiB, `max_store_bytes` 1 байт..16 MiB;
- `analyzer.laravel_min_score` в (0, 1];
- `ingest.max_error_ratio` в (0, 1];
- `subdomains`: 1..63 записи, метки в нижнем регистре без точек, без повторов;
- пути (`ingest.dir`, `content.dir`, `analyzer.rules_dir`) непустые;
- `log.level` — одно из `debug`/`info`/`warn`/`error`.

## Устаревшие переменные (обратная совместимость)

| Переменная | Действие |
|---|---|
| `APP_PG_DSN` | переопределяет `postgres.dsn`, если не задана `CRAWLER_POSTGRES_DSN`; используется `deploy/docker/compose.yaml` и Makefile |
| `APP_CONFIG` | запасное имя переменной пути к файлу конфигурации |
| `METRICS_ADDR` | адрес healthz/metrics конкретного сервиса; для `monitor` значение по умолчанию — `monitor.listen` из конфигурации, для остальных — фиксированные порты dev-каркаса (`:9101`…`:9106`) |

Новые имена (`CRAWLER_*`) всегда важнее устаревших. Дополнять стоит только
ими; устаревшие поддерживаются, пока на них ссылается dev-окружение.

## Dev-окружение (Docker)

- [`deploy/docker/config.dev.yaml`](../deploy/docker/config.dev.yaml)
  монтируется в контейнеры как `/etc/crawler/config.yaml`; путь задаётся
  переменной `CRAWLER_CONFIG` (общий блок `x-go-common-env` в compose).
- DSN поверх YAML даёт `APP_PG_DSN` (собирается в compose из `.env`).
- `User-Agent` dev-краулера: `CRAWLER_USER_AGENT` из `.env` → переменная
  `CRAWLER_HTTP_USER_AGENT` в контейнерах (обязательная пометка dev).
- В docker-сети нет IPv6: в dev-конфиге `dns.ipv6: false`; fallback-резолверы
  пусты — окружение изолировано от интернета (см.
  [`dev-environment.md`](dev-environment.md), режим internet).

## Интеграция в код

- `config.Load()` — путь из `CRAWLER_CONFIG`/`APP_CONFIG` (или автопоиск
  `./config.yaml`), наложение окружения, валидация; вызывается в `main`
  каждого сервиса.
- `config.LoadFile(path)` — явный файл + окружение процесса.
- `config.LoadEnv(getenv)` — то же с инъекцией окружения (тесты).
- `config.Default()` — значения по умолчанию из ТЗ 5.10.
- `service.Options.Config` — загруженный конфиг передаётся в каркас
  (`internal/service`); DSN для миграций берётся из него (или из прямого
  `Options.PGDSN`), `log.level` — для логгера каркаса
  (`service.NewLogger`; сам `Run` тоже создаёт логгер, если `Options.Logger`
  не задан, и делает его дефолтным `slog.SetDefault`).
- `db.NewOptions(cfg.Postgres)` — секция `postgres` → параметры пула
  `internal/db` (`db.Open`; см. [`db.md`](db.md)).

Таблица привязок «переменная → поле» — `envSpecs()` в
`internal/config/load.go`; тесты: `internal/config/config_test.go`
(дефолты, YAML, окружение, приоритеты, валидация) и
`test/integration/config_test.go` (dev-окружение целиком).
