# Входные файлы доменов: контракт (ТЗ 5.1–5.2)

Единое описание входящих файлов для оператора и интеграций: структура
наблюдаемой папки, формат файла, правила валидации строк, отчёты и
жизненный цикл. Реализация — конвейер `internal/ingest` (T-013…T-023);
параметры — секция `ingest` конфигурации
([`configuration.md`](configuration.md)).

## 1. Структура наблюдаемой папки

```
<ingest.dir>/
  <зона>/                  — файлы одной зоны (зона задаётся каталогом)
    add/       *.txt, архивы §9 — добавить или обновить домены
    delete/    *.txt, архивы §9 — удалить домены (из зарегистрированных ранее)
  add/         *.txt, архивы §9 — зона-less файл: домены любых зон
  delete/                   в одном файле, зона выводится из имени
  processed/            — архив успешно обработанных файлов
  failed/               — ошибочные файлы с лог-отчётом *.report рядом
```

- Каталог — `ingest.dir` (по умолчанию `/data/incoming`;
  dev-окружение — `var/incoming/` в корне репозитория, бой —
  `/var/lib/crawler/incoming`, права — [`deploy.md`](deploy.md) §3–4).
  Отсутствующий каталог создаётся сервисом при старте.
- **Зона-less файл** (`add/<файл>` без каталога зоны) может смешивать
  зоны: зона каждой строки выводится из самого домена по списку
  publicsuffix (`internal/idn`, ТЗ 5.2 п. 5); зоны создаются
  автоматически по первым строкам файла. Удобно для списков «как есть»
  (ручная проверка, выгрузки без разбивки). Нюанс: тестовые зоны PSL не
  знает — `example.crawl.test` попадёт в зону `test` с составной меткой;
  для testbed-доменов пользуйтесь каталогом зоны (`crawl.test/add/…`).
  Так же доставляется ежесуточный NRD-фид smet.cz — автоматически, cron-
  выгрузкой в `add/` ([`deploy/nrd/`](../deploy/nrd/),
  [`deploy.md`](deploy.md) §4.9).
- **Зона** — имя каталога: TLD или публичный суффикс (`com`, `co.uk`),
  допускается unicode или punycode (`москва` и `xn--80adxhks` — одна зона,
  дублей в справочнике не будет). Составные зоны (`co.uk`) разрешены.
  Новая зона создаётся в `zones` автоматически при первом файле
  (`is_active = true`); имя хранится в punycode, unicode-форма — только
  для отображения.
- **Операция** — строго каталог `add` или `delete` в нижнем регистре;
  лишняя вложенность (`<зона>/add/sub/x.txt`, `add/sub/x.txt`) — ошибка
  структуры пути.
- Расширение — `*.txt` или архив поддерживаемого формата (§9), без учёта
  регистра (`.TXT` берётся); каталоги `processed/` и `failed/` наблюдением
  не сканируются.

## 2. Формат файла

| Что | Правило |
|---|---|
| Кодировка | UTF-8; строка с невалидным UTF-8 отклоняется (`invalid_utf8`), разбор продолжается |
| Строка | **полное имя домена** (`example.com`) в любой форме: регистр, краевые пробелы, завершающая точка, unicode/punycode — нормализуются (ТЗ 5.2, `internal/idn`); либо произвольная запись, среди посторонних данных которой домен извлекается (T-132 — см. ниже) |
| Концы строк | `\n`, `\r\n`, `\r` — смешивание в одном файле допустимо |
| Пустые строки | пропускаются (не отклонение) |
| Комментарии | строка, первый значимый символ которой `#` (после краевых пробелов), — пропускается |
| BOM | в начале файла снимается; в середине остаётся в данных и убирается нормализацией имени |
| Длина строки | до 1024 байт; длиннее — построчное отклонение `line_len` |
| Размер файла | не ограничен: разбор потоковый, память не зависит от размера; загрузка в БД пачками по `ingest.batch_size` (50000) |

### Извлечение домена из произвольной строки (T-132)

Реальные выгрузки регистраторов несут в строке посторонние данные:
`xxx.com 2029-11-11 TIMEWEB`, CSV, URL. Строка **без разделителей**
(пробельные символы, запятая, точка с запятой) и без явной схемы
`http(s)://` — по-прежнему одно полное имя домена: она валидируется
прежними правилами (§3), причины отклонений одиночных строк не
изменились. Иначе строка разбирается на токены:

- разделители — пробельные символы (`unicode.IsSpace`), `,`, `;`;
- с краёв токена снимаются кавычки и пунктуация: `"xxx.com",` →
  `xxx.com`;
- токен с явной схемой `http(s)://` (регистр не важен) заменяется
  хостом из `net/url` — порт и путь срезаются: `https://xxx.com/page` →
  `xxx.com`; другие схемы (`ftp://…`) не заменяются;
- кандидаты — токены, содержащие ASCII-точку `.`: даты `2029-11-11` и
  слова без точек кандидатами не являются. Идиографические точки
  (`。`/`．`) нормализация понимает в одиночных строках; в смешанных
  кандидатом делает только ASCII-точка — известное ограничение;
- кандидаты просматриваются слева направо через полную валидацию
  (нормализация ТЗ 5.2 + сверка зоны пути): первый прошедший становится
  записью строки; если очередной валидный кандидат оказался из чужой
  зоны — берётся следующий (`yyy.org xxx.com` в каталоге зоны `com` →
  `xxx.com`);
- ни один не прошёл — отклонение `no_domain` (§3) в лог `rejected` и
  разрез причин отчёта.

Следствие: пробел внутри строки теперь — разделитель полей. Опечатки
вида «при мер.рф» больше не склеиваются в одно имя: из такой строки
извлекается токен с точкой (`мер.рф`). Нормализация имён
(ТЗ 5.2 пп. 1–6) не менялась — извлечение лишь выбирает, какой токен
строки идёт в конвейер. Конфигурационного флага нет: старый формат —
подмножество нового, приём только расширяется; лимит строки (1024
байта) прежний — строки дампов коротки.

**Готовность файла.** Обрабатывается только файл, запись которого
завершена: размер и mtime стабильны `ingest.stable_seconds` секунд
(по умолчанию 10), плюс периодический полный обход папки раз в
`ingest.scan_interval` (страховка к fsnotify, подхватывает файлы,
существовавшие до старта). Правильный способ доставки — записать под
временным именем (`*.tmp`, `*.part` — наблюдатель их игнорирует) и
переименовать в `*.txt`.

## 3. Валидация строк и причины отклонений

Строка (для смешанных строк — извлечённый токен-кандидат, T-132, §2)
обязана быть полным именем домена из зоны, указанной в пути файла.
Нормализация по ТЗ 5.2: нижний регистр, снятие пробелов и завершающей
точки, punycode (профиль UTS-46 Lookup, некорректные `xn--`-метки
отклоняются), контроль длин (метка ≤ 63, имя ≤ 253 октета),
отделение зоны по списку публичных суффиксов. Суффикс из одних цифр
зоной быть не может — таких TLD не существует, даты выгрузок и
IPv4-литералы отклоняются (`numeric_zone`). У зона-less файла
(`add/<файл>`) зона строки и есть отделённый публичный суффикс — сверка
с зоной пути не выполняется, `wrong_zone` невозможна.

Отклонённые строки **не роняют файл**: пишутся в лог `rejected`
(записи с атрибутом `service=rejected` в stderr сервиса ingest: файл,
номер строки, обрезанная строка, причина) и в счётчики отчёта.

| Причина | Смысл | Пример |
|---|---|---|
| `invalid_utf8` | строка не UTF-8 | байты `\xff\xfe` |
| `line_len` | строка длиннее 1024 байт | мусорная строка |
| `empty` | после нормализации имя пусто | строка из одной точки |
| `invalid` | невалидное имя / битый punycode | `ex_ample.com`, `xn--e` |
| `label_len` | метка длиннее 63 октетов | 64-символьная метка |
| `name_len` | полное имя длиннее 253 октетов | цепочка меток |
| `no_label` | нет метки домена | голая зона `com` |
| `numeric_zone` | публичный суффикс имени состоит только из цифр — числовых TLD не существует | дата выгрузки `18.06.1999`, IPv4-литерал `1.2.3.4` |
| `wrong_zone` | домен не из зоны пути (только файлы с каталогом зоны) | `example.com` в файле `ru/add/`; `example.co.uk` при зоне `uk` (вложенная публичная зона) |
| `no_domain` | в строке с посторонними данными (T-132) не найден домен: кандидатов нет или ни один не прошёл валидацию | `2029-11-11 TIMEWEB`; `yyy.org регистратор` в файле `com/add/` |

Дубликаты внутри файла (включая unicode/punycode формы одного IDN-имени)
не отклоняются — дедуплицирует БД по уникальному ключу `(zone_id, label)`.

## 4. Порог доли ошибок

`ingest.max_error_ratio` (по умолчанию 0.1) — доля отклонённых строк,
выше которой файл считается ошибочным **целиком** (ни одна строка не
применяется):

- доля отказов **строго выше** порога → файл ошибочен → `failed/`;
- равна порогу и ниже — файл применяется, отклонённые строки видны в
  отчёте и логе `rejected`.

Смысл (ТЗ 5.1): единичный мусор файлу не вредит, а «файл не в той зоне»
или битый дамп дают долю, близкую к 1, и попадают в `failed/`.

## 5. Жизненный цикл файла

| Итог | Куда | Что остаётся |
|---|---|---|
| применён | `processed/<зона>/<операция>/…` | строка `ingest_files` (sha256, счётчики) |
| дубль — точная повторная доставка (та же зона + то же действие + тот же sha256) | `processed/…` | без нового отчёта — повторная обработка не выполняется |
| ошибочен (структура пути, зона, доля отказов выше порога) | `failed/…` | лог-отчёт `<файл>.report` рядом; записи в `ingest_files` нет — исправленный файл можно положить снова |
| сбой инфраструктуры (БД, чтение) | остаётся в `incoming/` | переработается после рестарта/очередного обхода (at-least-once, ТЗ 3.4) |

Структура зоны/операции в архиве сохраняется; коллизия имени в архиве
разрешается суффиксом `-2`, `-3`… Дедуп — по содержимому (sha256), а не
по имени файла: изменённый файл по тому же пути обрабатывается заново.
Дубль при этом — только **точная повторная доставка**: совпадение зоны,
действия и sha256 (уникальный ключ `ingest_files (zone_id, action,
sha256)`, T-113). То же содержимое **другим действием** (undo: тот же
список из `delete/` после `add/`) и **в другой зоне** обрабатывается
заново — см. §6. Дедуп файла — оптимизация; корректность повторной
доставки гарантируют операции над доменами (§6, «Идемпотентность
повторной доставки»).

**Аварийная смерть сервиса.** Обработка, прерванная `kill -9` или
падением СУБД, оставляет партию файла в staging-таблице `ingest_stage`
осиротевшей: её `batch_id` больше не встретится (повторная обработка
берёт свежий), а UNLOGGED-таблица переживает рестарт сервиса (усекается
только аварийным восстановлением PostgreSQL — crash recovery; штатный
рестарт СУБД строки сохраняет). Такие партии удаляет тот же фоновый
цикл очистки, что и результаты удалённых доменов (проход раз в
минуту): строки партий старше суток чистятся диапазоном по `batch_id`
— время создания зашито в старшие байты идентификатора, отдельной
колонки времени в staging нет — с записью Warn в лог сервиса. Порог
заведомо больше времени обработки любого реального файла (файлы
обрабатываются по одному, пачки COPY дают ~10⁵–10⁶ строк/с), поэтому
партия идущей обработки не задевается. Граница контракта — системные
часы (возраст партий — wall time): синхронизация времени узлов
обязательна (NTP/chrony в режиме slew); скачок часов вперёд больше
порога в момент живой обработки — вне контракта.

## 6. Семантика add и delete

**add** (`INSERT … ON CONFLICT DO NOTHING` + возврат удалённых):

- новый домен вставляется (`status = new`, `check_state = pending`);
- существующий живой домен **не меняется** вовсе (результаты, флаги,
  сроки сохраняются);
- домен в статусе `deleted` возвращается в оборот: `new`/`pending`,
  `queued_at` сбрасывается (счётчик «возвращено» — в лог-отчёте, входит
  в «добавлено»).

**delete**:

- домен переводится в `status = deleted` и **остаётся в БД** (ТЗ 13.1);
  результаты и контент вычищает фоновая очистка (проход раз в минуту
  пачками до 1000 доменов, T-020);
- строки без домена в БД — «не найдено» в лог-отчёте (колонки в
  `ingest_files` для этого нет);
- удалённые домены не проверяются и не выбираются планировщиком;
  повторный delete-файл — no-op.

### Идемпотентность повторной доставки (T-097)

Повторная доставка файла безопасна на двух уровнях:

- **уровень файла (оптимизация)** — уникальная тройка (зона, действие,
  `sha256`) в `ingest_files` (T-113): точная повторная доставка не
  применяется повторно, файл просто уходит в `processed/` без второй
  записи журнала; то же содержимое другим действием или в другой зоне
  обрабатывается заново (см. «Контракт дедупа» ниже);
- **уровень доменов (корректность)** — даже если то же содержимое снова
  дойдёт до применения (сбой после применения до записи отчёта, потеря
  строки журнала, тот же список в другом файле), операции над доменами
  сходятся к тому же состоянию БД:

| Путь повторного применения | Гарантия |
|---|---|
| `add` существующего живого домена | no-op: `INSERT … ON CONFLICT DO NOTHING` по уникальному `(zone_id, label)`; статус, флаги, результаты и сроки не меняются |
| `add` домена в статусе `deleted` | возврат в оборот (`new`/`pending`, lease сброшен); повторный `add` уже возвращённого — no-op (охрана `status = deleted`) |
| `delete` отсутствующего домена | no-op, строка попадает в «не найдено» |
| `delete` уже удалённого | остаётся `deleted`, счётчик «удалено» стабилен |
| загрузка файла | свежий `batch_id` на попытку: строки прерванной партии в `ingest_stage` никогда не применяются повторно, применённая партия покидает staging |
| гибель сервиса при обработке (`kill -9`, падение БД) | файл остаётся в `incoming/`, партия в `ingest_stage` осиротевшая — удаляется фоновой зачисткой по возрасту `batch_id` (T-098); повторная обработка берёт свежий идентификатор |
| фоновая очистка | вычищенные домены не выбираются повторно; `contents.refcount` уменьшается строго по фактически удалённым ссылкам |

Итог: **тот же файл, обработанный дважды, не меняет состояние доменов**
(закреплено юнит- и интеграционными тестами идемпотентности, T-097).
Счётчики отчёта при этом отражают последнюю попытку («уже было» вместо
«добавлено») — на состояние БД это не влияет.

### Контракт дедупа (T-113)

Точная повторная доставка = совпадение **зоны, действия и sha256**
(уникальный ключ `ingest_files (zone_id, action, sha256)`, миграция
000009) — только она пропускается как дубль. Отсюда два штатных
сценария обработки того же содержимого заново:

- **undo тем же списком** — файл из `add/`, затем тот же список в
  `delete/`: действие другое, дубля нет, домены удаляются (в журнале —
  вторая строка);
- **повторная доставка в другой зоне** — домены той зоны первая доставка
  не трогала (строки файла обязаны принадлежать зоне пути, §3),
  обработка легитимна; оператору подсвечивается Warn в логе сервиса
  (полезно видеть повторное использование одного списка).

Более раннее ограничение — глобальный дедуп по одному `sha256`,
пропускавший оба сценария, — снято T-113 (продуктовое решение
2026-10-18); безвредность повторного применения гарантирует уровень
доменов выше (T-097, `TestIngest_ReapplySameFileConverges`).

### Операторский сценарий: undo добавления тем же списком

Ошибочно доставленный список отменяется его повторной доставкой в
`delete/` — байт-в-байт:

```
var/incoming/crawl.test/add/2026-10-18.txt      # доставили
example.crawl.test
shop.crawl.test

var/incoming/crawl.test/delete/2026-10-18.txt   # тот же список — undo
example.crawl.test
shop.crawl.test
```

Совпадение зоны и `sha256` при другом действии — не дубль: файл
применяется, домены списка переходят в `deleted` (остаются в БД,
ТЗ 13.1), журнал пополняется второй строкой. Готовить отдельный
«правильный» файл для отмены не нужно — и не следует: точная копия
гарантирует, что отменяется ровно тот список, который был доставлен.
Конвейер подсвечивает повторное использование содержимого записью Info
«то же содержимое уже доставлялось другим действием — обрабатывается
(undo)» с путём первой доставки. Обратное направление работает так же:
возврат удалённого домена допускает тот же список из `delete/` в
`add/`. Точная повторная доставка — совпадение зоны, действия и
содержимого (`sha256`) — по-прежнему дубль и не применяется.

## 7. Отчёты

**Журнал `ingest_files`** (SQL, `make psql`): зона, действие, путь,
`sha256`, счётчики `lines_total / added / existed / deleted / rejected`,
время обработки.

**Лог-отчёт `failed/<файл>.report`** — текст рядом с ошибочным файлом:

```
# лог-отчёт ingest (ТЗ 5.1)
файл: /var/lib/crawler/incoming/ru/add/dump.txt
зона: ru (id 42)
действие: add
sha256: …
итог: ошибочен — доля отклонённых строк 620 из 1000 выше ingest.max_error_ratio (0.1)
строк: 1000
  пропущено (пустые и комментарии): 12
  отклонено: 620
    wrong_zone: 611
    invalid: 9
  валидных: 368
```

Тот же текст — основа записей лога сервиса ingest об обработке файла.

**Лог `rejected`** — поток построчных отклонений в stderr сервиса
(атрибут `service=rejected`): номер строки, обрезанная до 255 рун строка,
причина.

## 8. Пример

```
var/incoming/crawl.test/add/2026-10-18.txt     # зона создастся автоматически

# свежие домены (посторонние данные в строке снимает извлечение, T-132)
example.crawl.test
пример.crawl.test          # IDN: нормализуется в xn--e1afmkfd.crawl.test
www2.example.crawl.test    # ок: составные метки допустимы (контракт idn)

# шум — одиночные строки, прежние причины (не роняют файл при доле ≤ 10%)
example.com
под_чёркивание.crawl.test
```

Первый блок — смешанные строки: извлечение берёт первого прошедшего
кандидата (инлайн-комментарий после домена не мешает — это просто
следующие токены строки). Второй блок — одиночные строки прежним путём:
`example.com` → `wrong_zone` (не из зоны `crawl.test`),
`под_чёркивание.crawl.test` → `invalid`.

После обработки: файл в `var/incoming/processed/crawl.test/add/`,
домены в БД (метка punycode, бит `is_idn` у IDN), строка в
`ingest_files`, зона `crawl.test` видна в `crawlerctl zones list`.

## 9. Архивы (.zip, .tar, .tar.gz, .tgz, .gz)

Реальные выгрузки регистраторов и публичные дампы зон приходят
запакованными. Кроме `*.txt` каталог `<зона>/add|delete/` принимает
архивы: `.zip`, `.tar`, `.tar.gz`, `.tgz`, `.gz` (без учёта регистра).
Форматы — stdlib Go; `rar`/`7z` **не поддерживаются** (рассматривались и
отклонены: не stdlib) — такие файлы наблюдатель не выдаёт, приём
разбирает только выданное.

- **Готовность** — та же, что у txt (§2): стабильность размера/mtime
  `ingest.stable_seconds`, доставка под временным именем (`*.tmp`,
  `*.part`) и переименование.
- **Обработка потоковая** (ТЗ 3.5): члены не материализуются на диск,
  каждый читается как поток и проходит обычный конвейер §2–§3 — тот же
  формат строки, та же нормализация (ТЗ 5.2), те же причины отклонений.
  Память — как у txt-файла: окно парсера плюс пачка COPY.
- **Зона и действие — только из каталога архива**
  (`com/add/x.zip` → зона `com`, действие `add`). Внутренние пути членов
  на зону **не влияют**: члены — списки доменов зоны каталога;
  самостоятельный выбор зоны из пути члена небезопасен (член `ru/list.txt`
  в архиве `com/add/x.zip` — это список доменов зоны `com`, а не `ru`).
  Внутренний путь используется только в адресации отклонений.
- **Пропускаются с Warn** в лог сервиса: каталоги, скрытые файлы и
  каталоги (компонент пути начинается с точки — включая мусор macOS
  `._*`, `.DS_Store` и скрытые деревья целиком), ресурсный каталог
  `__MACOSX` и его содержимое. Пропущенные записи не роняют архив.
- **Вложенные архивы не распаковываются** — один уровень: член-архив
  читается как текст, бинарный мусор даёт долю ошибок выше порога —
  архив целиком в `failed/`.
- `.gz` — **один член** с именем архива без расширения (`zone.gz` →
  член `zone`); многосегментный gzip (склейка потоков) читается одним
  членом. `.tar.gz`/`.tgz` — gzip поверх tar.

### Единица учёта и отчёт

Единица учёта — **архив**: одна строка `ingest_files` — `sha256` байтов
архива (сжатая форма файла), `lines_total / added / existed / deleted /
rejected` — суммы по членам, зона и действие — из каталога. Отклонённые
строки адресуются «архив!член:строка» — в логе `rejected` атрибут `file`
для строки 42 члена `ru/list.txt` архива `com/add/x.zip` равен
`com/add/x.zip!ru/list.txt` с `line=42`; лог-отчёт рядом с ошибочным
архивом дополнительно показывает число членов. Идемпотентность — та же,
что у txt (§5–§6): точная повторная доставка архива — дубль (обработка
не повторяется), повторная подача после сбоя сходится к тому же
состоянию доменов (`ON CONFLICT DO NOTHING`, ТЗ 5.1).

### Лимиты и вердикт

| Параметр | Смысл | По умолчанию |
|---|---|---|
| `ingest.archive_max_uncompressed` | суммарный несжатый объём потока (у zip — членов) | `8GiB` |
| `ingest.archive_max_files` | число записей архива (включая каталоги и мусор) | `1000` |

Архив попадает **целиком** в `failed/` с лог-отчётом рядом, а его партия
отбрасывается (строки не применяются), если:

- доля отклонённых строк **любого члена** выше `ingest.max_error_ratio`
  (порог действует на член — как txt-файл; причина в отчёте адресует
  член);
- архив **битый**: не читается (мусорные байты, пустой `.gz`) или
  повреждён при чтении (обрезанное тело, битый CRC/заголовок tar);
- превышен любой из лимитов: для zip несжатый объём проверяется **до
  чтения члена** по заголовку `UncompressedSize64`, для tar/gz —
  счётчиком по всему распакованному потоку (заголовки tar и содержимое
  членов); фактическое чтение zip тоже считается — заголовок может
  лгать. Число записей: у zip — по центральному каталогу до чтения
  членов, у tar — каждый заголовок, включая каталоги и пропускаемый
  мусор (бомба метаданными — тысячи пустых каталогов — сжимается на
  порядки и ловится обоими лимитами). Расходы на сам центральный
  каталог zip ограничены размером входного файла (incoming — зона
  ответственности оператора, ТЗ 5.1), лимит ограничивает последующую
  обработку.

Сбой инфраструктуры (БД, диск) архив не роняет: он остаётся в
`incoming/` и переработается (at-least-once, ТЗ 3.4); строки, успевшие
примениться до сбоя, безвредны для повторной подачи (§6).

Тонкость полноты чтения: tar-поток завершается нулевыми блоками и
паддингом (GNU tar дополняет до 10 КиБ), gzip проверяет CRC только по
трейлеру — конвейер дочитывает остаток потока после последнего члена,
поэтому `sha256` в `ingest_files` равен `sha256sum` файла целиком, а
битый трейлер ловится (байты после gzip-потока, не образующие корректную
склейку потоков, тоже считаются повреждением). Ошибочные архивы
дочитываются не полностью — хэш в их лог-отчёте не печатается. Пустой
(без записей) tar/zip — корректный пустой архив (применяется пустой
партией, как пустой txt); файл нулевой длины — битый архив любого
формата (у zip/gz нет корректного контейнера).

### Пример

```
var/incoming/com/add/2026-10-19.zip     # зона создастся автоматически

  sub/one.txt        # внутренние пути произвольны — зона не из них
    example.com
  ru/two.txt         # имя каталога члена — НЕ зона: строки обязаны быть com
    shop.com
  __MACOSX/junk      # пропущено с Warn
```

После обработки: архив целиком в `var/incoming/processed/com/add/`,
домены обоих членов в БД, одна строка `ingest_files` с суммами по членам.
