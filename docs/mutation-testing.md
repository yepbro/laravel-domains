# Мутационное тестирование

Мутационное тестирование проверяет **качество тестов**, а не кода: в
исходник по одному вносятся мелкие ошибки (мутации — инвертированные
условия, вырезанные ветки, изменённые операторы и константы), и после
каждой запускаются тесты пакета. Мутант, который тесты **не заметили**
(«выжил»), — участок кода, не зафиксированный утверждениями. Доля убитых
мутантов — mutation score — метрика строгости тестовой suite.

В проекте это вспомогательная, тяжёлая проверка: в CI каждого пуша она
не входит, гоняется еженедельным workflow и вручную.

## 1. Инструмент

[`go-mutesting`](https://github.com/zimmski/go-mutesting) в живом форке
[avito-tech/go-mutesting](https://github.com/avito-tech/go-mutesting):
апстрим zimmski не обновлялся с 2021 и паникует в `go/types` под
современными тулчейнами; форк — тот же инструмент (те же мутаторы и
встроенный exec через `go test`), дополненный конфигом YAML, аннотациями
отключения мутаций, JSON/HTML-отчётами и набором мутаторов
(arithmetic/loop/numbers поверх branch/expression/statement).

Версия пинится в `.env` (`GO_MUTESTING_VERSION`, ставится в dev-образ
`deploy/docker/Dockerfile.go`); выбранная ревизия — последняя, не
требующая тулчейн новыше проектного (`go 1.25.5` при проектном Go
1.26.x: `go install` не тянет лишний toolchain).

## 2. Запуск

```bash
make mutate                                    # охват по умолчанию
make mutate PKGS='./internal/httpfetch/...'    # точечный пакет
make mutate PKGS='./internal/queue/... ./internal/idn/...'
make mutate MUTATION_MIN_SCORE=0.7             # упасть, если score < 0.7
make mutate MUTATE_TIMEOUT=120                 # таймаут go test на мутанта, с
```

Всё выполняется в контейнере `tools` (как `make test`); Go на хосте не
нужен. Переменные:

| Переменная | Значение | По умолчанию |
|---|---|---|
| `PKGS` | охват — локальные `./`-шаблоны пакетов через пробел | «логическое ядро», см. ниже |
| `MUTATION_MIN_SCORE` | порог score 0..1, ниже — exit 1 | `0` (только отчёт) |
| `MUTATE_TIMEOUT` | таймаут `go test` на одного мутанта, с | `60` |

Важно: `go-mutesting` резолвит цели GOPATH-эрой логикой — шаблоны
обязательно локальные (`./internal/...`), импортные пути модуля
(`crawler/internal/...`) не работают.

- тяжёлые по времени прогона (`httpfetch`, `content`, `watch`,
  `dnsclient`, `httpworker`, `dnsworker`, `ingest`, `migrate`, `db`,
  `service`, `renderworker`, `metrics`) — мутационный прогон умножает
  время их тестов на число мутантов (для `httpfetch` это часы).

### Как это работает

`deploy/docker/scripts/mutate.sh` (вызывается make-целью):

1. Копирует исходники в изолированный каталог внутри контейнера
   (`/tmp/mutation-src`, без `.git`/`var`/`tmp`). Копия нужна потому,
   что go-mutesting подменяет файлы мутантами **прямо в дереве**, а
   рабочее дерево смонтировано в контейнеры сервисов с hot-reload.
2. Запускает `go-mutesting` с конфигом `test/mutation/go-mutesting.yml`
   и встроенным exec: на каждого мутанта — `go test` его пакета с
   таймаутом `MUTATE_TIMEOUT` (кэши `gomod`/`gocache` общие — компиляция
   зависимостей не повторяется).
3. Выгружает отчёты в `var/mutation/` и сравнивает итоговый score с
   `MUTATION_MIN_SCORE` (сам go-mutesting всегда выходит с кодом 0,
   порог гейтит обёртка).

## 3. Отчёты

`make mutate` пишет в `var/mutation/` (каталог в git не попадает):

- `mutate.log` — полный вывод: по мутанту строка `PASS` (убит) / `FAIL`
  (выжил, с diff-патчем) / `SKIP` (не скомпилировался) и итоговая строка
  `The mutation score is ...`;
- `go-mutesting-report.html` — интерактивный отчёт по выжившим мутантам
  (diff, файл, мутатор) — основной инструмент разбора;
- `report.json` — те же данные в машиночитаемом виде.

Терминология вывода обратная интуиции: `PASS` — хорошо (тесты убили
мутанта), `FAIL` — выживший мутант, дыра в тестах.

## 4. Ложные срабатывания

Часть мутантов бессмысленна (оптимизации, логирование, дебри
форматов). Их не гасят тестами, а исключают — в порядке приоритета:

1. **Аннотации в коде** (рекомендуемый способ, живёт рядом с кодом):

   ```go
   // mutator-disable-func            — не мутировать функцию целиком
   // mutator-disable-next-line *     — не мутировать следующую строку
   // mutator-disable-next-line branch/if, expression/comparison
   // mutator-disable-regexp `^log\.` *  — строки по регулярному выражению
   ```

2. **Блэклист чексумм** — `test/mutation/blacklist.txt` (MD5 из строки
   `FAIL "..." with checksum <md5>` в `mutate.log`, по одной в строке;
   парсер форка требует ровно 32 hex-символа — комментарии в файле
   недопустимы, обоснования групп — в этом файле, ниже);
   подключается автоматически, если файл непуст. Способ хрупкий: правка
   исходника меняет чексуммы — поэтому только для мутантов, которые
   нельзя закрыть аннотацией. Занесённые в блэклист мутанты идут как
   duplicates и НЕ входят ни в числитель, ни в знаменатель score
   (`Msi = (killed + error + skipped) / (killed + escaped + error +
   skipped)`, internal/models форка) — погашение повышает score ровно
   как убийство тестом, потому группа обязана быть доказуемо
   эквивалентной/ненаблюдаемой, а не «не нашёл, как убить».

   Состав блэклиста (триаж выживших CI-прогна 09.11.2026, половина A —
   96 чексумм) по группам:

   | Группа | Где | Обоснование |
   |---|---|---|
   | `parsefloat-bitsize` | load.go, psi.go, renders.go | `strconv.ParseFloat` с bitSize ≠ 32 ведёт себя как 64 (ветвления по 32/остальное в strconv) — мутанты bitSize 63/65/9 эквивалентны |
   | `log:side-effect`, `*-log` (loop/drain/info/warn/debug) | monitor, analyzer | журнальные вызовы (log.Info/Warn/Debug и их охранные `ctx.Err() == nil`): единственный эффект — строка в журнале, контракт поведения не меняется; suppressed тем же смыслом, что аннотации `mutator-disable-regexp log\.…` в nearstats/historystats |
   | `make-cap` | zonestats.go, renders.go | ёмкость `make(...)` — хинт производительности: значения длины/содержимое не меняются |
   | `load:guest-break` | load.go L261 | `break → continue` в цикле тиков: после 8 полей обе формы ничего не пишут (continue лишь лишние итерации без эффектов) |
   | `load:closeq-open` | load.go | `close_ <= open → <`: close_ == open недостижимо (разные символы скобок) |
   | `load:read-max-eq` | load.go | максимум по группам с равным entries-read — то же значение |
   | `load:busy-clamp-eq`, `load:round-neg-eq` | load.go | клампы нуля: при 0 обе ветви дают 0; для `v < -1` — усечение int(x+0.5) к 0 на [-1, 0.5) |
   | `load:procwin-guard` | load.go | ослабления `d > 0`/`perCore > 0`/`agg.Ticks <= prev` прикрыты внутренней охраной `perCore > 0` и порогом шума topByCPU: доля 0 отфильтровывается, отчёт тот же |
   | `load:rate-window-eq` | load.go | `window == 0` между проходами недостижимо (тикер ≥ интервала); равный/упавший Read даёт темп 0/отрицательный — строка темпа не печатается ни в одном из вариантов |
   | `load:top-trunc-eq` | load.go | `len(items) >= topProcs` при равенстве — срез той же длины |
   | `zonestats:init-guard` | zonestats.go init() | защита от рассинхрона легенды при будущих правках: на согласованном коде невыполнима (см. соседнюю аннотацию-прецедент) |
   | `zonestats:drift-int`, `zonestats:absdiff-eq` | zonestats.go | `d < 0 → <= 0` и `a > b → >= b` на int64: в точке равенства обе ветви дают 0 |
   | `zonestats:sort-uniq` | zonestats.go | компаратор `<=`: ключи zoneIDs уникальны (map), равенство недостижимо |
   | `zonestats:took-eq` | zonestats.go | `took >= interval` различается только при точном равенстве измеренной длительности интервалу — недетерминированно/недостижимо в тесте |
   | `zonestats:globals-prezero` | zonestats.go | предобнуление статусов перед `+=`: += по отсутствующему ключу читает 0 — карта неотличима |
   | `zonestats:returning-missing` | zonestats.go L1123 | ветка «RETURNING не вернул зону» недостижима: writeZonePositions требует len(out) == len(ids) и роняет проход раньше |
   | `slowqueries:phrase-eq` | slowqueries.go | `n%100 <= 10`/`> 20` отличаются только при n%100==10/20, где n%10==0 — первая клауза `n%10 >= 2` уже отсекает; `n%10 >= 1` перекрыто case 1 (`n%10 == 1 ∧ n%100 != 11`) — доказано перебором 0..300 |
   | `renders:trunc-hash` | renders.go | усечение `#`-хвоста: значение — первый токен rest в обоих вариантах (защитный код) |
   | `renders:labels-end-neg` | renders.go | `end <= 0`: end ≥ start+1 ≥ 1, нуль недостижим |
   | `renders:escape-boundary-eq` | renders.go | `i+1 < len(s) → i+0/i-1/true` (граница последнего символа): обе формы заканчивают цикл без находки скобки |
   | `renders:rateof-eq` | renders.go | `cur <= prev → <`: при равенстве обе дают 0 |
   | `renders:dt-clamp-eq` | renders.go | кламп dt прикрыт собственной охраной rateOf (`dt <= 0 → 0`) — отрицательное окно даёт 0 в обоих путях |
   | `renders:body-close`, `renders:ctx-cancel` | renders.go | Close тела/отмена контекста после чтения — без наблюдаемого эффекта в юнит-поверхности |
   | `idn:unreachable-guard` | idn.go | `i == 0` (имя с ведущей точкой) исключено normalizeASCII; соседняя ветка-защита уже погашена аннотацией с тем же обоснованием |
   | `worker:drain-log` | worker.go | `stats.Rows > 0 → >= 0/> -1/> 1`: тело ветки — только log.Info |

Конфиг `test/mutation/go-mutesting.yml` дополнительно отсекает файлы без
сопутствующего `*_test.go` и файлы, чьи тесты под build-тегом, — убить
мутанта без исполняемых тестов невозможно.

Гранулярность аннотаций — строка целиком: `next-line` и `regexp`
действуют на все мутации перечисленных мутаторов на строке, а не на
конкретный операнд. На строке с несколькими мутациями разной ценности
аннотация эквивалентного может попутно погасить и убиваемых (пример —
T-M02: `if a || b` с эквивалентным мутантом `b → false` гасит и
убиваемого `a → false`; индекс-литерал рядом с недробимым `bitSize`).
Полное устранение — разнос выражений по строкам, но это правка
продуктового кода: без бага она не делается, trade-off фиксируется в
коммите задачи и снимается при следующей содержательной правке файла.

## 5. CI

[`.github/workflows/mutation.yml`](../.github/workflows/mutation.yml):
еженедельный прогон по `master` (воскресенье 20:00 МСК) + запуск вручную
(inputs: `pkgs`, `min_score`, `timeout`).

Полный охват не влезает в платформенный потолок hosted-джоба 6 ч:
локальные ~2.5 ч на CI-раннере замедляются в разы, последовательно
полная дистанция по замерам — ~9.5–11.5 ч. История сплитов: одиночный
джоб срезался по таймауту дважды (240 мин; ручная остановка на
~4.6 ч в 7-м пакете из 10); следующий сплит на две половины по весу
(LOC 52/48) провалился фактом прогона 42595221462 от 09.11.2026:
половина A прошла шаг мутации за ~2ч15м (гейт качества при этом
упал — score 0.758, разбор выживших — отдельная задача), а половина
B (тогда queue+render+rules+scheduler+status) срезана шаговым
таймаутом 340 мин — queue отработал ~77 мин (770 мутантов,
~6 с/мутант), но render идёт темпом ~29 с/мутант (за 265 мин —
лишь ~70–85% пакета, т.е. полный пакет ~5.2–6.3 ч),
rules/scheduler/status не начались; полный B-набор — ≥7 ч
(queue + render + не начатые пакеты). Вывод: балансировать надо
по времени, а не по числу мутантов или LOC — время пропорционально
«мутанты × время тестов пакета», и темп задаёт тестовый сюит
пакета, расходясь в разы (queue ~6 с/мутант против ~29 с/мутант у
render; числа мутантов в таблице §2 — на 2026-10, код с тех пор
вырос: queue по счёту рана уже 770 против 392). Поэтому полный
охват разделён на три параллельных джоба — части:

| Джоб | Пакеты | Время на CI |
|---|---|---|
| `mutate-a` | analyzer, dashboard (вкл. auth), idn, model, monitor | замер 09.11.2026: ~2ч15м |
| `mutate-b` | queue, rules, scheduler, status | оценка ~2–3 ч: queue замерен (77 мин), rules/scheduler/status в CI не гонялись — предположительно быстрые сюиты, уточнится первым прогоном |
| `mutate-c` | render | ~5.2–6.3 ч по замеру темпа ~29 с/мутант (544 мутанта за 265 мин ≈ 70–85% пакета) |

Render выделен в отдельный джоб не по числу мутантов, а по времени:
медленный тестовый сюит даёт ~29 с/мутант — впятеро медленнее queue —
и в одной связке с queue не влезал в потолок 6 ч (замер выше: срез
на ~70–85% render при не начатых rules/scheduler/status).
Пессимистичный край оценки C (~6.3 ч) задевает шаговый потолок
340 мин (срез на ~90% пакета) — даже тогда прогон информативнее
прежней половины B, а отчёты сохранит always()-выгрузка;
дальнейший рычаг — ускорение тест-сюита render (вне задачи о
балансе джобов).

Каждый джоб независим: собирает tools-образ, гонит свою часть и
выгружает отчёты в свой artifact (`mutation-report-{a,b,c}-<run_id>`);
`timeout-minutes: 360` на джоб — платформенный максимум, а у самого
шага мутации потолок 340 мин: при срезе по шаговому потолку
always()-выгрузка выполняется штатно, убийство же джоба по джобовому
потолку выгрузку не гарантирует.

Ручной запуск: пустой `pkgs` — все три части (полный охват);
непустой — точечный прогон одного джоба `mutate-a` с этим набором
(полный список в него не вписывать — один джоб срежется по 6 ч;
набор валидируется по белому списку символов — значение попадает
в рецепт make в одинарных кавычках), `mutate-b` и `mutate-c`
скипаются. `min_score`/`timeout` применяются ко всем трём джобам.

Порог по умолчанию — `0.98`, гейтит **каждую часть отдельно**: это
строже глобального взвешенного порога — тот допускал бы перекос
(идеальная часть компенсировала бы провальную ниже 0.98), а гейт
по частям локализует дыры в пакетах части; осознанное решение.
Запас ~0.02 (десятки мутантов на часть) покрывает тайминг-чувствительные
тесты (контрольный прогон T-M14 однажды показал выжившего-флака
`wait.go.6`: kill через отмену ctx — гонка teardown chromedp, закрыт
детерминированным субтестом, но запас порога оставлен осознанно);
ниже порога недельная проверка краснеет, но разработку не блокирует
(в PR workflow не вызывается).

Порог поднимают осознанно: выжившие мутанты чинятся новыми тестами либо
явно гасятся (§4), и только после этого планка повышается до
достигнутого уровня минус запас (~0.02).

## 6. Когда запускать

- перед существенными правами пакета из охвата по умолчанию — точечно:
  `make mutate PKGS='./internal/<pkg>/...'`;
- при падении еженедельного прогона — разобрать HTML-отчёты всех частей
  (artifacts `mutation-report-{a,b,c}-*`), закрыть дыры
  тестами или погасить ложные, поднять порог;
- полным прогоном — эпизодически, для сверки общей картины.
