# Мутационное тестирование

Мутационное тестирование проверяет **качество тестов**, а не кода: в
исходник по одному вносятся мелкие ошибки (мутации — инвертированные
условия, вырезанные ветки, изменённые операторы и константы), и после
каждой запускаются тесты пакета. Мутант, который тесты **не заметили**
(«выжил»), — участок кода, не зафиксированный утверждениями. Доля убитых
мутантов — mutation score — метрика строгости тестовой suite.

В проекте это вспомогательная, тяжёлая проверка: в CI каждого пуша она
не входит, гоняется ночным workflow и вручную.

## 1. Инструмент

[`go-mutesting`](https://github.com/zimmski/go-mutesting) в живом форке
[avito-tech/go-mutesting](https://github.com/avito-tech/go-mutesting):
апстрим zimmski не обновлялся с 2021 и паникует в `go/types` под
современными тулчейнами; форк — тот же инструмент (те же мутаторы и
встроенный exec через `go test`), дополненный конфигом YAML, аннотациями
отключения мутаций, JSON/HTML-отчётами и набором мутаторов
(arithmetic/loop/numbers поверх branch/expression/statement).

Версия пинится в `.env` (`GO_MUTESTING_VERSION`, ставится в dev-образ
`deploy/docker/Dockerfile.go`); выбранная ревизия — последняя, не
требующая тулчейн новыше проектного (`go 1.25.5` при проектном Go
1.26.x: `go install` не тянет лишний toolchain).

## 2. Запуск

```bash
make mutate                                    # охват по умолчанию
make mutate PKGS='./internal/httpfetch/...'    # точечный пакет
make mutate PKGS='./internal/queue/... ./internal/idn/...'
make mutate MUTATION_MIN_SCORE=0.7             # упасть, если score < 0.7
make mutate MUTATE_TIMEOUT=120                 # таймаут go test на мутанта, с
```

Всё выполняется в контейнере `tools` (как `make test`); Go на хосте не
нужен. Переменные:

| Переменная | Значение | По умолчанию |
|---|---|---|
| `PKGS` | охват — локальные `./`-шаблоны пакетов через пробел | «логическое ядро», см. ниже |
| `MUTATION_MIN_SCORE` | порог score 0..1, ниже — exit 1 | `0` (только отчёт) |
| `MUTATE_TIMEOUT` | таймаут `go test` на одного мутанта, с | `60` |

Важно: `go-mutesting` резолвит цели GOPATH-эрой логикой — шаблоны
обязательно локальные (`./internal/...`), импортные пути модуля
(`crawler/internal/...`) не работают.

### Охват по умолчанию

`PKGS` по умолчанию — пакеты бизнес-логики с герметичными и быстрыми
юнит-тестами: `./internal/{analyzer,dashboard,idn,model,monitor,queue,
render,rules,scheduler,status}/...`. Замер полного прогона (2026-10,
71e1da3): **94 минуты, 2877 мутантов, score 0.673**; по пакетам:

Не входят в охват по умолчанию и проверяются точечно по мере
необходимости:

- `config`, `web` — сотни мутантов по yaml-биндингу и i18n-обвязке при
  низком сигнале;
- тяжёлые по времени прогона (`httpfetch`, `content`, `watch`,
  `dnsclient`, `httpworker`, `dnsworker`, `ingest`, `migrate`, `db`,
  `service`, `renderworker`, `metrics`) — мутационный прогон умножает
  время их тестов на число мутантов (для `httpfetch` это часы).

### Как это работает

`deploy/docker/scripts/mutate.sh` (вызывается make-целью):

1. Копирует исходники в изолированный каталог внутри контейнера
   (`/tmp/mutation-src`, без `.git`/`var`/`tmp`). Копия нужна потому,
   что go-mutesting подменяет файлы мутантами **прямо в дереве**, а
   рабочее дерево смонтировано в контейнеры сервисов с hot-reload.
2. Запускает `go-mutesting` с конфигом `test/mutation/go-mutesting.yml`
   и встроенным exec: на каждого мутанта — `go test` его пакета с
   таймаутом `MUTATE_TIMEOUT` (кэши `gomod`/`gocache` общие — компиляция
   зависимостей не повторяется).
3. Выгружает отчёты в `var/mutation/` и сравнивает итоговый score с
   `MUTATION_MIN_SCORE` (сам go-mutesting всегда выходит с кодом 0,
   порог гейтит обёртка).

## 3. Отчёты

`make mutate` пишет в `var/mutation/` (каталог в git не попадает):

- `mutate.log` — полный вывод: по мутанту строка `PASS` (убит) / `FAIL`
  (выжил, с diff-патчем) / `SKIP` (не скомпилировался) и итоговая строка
  `The mutation score is ...`;
- `go-mutesting-report.html` — интерактивный отчёт по выжившим мутантам
  (diff, файл, мутатор) — основной инструмент разбора;
- `report.json` — те же данные в машиночитаемом виде.

Терминология вывода обратная интуиции: `PASS` — хорошо (тесты убили
мутанта), `FAIL` — выживший мутант, дыра в тестах.

## 4. Ложные срабатывания

Часть мутантов бессмысленна (оптимизации, логирование, дебри
форматов). Их не гасят тестами, а исключают — в порядке приоритета:

1. **Аннотации в коде** (рекомендуемый способ, живёт рядом с кодом):

   ```go
   // mutator-disable-func            — не мутировать функцию целиком
   // mutator-disable-next-line *     — не мутировать следующую строку
   // mutator-disable-next-line branch/if, expression/comparison
   // mutator-disable-regexp `^log\.` *  — строки по регулярному выражению
   ```

2. **Блэклист чексумм** — `test/mutation/blacklist.txt` (MD5 из строки
   `FAIL "..." with checksum <md5>` в `mutate.log`, по одной в строке);
   подключается автоматически, если файл непуст. Способ хрупкий: правка
   исходника меняет чексуммы — поэтому только для мутантов, которые
   нельзя закрыть аннотацией.

Конфиг `test/mutation/go-mutesting.yml` дополнительно отсекает файлы без
сопутствующего `*_test.go` и файлы, чьи тесты под build-тегом, — убить
мутанта без исполняемых тестов невозможно.

## 5. CI

[`.github/workflows/mutation.yml`](../.github/workflows/mutation.yml):
ночной прогон по `master` + запуск вручную (inputs: `pkgs`, `min_score`,
`timeout`). Порог по умолчанию — `0.60`: при baseline 0.673 (см. таблицу
выше) это ~200 мутантов запаса на колебания тайминг-чувствительных
тестов; ниже порога ночная проверка краснеет, но разработку не
блокирует (в PR workflow не вызывается). Отчёты прогона выгружаются
в artifact рана.

Порог поднимают осознанно: выжившие мутанты чинятся новыми тестами либо
явно гасятся (§4), и только после этого планка повышается до
достигнутого уровня.

## 6. Когда запускать

- перед существенными правами пакета из охвата по умолчанию — точечно:
  `make mutate PKGS='./internal/<pkg>/...'`;
- при падении ночного прогона — разобрать HTML-отчёт, закрыть дыры
  тестами или погасить ложные, поднять порог;
- полным прогоном — эпизодически, для сверки общей картины.
