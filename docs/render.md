# Рендер: Chromium под управлением render-worker (ТЗ 5.6, §9)

Пакет `internal/render` (T-061) — управление **одним** Chromium на воркер и
параллельный рендер страниц в изолированных контекстах. Блокировка
ресурсов (T-062), ожидание готовности страницы (T-063) и съём итогового
DOM/cookies/заголовков (T-064) описаны ниже; перезапуск браузера по
страницам и памяти (T-065) — Manager; цикл очередей — T-066 (публикация
q:render при SPA, флаг `render_pending`) и T-067 (потребление q:render —
замена контента, следующий раздел); потребитель зовёт `Manager.Run`.

## Один браузер, два режима

`render.StartBrowser(ctx, opts)` — один процесс/соединение на воркер
(ТЗ 5.6 «один браузер»):

| Режим | Условие | Аллокатор |
|---|---|---|
| внешний Chromium | `render.remote_url` задан (`ws://host:9222`) | собственный аллокатор поверх `chromedp/remote` (remotealloc.go — детерминированное закрытие сокета, T-218) |
| собственный процесс | `render.remote_url` пуст | `chromedp.NewExecAllocator` + headless-набор флагов и `--no-sandbox` |

Внешний режим — dev-стек: compose-сервис `chromium`
(`chromedp/headless-shell`, `mem_limit` 2 ГБ ≈ бюджет ТЗ 3.2, CDP на
`172.28.100.14:9222`). Собственный — боевой render-образ
(`deploy/docker/Dockerfile.render`: headless-shell + бинарник воркера,
`USER nobody` — отдельный непривилегированный пользователь по ТЗ §9).
Профиль браузерной сессии служебный (headless-shell без пользовательского
каталога): страницы задач в нём не рендерятся.

`ctx` стартового вызова — контекст жизненного цикла воркера: в chromedp
браузер живёт, пока жив контекст первого вызова, отмена ctx останавливает
и подключение/процесс, и незавершённую инициализацию.

### Движки рендера: chromium / moli / lightpanda (этап 35)

Поле `render.engine` (ТЗР движков рендера, ФТ-1) выбирает движок:
`chromium` — дефолт, воспроизводит поведение выше пиксель-в-пиксель;
`moli` и `lightpanda` — внешние CDP-серверы, контейнер движка поднимает
инфраструктура (dev-стек — профиль `render-engines`, см.
[`dev-environment.md`](dev-environment.md)), воркер только подключается.
Движковая специфика изолирована на двух границах (ФТ-4): сборка
конфигурации → `render.Options` (поле `Engine` + валидация) и
remote-аллокатор; ядро пакета — Session/Pool/Manager/extract/block/wait —
движок не различает, ветвлений по нему нет.

Валидация (и конфигурации, и `Options`) проверяет связку
«движок × `remote_url` × `restart_memory_bytes`» (ФТ-3): для
moli|lightpanda `remote_url` обязателен (собственный процесс браузера —
только chromium), его схема — `ws`/`wss` (адрес идёт в WebSocket-диал
напрямую) и `restart_memory_bytes` обязан быть 0 — RSS чужого процесса
недоступен, как и сегодня в remote-режиме dev-стека.

Режим адреса аллокатора — по движку (поведение подтверждено на
закреплённых образах стека: moli v1.1.21, lightpanda 1.0.2):

| Движок | Подключение |
|---|---|
| chromium | резолв хоста в IP + уточнение `/json/version`, рекламируемый `webSocketDebuggerUrl` как есть (как до этапа 35) |
| lightpanda | адрес конфигурации как есть (аналог `remote.NoModifyURL`): browser-WS движка живёт на корневом пути |
| moli | путь `/devtools/browser/<uuid>` — из `/json/version` (uuid генерируется на каждый старт процесса, в конфиге его не задать), authority (хост:порт) — из адреса конфигурации |

Подмена authority у moli нужна потому, что движок строит рекламу от
адреса бинда (флага advertise-host, как у lightpanda, у него нет), и при
бинде 0.0.0.0/127.0.0.1 рекламируемый адрес недостижим извне контейнера.
Health-check воркера не меняется: `/json/version` поддерживают все три
движка.

## Изолированные контексты и отказ от сохранения состояния

`Browser.NewSession` — изолированный контекст CDP
(`Target.createBrowserContext`, опция chromedp `WithNewBrowserContext`):
инкогнито-профиль со **своими** cookies, кэшем и хранилищами (localStorage,
IndexedDB, service workers) и одна вкладка `about:blank`.

Сессия живёт ровно одну задачу: после страницы пул закрывает её
(`Target.disposeBrowserContext`), следующая задача получает новый профиль.
Пересоздание вместо выборочной очистки: dispose выкидывает все хранилища
профиля атомарно и без перечисления origin'ов (очистка потребовала бы
`Storage.clearDataForOrigin` по каждому встреченному origin и не покрывала
бы кэш), а стоимость — один `createBrowserContext` + `createTarget`,
незаметная на фоне таймаута страницы в секунды. Требование ТЗ §9 «без
сохранения состояния между страницами» выполняется конструкцией; изоляция
подтверждается live-тестом (cookie, положенная в профиль сессии, не видна
в следующей).

## Пул

`render.NewPool(browser)` — параллелизм `render.contexts` (рекомендация
ТЗ 5.6: 2–4): одновременно не больше N задач, каждая — в свежем
изолированном профиле. `Pool.Run(ctx, task)`:

- ждёт свободный слот (или отмену ctx / закрытие пула);
- одна попытка = новая сессия → задача → закрытие профиля при любом
  исходе;
- при ошибке класса `context` — один повтор на новом контексте;
- успешная страница инкрементирует `Browser.Pages()` — счётчик для
  перезапуска «каждые N страниц» (`render.restart_every_pages`, ТЗ 5.6);
  смена поколения — Manager (T-065, ниже).

`Pool.Close` — graceful shutdown по ТЗ 3.4: новые задачи отклоняются
(`ErrClosed` → повторная доставка уровнем очереди), текущие дорабатываются
(каждая ограничена `render.timeout`), затем останавливается браузер.

Задача и результат — `RenderTask{URL}` и `RenderOutput`: итоговый URL
(включая JS-редиректы, которых HTTP-этап не видит), `Title`,
итоговый `DOM`, `Cookies` и `ResponseHeaders` (T-064, ниже). Схема
задачи контролируется до перехода (`validateTaskURL`, R-09 — только
http/https); при включённом `http.block_internal_addrs` в начале `Run`
отвергаются задачи с внутренними хостами (SSRF-контур T-219, класс
task: IP-литералы любых форм — включая IPv4-в-IPv6 и числоподобные
`127.1`/`2130706433`, которые Chromium канонизирует, — и loopback-имена;
`renderHostInternal`). Той же проверкой живёт перехват запросов
Chromium (`blockInternal`): при включённом флаге `Fetch.enable` получает
паттерн-«всё», и любой запрос сессии — навигации по HTTP/JS-редиректам
(Document) и подресурсы (Script/XHR/WebSocket) — с внутренним хостом
отклоняется до выхода в сеть; цена — CDP-цикл на каждый запрос, поэтому
паттерн ставится только флагом. С T-230 перехват резолвит и
произвольные имена-хостов (шов `Options.LookupHost`, дефолт — системный
резолвер, как у самого Chromium; кэш на сессию с TTL 30 с и потолок
одного обмена 3 с — `dnsCache`, block.go): имя, публичное на HTTP-этапе
и внутреннее на момент рендера (DNS-rebinding во времени), отклоняется
failRequest'ом; ошибка резолва — запрос проходит (NXDOMAIN рекламных
подресурсов — норма страницы), найденный внутренний адрес — отклонение.
Остаточный вектор: атакующий с контролем зоны различает резолв перехвата
и собственный резолв Chromium (два отдельных DNS-обмена) и отвечает им
разными адресами — «публичный» перехвату, «внутренний» браузеру.
Поэтому для Internet-эксплуатации контейнер Chromium стоит держать в
сетевой egress-политике без доступа во внутренние подсети — эшелонированная
защита, которую перехват дополняет (закрывая смену адреса между этапами),
но не заменяет; имена-хосты задач фильтруются HTTP-этапом той же
воронкой — docs/configuration.md, `block_internal_addrs`). User-Agent
страниц — единый идентифицируемый UA краулера `http.user_agent` (ТЗ §9; в
секции render ТЗ 5.10 отдельного поля нет): применяется к вкладке через
`Emulation.setUserAgentOverride`.

## Перезапуск браузера и порог памяти (T-065)

`render.NewManager(ctx, opts)` — жизненный цикл Chromium воркера (ТЗ 5.6:
«перезапуск браузера каждые N страниц и при превышении порога памяти»).
`Manager.Run(ctx, task)` — точка входа задач вместо прямого `Pool.Run`
(цикл очередей — T-067): перед задачей гарантируется живое поколение
«браузер + пул», триггеры смены поколения:

| Триггер | Условие | ТЗ |
|---|---|---|
| порог страниц | `Browser.Pages() ≥ render.restart_every_pages` (500) | 5.6 |
| порог памяти | RSS дерева процессов Chromium ≥ `render.restart_memory_bytes` (1536 MiB) | 5.6, 3.2 |
| смерть браузера | `!Browser.Alive()`: потеря соединения/процесса | §3.4 |

**Автомат поколения (T-263).** Живость поколения «браузер + пул» — один
предикат `Manager.genStateLocked` с шестью состояниями: отсутствует |
стартующий | активный | draining | мёртв | закрыт. Спецификация и
таблица переходов с причинами замены и побочками (рестарт, дрен, логи) —
`internal/render/genstate.go` (ТЗ-fsm §3 ФТ-9); решения принимают
`swapReasonLocked` и `Alive` через предикат. Пороги страниц/памяти из
таблицы выше — не состояния, а причины плановой замены живого поколения.
Формализация без изменения поведения: до T-263 решение сводилось из пяти
независимых проверок внутри `swapReasonLocked`.

**Смена поколения не ждёт задач.** Старый пул выводится из работы
синхронно (`retire`: новые задачи — `ErrClosed`), дорабатывает свои
страницы (каждая ограничена `render.timeout`, ТЗ 3.4) и закрывает свой
браузер уже фоновой горутиной; новый браузер стартует сразу — иначе
перезапуск по памяти ждал бы самые «тяжёлые» страницы, съевшие бюджет.
Задача, не начавшаяся в закрываемом пуле (`ErrClosed` — она не
выполнялась), и умерший посреди задачи браузер (`ClassBrowser`) — смена
поколения и повтор задачи, не более двух на задачу: краш-луп Chromium не
должен множить выполнения одной страницы, дальше — повторная доставка
уровнем очереди.

**RSS — из /proc, всё дерево процессов.** Chromium — не один процесс:
главный, рендереры, GPU; в бюджет ТЗ 3.2 вкладывается каждый. PID
главного процесса chromedp отдаёт явно (`Browser.Process()`, метод
задокументирован ровно для сбора метрик процесса); от него суммируется
RSS потомков по `/proc/<pid>/stat` (поле `rss`, обход по PPid до листьев —
`internal/render/proc.go`). Проверка — перед каждой задачей, но обход
`/proc` (листинг всех процессов контейнера) кэшируется на 10 секунд
(`rssCacheTTL`, T-229): полный проход — не чаще раза в окно, погрешность
безопасна — перезапуск по памяти мягкая профилактика, жёсткий потолок
держит cgroup. Кэш хранит только положительные измерения и ключуется
корнем дерева: смена поколения (новый Browser) читает свежо. В
remote-режиме (dev-стек) процесс Chromium в другом контейнере — RSS
неизвестен (`Browser.RSS() = -1`), порог по памяти не срабатывает:
жёсткий потолок там держит `mem_limit` compose-сервиса chromium
(2 ГБ — бюджет ТЗ 3.2).

**Старт и реконнект.** `Manager.Start()` поднимает первое поколение
немедленно: ошибка старта — ошибка запуска сервиса (код 1, systemd
`Restart=on-failure`), а не перебор попыток доставок. `Manager.Alive()` —
зонд потребления воркера (`renderworker.Options.Alive`): мёртвое или
отсутствующее поколение зонд заменяет прямо в вызове, поэтому после
потери соединения или рестарта Chromium (юнит `crawler-chromium.service`,
docker-рестарт контейнера) пауза потребления не зависает навсегда —
следующий зонд подключается к новому поколению.

**Обрыв CDP: полузакрытое соединение (T-218, инцидент 02.11).** После
ресайкла Chromium (таймер T-208) воркеры копили WebSocket-соединения к
:9222 (до 284 за ~6 ч), `Target.createBrowserContext` висел до
`SessionStartTimeout` (11 520 WARN «контекст рендера умер» за 6 ч), темп
падал ~5,5 ч и к 07:25 рендер встал; свежий Chromium был здоров —
ломалось состояние воркеров, лечение — рестарт воркеров. Причина в
транспорте chromedp: чтение WebSocket (`remote.Conn.Read`) не реагирует
ни на контекст, ни на таймауты — о смерти соединения библиотека узнаёт
только от ошибок сокета, а полузакрытое/подвисшее соединение (без
FIN/RST) выглядит живым бесконечно; запись (`remote.Conn.Write`) тоже без
дедлайна — насосы chromedp виснут в записи до исчерпания
TCP-ретрансмиссий, и upstream-аллокатор не закрывает сокет, пока не
завершатся насосы. Три контрмеры:

- **зонд соединения** `Browser.probeConn` — живая команда уровня браузера
  (`Target.getTargets`, 5 с) перед созданием каждой сессии, в
  классификации таймаутов создания контекста и при таймауте страницы:
  неудача — класс browser; потерянным (залипающе — полузакрытый сокет не
  воскресает) браузер помечается со второй подряд неудачи зонда (T-226:
  одиночный таймаут не различает чёрную дыру и перегруженный Chromium, а
  ложная смерть на нагруженном воркере дороже лишнего зонда) либо сразу —
  по доказанной смерти транспорта (`context.Canceled`: отмена контекста
  браузера, закрытый сокет через LostConnection); Manager меняет
  поколение и повторяет задачу на новом соединении; висящая команда при
  живом зонде остаётся классом context (повтор на новом контексте), а
  таймаут страницы при живом зонде — классом task (тарпит-политика
  T-148). Зонд дёшев на живом браузере (миллисекунды даже при медленной
  странице); восстановление после рестарта Chromium — за одну задачу
  (два зонда + подключение), без рестарта воркера;
- **собственный аллокатор remote-режима** (`remotealloc.go`): после
  отмены контекста поколения — штатное закрытие вкладок chromedp
  (ограничено таймаутами библиотеки, ≤ ~5,5 с), затем принудительный
  `Close()` сокета независимо от состояния насосов — старые соединения
  освобождаются в границы таймаутов chromedp, а не TCP-ретрансмиссий;
- **потолок инициализации** `initBrowserSession`: bootstrap-команды
  chromedp (служебная вкладка, домены) самой библиотекой не
  ограничиваются — на подвисшем, но принимающем соединения Chromium старт
  висел бы бесконечно, удерживая мьютекс менеджера; попытка гонится с
  потолком `DialTimeout + SessionStartTimeout`.

Воспроизведение — юнит-тест `TestManagerRecoversAfterBrowserDeath`
(`internal/render/reconnect_test.go`): «чёрная дыра» CDP (чтение висит,
записи принимаются) на месте умершего браузера — assertions: контексты
на мёртвом сокете не создаются, поколение меняется сам, задача проходит
на новом соединении ≤ минуты, соединения не растут (старый сокет закрыт
принудительно).

**Почему порог 1536 MiB при лимите 2 ГБ.** Перезапуск — мягкая
профилактика утечек до срабатывания cgroup-OOM (`mem_limit`/`MemoryMax`,
ТЗ 3.2/10.1). Запас 25 % — на рост памяти между проверками (проверка —
каждая задача, снимок RSS — не старее окна кэша 10 с, T-229)
и на tmpfs `/dev/shm`, который учитывается в памяти cgroup, но не в RSS
процессов. При дефолтных 8 контекстах (T-169) запас не сужается
подъёмом порога: страницы в полёте наращивают RSS и после последней
проверки; систематическое проживание RSS у порога — сигнал насыщения
одного Chromium (ответ — второй Chromium :9223 и второй воркер против
него, deploy.md §2.2), порог не поднимают. Настроить —
`render.restart_memory_bytes` (0 — отключить).

**Непривилегированный пользователь и память контейнера** (ТЗ §9, §10.1):
боевой образ `deploy/docker/Dockerfile.render` работает под `USER nobody`,
Chromium запускается воркером с `--no-sandbox` (обязателен в контейнере
без привилегий; граница изоляции — сам контейнер). Ресурсные требования
зафиксированы в compose-профиле `runtime` (сервис `render`,
`deploy/docker/compose.yaml`): `mem_limit` ≈ 2 ГБ, `shm_size`, `init`,
`cap_drop: ALL`, `no-new-privileges`. systemd-юниты с `MemoryMax`/`User=`
— этап 9 (ТЗ 10.1).

## Съём результата (T-064)

Финальный этап `Session.Run` после перехода (`extract.go`; ТЗ 5.6 «Результат:
итоговый DOM (`document.documentElement.outerHTML`) и все cookies (включая
выставленные JS) через CDP», §11.4 п. 3):

| Что | Как | Почему |
|---|---|---|
| итоговый DOM | `chromedp.Evaluate` выражения `document.documentElement.outerHTML` | сериализация живого дерева после дорисовки JS тем же HTML-сериализатором Chrome, что отдаёт «сохранить страницу»: формат идентичен сыровму HTML — прямо в хранилище (T-067) и в правила по HTML/meta (T-068) без преобразований; `DOM.getFlattenedDocument` (дерево узлов с nodeId, требует посереди `DOM.getOuterHTML`) отвергнут |
| все cookies | CDP `Network.getCookies` с URL итоговой страницы | читает хранилище cookies изолированного контекста, а не `document.cookie` — видны httpOnly и выставленные JS. `Network.getAllCookies` из актуального протокола удалён (в cdproto v0.157.8 команды нет); `Network.getCookies` над сессией вкладки — то же хранилище, а явный URL даёт набор «cookies этой страницы» без subframe-шума |
| заголовки ответа | `chromedp.NavigateResponse` (ответ основной навигации из `Network.responseReceived`) | ТЗ 5.8 — правила по заголовкам: у отрендеренной страницы итоговый документ не обязан совпадать со снятым HTTP-этапом. Chromedp сам ведёт цепочку loader/request через редиректы — подписки на события не нужны. Формат `http.Header` — единый контракт с HTTP-этапом (T-058) |

`Cookies` — `[]ExtractCookie`: форма записи повторяет cookie HTTP-этапа
(`subdomain_results.cookies`, T-058: `name`/`value` — цели правил ТЗ 5.8,
`path`/`domain`/`expires` RFC 3339 UTC/`secure`/`http_only`/`same_site`
строчными `lax`/`strict`/`none`), порядок детерминирован
(name, domain, path). `max_age` не заполняется: хранилище браузера держит
только абсолютный срок. Cookies снимаются по итоговому URL; задачи —
только http/https (`validateTaskURL`, R-09), не-http итоговый URL —
оборонительный случай (шаг cookies пропускается), ответ основной
навигации — реальный сетевой.

## Блокировка изображений, шрифтов и медиа (T-062)

Отчёт о всех методах оптимизации рендер-конвейера, проверенных на проде
A/B-замерами (успешные и отклонённые, 29.10–01.11.2026), —
[`optimizations.md`](optimizations.md).

ТЗ 5.6 требует не грузить изображения, шрифты и медиа (экономия ресурсов).
Механика — перехват запросов вкладки доменом CDP `Fetch` (в протоколе
больше нет `Network.setRequestInterception`; chromedp v0.21 даёт события
`fetch.RequestPaused`). `Session.Run` включает перехват **до** перехода в
порядке «подписка на события → `Fetch.enable` → навигация» — событие,
пришедшее до подписки, осталось бы без ответа и держало бы запрос до
таймаута страницы.

`Fetch.enable` получает паттерны по блокируемым типам — `Image`,
`Media`, `Font`, стадия `Request`: приостанавливается лишь то, что будет
отклонено (`Fetch.failRequest` с `BlockedByClient`, запрос не покидает
браузер). Остальные типы (`Document`, `Stylesheet`, `Script`, `XHR`,
`WebSocket`, …) браузер не приостанавливает вовсе: скрипты и XHR обязаны
грузиться (SPA-оболочки дорисовываются — рендер и существует ради JS), а
сбой слушателя не может повесить страницу (fail-open: блокировка —
экономия, а не условие корректности). Favicon, запрошенный страницей
(`link rel=icon`), идёт типом `Image` и блокируется; браузерный
`/favicon.ico` приходит типом `Other` и проходит (в headless-shell таких
запросов нет, URL-эвристика ради одного файла не оправдана). Паттерны
по доменам аналитики (T-214, следующий раздел) — дополнительные и
правилам fail-open подчиняются так же: судьбу каждого приостановленного
запроса решает слушатель.

Слушатель — горутина на контексте задачи: отвечает на каждый
`requestPaused`, завершается по `stop` (возврат из `Run`) или закрытию
сессии; `stop` дожидается выхода горутины (утечек нет, проверено `-race`).

### Блокировка CSS — опция `render.block_stylesheet` (T-213)

`Stylesheet` присоединяется к блокируемым типам тем же механизмом
(`blockTypes` в `internal/render/block.go`), когда включена опция
`render.block_stylesheet` (`CRAWLER_RENDER_BLOCK_STYLESHEET`). CSS —
оставшиеся 5–10% байт веса страницы и заметная часть style/layout CPU:
по ресёрчу 31.10 блок CSS+картинок даёт ещё −треть ко времени загрузки.

Дефолт `false` — риск: у редких сайтов JS читает computed styles и media
queries (`getComputedStyle`, `matchMedia`) — на не-применённых стилях их
логика и итоговый DOM могли бы отличаться, а с ним и вердикты детекции
Laravel. Поэтому решение о включении принимается по A/B на проде: диф
сигнатур Laravel до/после на одинаковой выборке (критерий — доля
расхождений детекции < 1%) и контроль темпа (не хуже текущего);
наблюдение после включения — те же метрики этапа (`/metrics`
render-worker, порт 9105). Скрипты и XHR опция не трогает: SPA-оболочки
по-прежнему дорисовываются — рендер и существует ради JS (ТЗ 5.6).

### Блокировка трекер-доменов — опция `render.block_tracker_domains` (T-214)

Веб-аналитика (GA, GTM, Метрика, Hotjar, …) приходит Script/XHR/Ping-
запросами — по типам её не отрезать (SPA-скрипты сайта обязаны
грузиться, ТЗ 5.6), а потери прямые: 5–15 запросов и 100–500 КБ на
страницу (замеры источников, ресёрч 31.10) плюс CPU таймеров трекеров,
продлевающих фазу «затишья» сети (T-063). Поэтому при включённой опции
`render.block_tracker_domains` (`CRAWLER_RENDER_BLOCK_TRACKER_DOMAINS`)
`Fetch.enable` получает **дополнительные** urlPattern-паттерны — по
одному на домен списка, без `resourceType` (ловит запрос любого типа).

Список доменов — константа пакета `blockTrackerDomains`
(`internal/render/block.go`), обновляемая: google-analytics.com,
googletagmanager.com, doubleclick.net, googleadservices.com,
googlesyndication.com, connect.facebook.net, hotjar.com, mc.yandex.ru,
mc.yandex.com, matomo.cloud, clarity.ms, mixpanel.com, fullstory.com,
amplitude.com, sentry.io. Принцип выбора: только домены, чьё единственное
назначение — аналитика/телеметрия/рекламные биды; НЕ CDN общего
назначения и не инфраструктура сайта, с которой грузится и полезный код
(исключены сознательно: yastatic.net, googleapis.com, jsdelivr — общие
статики; www.facebook.com — кнопки «поделиться» и редиректы наравне с
пикселем, из facebook взят только SDK-домен connect.facebook.net;
segment.io/segment.com — customer-data платформа, для сайта это
инфраструктура). Self-hosted Matomo/Sentry на домене самого сайта списком
не ловятся принципиально — свой домен сайта блокировать нельзя.

Точность — пара «широкий паттерн → точный вердикт». urlPattern в CDP —
glob с полным совпадением (`base::MatchPattern`: `*` — любая
последовательность), поэтому домен кладётся в паттерн звёздками:
`*google-analytics.com*` равно подстроке URL и ловит запросы любого
типа с этим доменом где угодно в адресе. Подстрока шире нужного
(путь сайта `/js/google-analytics.com.js` тоже приостанавливается) —
поэтому судьбу каждого приостановленного запроса решает точная хостовая
проверка `blockTrackerURL`: хост равен домену списка или его поддомен —
`failRequest`; иначе (подстрока в пути, userinfo, чужой суффикс вида
`google-analytics.com.evil.example`) — `continueRequest`. Инвариант
fail-open T-062 сохраняется: неблокируемое не приостанавливается вовсе,
а единственное намеренное исключение (подстрочная пауза чужого запроса)
живёт один цикл слушателя, смерть которого страхует fail-open
`Fetch.disable` насоса.

Дефолт `true` — отличие от `block_stylesheet` (T-213): трекеры не
участвуют в детекции Laravel (правила ищут сигнатуры фреймворка в
контенте и скриптах самого сайта, не в аналитике), остаточный риск —
экзотика, собирающая видимый контент тегами менеджера тегов; выгода
прямая, A/B не требуется. Контроль после включения — обычные метрики
этапа: темп и успешность рендера не хуже текущих. Live-проверка против
dev-стека — `TestBlockLiveTrackerDomains` (запуск с `--use-aliases` —
трекер-домены для теста резолвятся DNS-алиасами в run-контейнер, см.
докомментарий `block_live_test.go`).

## Ожидание готовности страницы (T-063, ТЗ 5.6)

После перехода `Session.Run` ждёт готовность в две фазы (стратегия —
`wait.go`, план `DefaultWaitPlan(render.timeout)`):

```
NavigateResponse (переход; само ждёт загрузку — T-064)
  → событие загрузки Page.loadEventFired, потолок = 1/2 таймаута
  → «затишье» сети: окно 2 с без новых Network.requestWillBeSent,
    потолок фазы = 1/5 таймаута
  → съём результата
```

- **Событие загрузки** — подписка `chromedp.Events(page.LoadEventFired)`
  ставится до перехода (буферизуется с момента подписки, события не
  теряются). Используется стартовая команда `Page.navigate`, а не
  `chromedp.Navigate`: последний сам ждёт конца загрузки без отдельного
  потолка — висящая страница съела бы бюджет до фазы затишья. У SPA load
  наступает до дорисовки — дорисовку ждёт следующая фаза.
- **Затишье сети** — окно 2 с без *новых* запросов: каждый
  `Network.requestWillBeSent` (домен `Network` включается на вкладку)
  запускает окно заново; запросы, ушедшие до входа в фазу, к окну не
  относятся. Значение 2 с — верх рекомендованного диапазона 1.5–2 с:
  цепочка XHR SPA укладывается в ~1 с, окно берётся с запасом и платится
  один раз на страницу.
- **Потолки фаз — мягкие**: истёк потолок (зависший подресурс, непрерывный
  фон аналитики/поллинга) → идём дальше, итог снимается как есть — «затишье»
  по ТЗ ограничено и снизу, и сверху. Доли бюджета (1/2 и 1/5) оставляют
  ~30 % на съём результата; окно затишья — константа темпа запросов сайта,
  но не больше половины потолка фазы, иначе при малых `render.timeout`
  окно не подтвердилось бы никогда.
- **Общий таймаут** `render.timeout` (25 с по умолчанию, ТЗ 5.6/5.10) —
  обёртка всего визита. Его истечение — **ошибка задачи** (`task`), а не
  частичный результат: по ТЗ §8 прерывание по лимиту фиксируется кодом
  ошибки, «частичного» DOM в схеме нет — замена полного сырого HTML
  недорисованным DOM (T-067) без маркера хуже повтора; сырой HTML уже
  сохранён HTTP-этапом, а рендер — асинхронное дополнение (ТЗ §7), неудача
  уходит на повторную доставку очередью (T-066).

## Классификация ошибок

Все ошибки пакета — `*render.Error` с классом (`render.ClassOf`):

| Класс | Причина | Реакция |
|---|---|---|
| `task` | таймаут страницы, отмена контекста задачи, `net::ERR_*` | повторная доставка — уровень очереди (T-066) |
| `context` | изолированный контекст умер (вкладка/рендер упали, профиль не отвечает) | `Pool` повторяет один раз на новом контексте |
| `browser` | Chromium недоступен / соединение потеряно | `Manager` (T-065) перезапускает браузер и повторяет задачу (до двух раз), пул не повторяет |

Классификация идёт по состоянию контекстов и соединения (не по текстам
ошибок): отмена контекста задачи и таймаут — по контекстам; смерть
браузера — `LostConnection`/отмена браузерного контекста; смерть вкладки —
отмена её контекста либо живой зонд (простейший `Evaluate`, chromedp не
отменяет контекст вкладки при её падении). Код ошибки загрузки страницы
(`net::ERR_*`) при этом доступен структурно — `render.LoadErrorCode`
(поле `chromedp.LoadError.ErrorText`, не разбор текста); потребители —
политики постоянных ошибок сертификата (T-159) и DNS-отказа (T-211),
разделы ниже.

## Цикл очередей (T-067, ТЗ 5.6/§5.7/§7)

Потребитель q:render — пакет `internal/renderworker`, цикл
`renderworker.Run` в `cmd/render-worker`. Стрим потребления — параметр
сборки воркера (T-236, ФТ-12): `renderworker.Options.Stream` (дефолт
`DefaultStream` = q:render, отдельные точки проводки — чтение цикла,
клейм RecoverLoop и коллектор глубины `crawler_queue_depth` в
`cmd/render-worker`); воркер фолбэка рендера (ТЗ фолбэка, §4.5) — тот же
бинарь другой сборкой: стрим q:render-fallback и отдельная группа
потребителей. Задача — `Result`-сообщение
(ключ строки `subdomain_results`, T-024); итоговый URL читается из
строки, сообщение идентификаторов не раздувает (ТЗ 4.2). Обработка
одной доставки — порядок «запись в БД → публикация → XACK» (ТЗ 4.2):

```
SELECT строки (final_url, content_hash)
  → Pool.Run (изолированный контекст, DOM + cookies + заголовки)
  → ContentStore.Put(DOM)                          — +1 новой ссылке
  → транзакция: UPDATE строки (rendered = true, content_hash = DOM,
      final_url/cookies/headers рендера, rules_version = NULL)
      + SwapRefTx(old, нулевой)                    — −1 старой ссылке
  → Publish q:analyze (тот же ключ; под гейтом T-026)
  → XACK (Processing, T-025)
```

- **Идемпотентность повторной доставки** (ТЗ 3.4): перезапись без охраны
  `rendered` — повторный рендер перезаписывает контент и refcount
  (баланс в духе T-058); DOM побайтово равен сохранённому — `Put` и
  своп пропускаются.
- **Гонка с перепроверкой** (recheck T-030 перезаписывает строки
  DELETE+INSERT, T-058) закрыта оптимистической охраной UPDATE по
  `content_hash`: изменившаяся строка не перезаписывается (0 строк —
  ссылка `Put` снимается, доставка подтверждается: задача была про
  прошлый эпизод).
- **Алиасы** (T-055) рендерятся по своему итоговному URL и получают
  собственную ссылку на DOM: профили изолированы, класс эквивалентности
  — оптимизация HTTP-этапа (не качать дважды), а не запрет записи
  владеть контентом.
- **`rules_version` сбрасывается в NULL**: контент сменился, повторная
  публикация q:analyze (§7) переанализирует запись свежими правилами
  (T-068+ проставит новую версию).
- **Флаг `render_pending`** (T-066) render-worker не трогает: владелец
  флага — HTTP-этап, его проход доработки снимает бит после публикации
  q:render; рендер меняет только строку результата (§7 — домен уже
  `done`, рендер асинхронное дополнение). Переходы бита (постановка в
  записи результата, снятие проходом) ведут счётчик рендер-долга
  `crawler_counters['render_pending']` (T-175) той же транзакцией —
  наблюдаемость долга без счёта по маске флагов (gauge
  `crawler_render_pending_domains`, алерт `render_debt`); render-worker
  счётчика тоже не касается. Формализованная спецификация автомата
  «бит × счётчик долга» (состояния, переходы, инварианты) — doc-комментарий
  `internal/httpworker/renderq.go` (T-258, ТЗ-fsm §3 ФТ-4).
- **Недоступный браузер** (зонд `browser.Alive` в `Options.Alive`):
  цикл приостанавливает потребление — доставки остаются в стриме
  непрочитанными, а не в PEL без XACK; перезапуск браузера — T-065.
  Ошибка старта Chromium — ошибка OnRun (код 1, Restart=on-failure).
- **Сбои**: ошибка рендера (класс task — `net::ERR_*`) и `ErrStoreFull`
  — доставка без XACK, вернётся повторной доставкой; `ErrTooLarge`
  (DOM раздут JS) — постоянное свойство страницы, попытки исчерпаются
  и задача уйдёт в q:dead (T-025) на разбор оператором.
- **Политика таймаутов** (T-148): таймаут страницы (`render.timeout`) —
  предсказуемый тарпит, а не случайная ошибка. Пока номер доставки
  (счётчик PEL, `ProcessingAttempt`/`RecoverLoopAttempt`) ниже
  `render.timeout_attempts` — обычный повтор (без XACK, клейм); на
  исчерпании лимита запись **финализируется без рендера**: итог — сырой
  HTML HTTP-фазы (`rendered = false`), публикация q:analyze, XACK —
  тяжёлая страница не уводит работу в q:dead (там остаются только
  инфраструктурные ошибки; разбор накопившегося — runbooks §2.5).
  Доля финализаций — метрика `crawler_render_tarpit_finalized_total`
  (с меткой `engine` сборки — S-P2-4: тарпит движко-зависим, метка
  атрибутирует его движку).
- **Постоянные ошибки сертификата хоста** (T-159, расширение T-172):
  `ERR_CERT_AUTHORITY_INVALID` (сертификат не издан доверенным ЦС),
  `ERR_CERT_COMMON_NAME_INVALID` (не покрывает имя хоста) и
  `ERR_CERT_DATE_INVALID` (просрочен/ещё не действует — добавлен по
  замеру T-172: за сутки 321 первая неудача, успешных ретраев 0, 92%
  исчерпали попытки в q:dead; окно продления сертификата парковки —
  дни — много шире окна ретраев — 3 доставки, ~полчаса) — свойства
  хоста, ретрай до смены сертификата самим хостом бессмысленен.
  Cert-класс распознаётся структурно — код `net::ERR_*` читается из
  `chromedp.LoadError` (поле ErrorText, обёртка `render.LoadErrorCode`),
  а не разбором текста ошибки — и финализируется той же механикой, что
  тарпиты, но **с первой же доставки**: тарпит-лимит даёт странице шанс
  в изменившихся условиях, у сертификата шанса нет. Итог записи — сырой
  HTML HTTP-фазы (`rendered = false`), публикация q:analyze, XACK:
  cert-хосты не жгут попытки доставок (замер §12: ~27% попыток рендера —
  cert-ошибки, до 4 доставок на хост до q:dead) и не уводят работу в
  q:dead. Штамп `render_failed_at` (T-210) фиксирует невозможность до
  смены контента, колонку `error` финализация не трогает — она
  принадлежит HTTP-проверке (ErrorClass T-058, её перезапись лгала бы об
  HTTP-фазе); итог несёт сама финализация — сырой HTML остаётся
  результатом (частичный результат по ТЗ §8), запись уходит в анализ;
  наблюдаемость — метрика `crawler_render_cert_finalized_total`. Маркер
  живёт до смены контента строки, не вечно: следующий эпизод
  перепроверки (T-030) перезаписывает строку (маркер — NULL) и публикует
  новую задачу q:render — с исправленным сертификатом рендер пройдёт.
  Список кодов закрыт намеренно: сетевые коды (`ERR_CONNECTION_REFUSED`
  — хост может подняться) остаются повторимыми ошибками до последней
  доставки (политика T-172 ниже); DNS-отказ — отдельный класс,
  следующий пункт.
- **DNS-отказ хоста** (T-211, по итогам T-207): `ERR_NAME_NOT_RESOLVED`
  — смерть хоста на уровне DNS. Запись попала в q:render через живой
  HTTP-эпизод (HTTP-фаза сама резолвила имя — иначе эпизода и строки не
  было бы), а браузер резолвит системным резолвером — тем же unbound,
  что обслуживает DNS-этап: отказ между эпизодом и рендером значит, что
  DNS хоста умер. Возврат DNS — событие масштаба дней, окно ретраев
  (3 доставки, ~20 мин в PEL по `redis.claim_min_idle`) его не покрывает
  — тот же аргумент детерминированности, что у `ERR_CERT_DATE_INVALID`
  (T-172: окно изменения свойства много шире окна ретраев). Замер T-207
  (29.10): 252 финализации `NAME_NOT_RESOLVED` за ~7 ч, каждая съедала
  все 3 доставки и ~20 мин PEL. Класс распознаётся структурно (код
  `net::ERR_*` из `chromedp.LoadError`, как у cert-класса) и
  финализируется той же механикой **с первой же доставки** по образцу
  cert-класса: итог — сырой HTML HTTP-фазы (`rendered = false`),
  публикация q:analyze, XACK — мёртвый хост не ест 3 доставки и не
  висит в PEL. Маркер `render_failed_at` (T-210) живёт до смены
  контента: следующий эпизод перепроверки (T-030) перезаписывает строку
  (маркер — NULL) и публикует новую задачу q:render — хост с вернувшимся
  DNS отрендерится; наблюдаемость — метрика
  `crawler_render_dns_finalized_total` (критерий T-211: −2 доставки на
  мёртвом хосте, счётчик растёт при нулевом приросте q:dead).
  `ERR_CONNECTION_REFUSED` в класс **не входит**: отказ соединения —
  свойство сервиса хоста (порт закрыт/фильтр/перезапуск),
  восстановление наблюдается — замер T-172: 6.6% ретраев успешны — он
  остаётся повторяемым до последней доставки (следующий пункт).
- **Последняя попытка × класс задачи** (T-172): прочая ошибка рендера
  класса `task` — отказ соединения, load error (свойство
  хоста, не инфраструктуры) — живёт общим путём повторных доставок,
  пока номер доставки (счётчик PEL, `ProcessingAttempt`) ниже
  `redis.max_attempts` (восстановление хостов наблюдается: замер T-172 —
  6.6% ретраев `ERR_CONNECTION_REFUSED` успешны), а на последней
  доставке запись **финализируется без рендера** по образцу тарпитов:
  итог — честный сырой HTML HTTP-фазы (`rendered = false`), публикация
  q:analyze, XACK — работа не уходит в q:dead (инцидент 23.10: волна
  459 смертей за 11 минут на токсичной смеси .рф-парковок — смешанная
  серия таймаут→refused не дотягивала до тарпит-финализации T-148 и
  пережигала все доставки). Инфраструктурный класс (БД, хранилище,
  публикация, браузер, отмена ctx) финализацией не покрывается —
  прежний путь `redis.max_attempts` → q:dead; q:dead остаётся только
  настоящим инфраструктурным ошибкам (в духе T-148). Маркер живёт до
  смены контента строки, не вечно: следующий эпизод перепроверки (T-030)
  перезаписывает строку (маркер — NULL) и публикует новую задачу q:render
  — поднявшийся хост отрендерится. Наблюдаемость — метрика
  `crawler_render_task_finalized_total{reason}` (код `net::ERR_*`,
  `timeout`, `other`).
- **Публикация фолбэка** (T-238, ТЗР этапа 35 §4.4, ФТ-7/8/10/14): при
  включённом `render.fallback.enabled` движко-зависимые кандидаты — тарпит
  T-148 и класс задачи T-172 на последней доставке (свойство пары
  «сайт × движок»: зависшая на лёгком движке страница может открыться в
  chromium) — не финализируются, а публикуются в `q:render-fallback`
  (`publishFallback`): запись остаётся без маркера и без q:analyze
  («ждёт фолбэка» — состояние живёт в очереди и метриках, ТЗР §4.8),
  дорабатывает её chromium-воркер B (тот же бинарь, ТЗР §4.5): успех —
  штатный путь (`rendered = true`, публикация q:analyze), исчерпание
  попыток — финализация с маркером. DNS-класс T-211 и cert-класс T-159
  фолбэка не получают при любом флаге (движко-независимые свойства
  хоста, ФТ-7). Порядок — «публикация → XACK» по образцу связи
  финализации с q:analyze: сбой публикации — ошибка без маркера,
  доставка вернётся и повторит попытку. Идемпотентность: повторная
  доставка уже опубликованной записи не даёт вторую запись в стриме —
  фильтр дубля по идентификатору записи (ключ строки + `checked_at`
  эпизода: доставки одного эпизода читают тот же `checked_at`,
  перезапись эпизода перепроверкой T-058 пишет новый — свежий эпизод
  легитимно проходит фолбэк заново, контентный `content_hash` эпизод
  не идентифицирует — совпал бы у эпизодов с тем же контентом; память
  процесса с ёмкостью выше потолка стрима, дубль после рестарта
  допустим и гасится консьюмером B, ФТ-11); уже отрендеренная к
  моменту дубля строка не публикуется вовсе. Публикация идёт
  только из стрима q:render — воркер B фолбэк не публикует (рекурсия
  запрещена, ФТ-10) — и только с движка-кандидата: движок сборки
  chromium (включая пустое значение `render.engine`) фолбэк не
  публикует вовсе — chromium сам себе не фолбэчится (шаг 1 приёмки
  ТЗР §6.2 п.2: включение фолбэка без смены движка оставляет
  q:render-fallback пустой; откат §6.4 п.1: возврат воркеров на
  chromium гасит публикацию сам, без смены флага — воркер B
  дорабатывает накопленное до пуста). Решение о публикации — чистая функция
  `fallbackPublishDecision` (кандидат × health-гейт × бюджет доли,
  T-239, ФТ-9); отказ любого входа приостанавливает публикацию (гейт —
  до восстановления движка, бюджет — до конца окна) — задача
  финализируется по-сегодняшнему (маркер `render_failed_at` +
  q:analyze), без потерь. **Health-гейт** (ФТ-9а,
  ТЗР §4.4 п.3): стрик инфра-ошибок класса браузера (ClassBrowser —
  основной движок недоступен) с последнего успешного рендера числом
  `render.fallback.health_gate_streak` (дефолт 3) закрывает публикацию
  до восстановления — успешный рендер обнуляет стрик (образец
  `renderFailBackoff`: обнуление успехом, нарастание сбоем; ошибки
  классов задачи/контекста и штатные отказы без рендера стрик не
  трогают — тарпиты есть и у здорового движка, no-op рендера не
  выполнял), единичная
  инфра-ошибка — шум живого потока, лежачий движок даёт стрик за
  секунды; сами browser-задачи при этом ждут в redelivery q:render —
  класс инфраструктурный, финализацией не покрывается (в пределах окна
  ретраев `redis.max_attempts`; затяжной простой движка уводит их в
  q:dead на ручной разбор — пре-существующее поведение T-025).
  **Бюджет доли**
  (ФТ-9б, ТЗР §4.4 п.4): доля публикаций за окно в 1000 подтверждённых
  доставок этапа сверх потолка `render.fallback.share_percent` (дефолт
  30, `0` — без потолка) приостанавливает публикации следующего окна:
  приостановленное окно публикаций не набирает, закрытие сбрасывает
  счётчики и фолбэк возобновляется (самовозврат) — штормовой
  размыкатель с алертом, не критерий канарейки. Состояния гейта и
  бюджета — память процесса воркера (рестарт обнуляет: стрик
  набирается заново за секунды, окно — за минуты; при нескольких
  инстансах рендера потолки действуют на инстанс — сегодня инстанс
  один, docs/deploy §2.2). События приостановок —
  `crawler_render_fallback_suspended_total{reason=gate|budget}`
  (одно на защёлкивание; материал алертов ТЗР §4.6 п.3). Наблюдаемость
  публикаций — `crawler_render_fallback_published_total{reason}`
  (словарь `taskFinalizeReason`: код `net::ERR_*`, `timeout`, `other`).
  Потребление — `crawler_render_fallback_consumed_total{result}`
  (T-245, считает только сборка воркера B: `rendered` — доработка успешна,
  `finalized` — исчерпание фолбэка, запись закрыта путём финализации
  (маркер `render_failed_at`, пока строка принадлежит эпизоду), `skipped`
  — строка ушла из-под задачи (строки нет, без итогового URL, охрана
  UPDATE отсекла) — доставка закрыта без побочных эффектов). Серии
  замкнутых словарей приостановок `{gate,budget}` и потребления
  `{rendered,finalized,skipped}` предсозданы нулевыми в NewMetrics
  (S-P1-4): семейства видны в `/metrics` с первого старта — алерт
  бюджета не простаивает в «не измеряется» на тихом проде и зонд не
  теряет первое событие (до предсоздания первая точка ленивой серии
  базировала prev и дельта 0→1 не срабатывала); открытые словари
  (`reason` кодов `net::ERR_*` у published/finalized) предсоздания не
  имеют — коды не перечислимы, серия рождается первой финализацией.
  Баланс-чек шага 4 приёмки ТЗР §6.2:
  `increase(published) = increase(consumed) + crawler_queue_depth
  {queue="q:render-fallback"} + increase(crawler_queue_dead_buried_total
  {queue="q:render-fallback"}) + increase(crawler_queue_dead_unidentified_total
  {queue="q:render-fallback"})` (глубина — коллектор сборки B:
  непрочитанный лаг + PEL; похороненные — ошибки классов
  браузера/инфраструктуры на исчерпании попыток; неидентифицируемые —
  записи без task_id, T-260: стационарно ноль, появляются только при
  публикации мимо контракта пакета), сверка по приростам
  между рестартами, при дренированной очереди остаток нулевой;
  формула и границы применимости — docs/services.md.
- **Маркер «рендер невозможен» `render_failed_at`** (T-210, миграция
  000017): все четыре финализации выше штампуют запись — финализированная
  без рендера строка навсегда `rendered = false` и до маркера была
  неотличима от «не пробовали», проход доработки переиздавал её без
  разбора (замер T-207: хвост ~180–220 тыс. битых записей). Исключение —
  публикация фолбэка (T-238, следующий пункт): тарпит и класс задачи при
  включённом фолбэке запись не маркируют. Выборка
  записей прохода (`renderPendingRowsSQL`) исключает отмаркированные
  (`render_failed_at IS NULL`) — прекращаются ПОВТОРНЫЕ издания:
  повторный проход по домену, чей флаг пережил публикацию (частичный
  сбой публикации — опубликованная часть финализируется за секунды,
  повтор издал бы её снова; выход Full после публикации соседей пачки;
  keep нечитаемого контента; рестарт между публикацией и снятием).
  Первая попытка свежего эпизода легитимна и не подавляется
  (перезапись эпизода сбрасывает маркер). Все записи домена
  отмаркированы — флаг `render_pending` снимается без публикации
  («черновой», как у страницы, переставшей быть SPA). Штамп ставится до
  публикации q:analyze с оптимистическими охранами (контент — как у
  замены контента; `rendered = false` — конкурентный рендер закрыл
  вопрос), значение — первая финализация (`coalesce`); сбрасывается
  перезаписью эпизода (DELETE + INSERT записи результата, T-058 —
  починившийся хост отрендерится на следующем эпизоде перепроверки
  T-030) и успешным рендером (`renderUpdateSQL`); инвариант:
  маркер ⇒ `rendered = false`. Контроль эффекта (критерий T-210 — доля
  отмаркированных в выборке прохода → 0; фильтр по доменам с флагом —
  знаменатель и есть кандидаты прохода, отдельные зоны — фильтром
  `d.zone_id`; seq scan по `subdomain_results` — редкий ad-hoc замер,
  на Live выполнять осознанно, см. T-201 о стоимости проходов):

  ```sql
  SELECT count(*) FILTER (WHERE r.render_failed_at IS NOT NULL)::float
         / nullif(count(*), 0) AS marked_share
  FROM subdomain_results AS r
  JOIN domains AS d ON d.zone_id = r.zone_id AND d.id = r.domain_id
  WHERE (d.flags & 2) <> 0
    AND r.rendered = false AND r.final_url IS NOT NULL;
  ```

Выборка пачки проходом доработки — без PK-порядка (T-181): ORDER BY по
PK держал index scan по `domains_default_pkey`, который при живом долге
вытаптывает дренированный «пустой» префикс PK-порядка — запрос №2
журнала медленных 24.10 (137 срабатываний >3 с за 2,7 ч, медиана 44 с,
max 143 с: 14,1 млн Rows Removed by Filter, ≈4,5 ГБ буферов за вызов;
без ORDER BY план тот же — статистики выражения `(flags & 2) <> 0` нет,
селективность оценена как 41,6/41,6 млн). Порядок доменов не важен
(решение оператора 24.10: снятие флага после публикации исключает
повторы), форма плана закреплена в `renderSelectPending` транзакцией
`SET LOCAL enable_indexscan/bitmapscan/indexonlyscan = off` (все
индексные формы доступа к domains закрыты — index-only по PK повторил
бы патологию) — seq scan находит первую сотню флаговых строк ранним
остановом LIMIT (флаговый долг `.рф` физически в начале кучи: ingest
ru/rf/su шёл первым, HOT-апдейты держат версии на родных страницах) —
43 мс против 30 с на замере 24.10 (700×). Физическая локальность —
эмпирический факт, а не контракт: при изменении раскладки кучи seq scan
подорожает — контроль журнал медленных (T-177), системная альтернатива
(keyset-курсор) сознательно отложена. Стационар без долга тяжёлый SELECT
не выполняет вовсе: guard точечным чтением
`crawler_counters['render_pending']` (T-175) — `value = 0` → пустая
пачка без обращения к `domains` (одно чтение строки за тик). Граница
доверия guard: бит и счётчик ведёт код парой ±1; при `value > 0` и
отсутствии выбираемых флагов проход платит полный seq scan за тик
(Warn «счётчик долга > 0, выборка пуста»): рассинхрон ручного SQL либо
биты-«сироты» — удалённые домены с флагом, которых выборка честно не
видит (§13.1); штатный источник сирот закрыт T-186 — применение delete
снимает бит и декрементирует счётчик той же транзакцией, остаток — хвост
удалённых до T-186 (разовая чистка) и дрейф, гасимый реконсиляцией;
чистка — [`runbooks.md`](runbooks.md)
§6. Темп дренажа ограничивают ворота q:render (T-174), а не выборка;
стартовый дренаж не крутится по пачке без прогресса (нечитаемый
контент) — ждёт следующего тика.

Хранилище контента и учёт refcount — [`content.md`](content.md)
(раздел «Замена контента рендером»); браузерные live-тесты к циклу не
относятся (юнит-тесты `internal/renderworker` — на фейках без БД/Redis;
сквозной прогон конвейера на testbed — интеграционные тесты
`test/integration`).

Счётчик долга читает и retention контента (T-185): записи доменов с
флагом `render_pending` исключаются из чистки критерием отбора, а курсор
дренажа retention по времени проходит их молча — при живом долге срез
за курсором копится. Точечное чтение
`crawler_counters['render_pending']` в начале каждого часового прохода
retention ловит переход счётчика в 0 — момент снятия всей рендер-защиты
разом — и планирует один catch-up-круг с нулевого курсора: догоняет всё
накопленное за эпоху долга, частота кругов следует фактам дренажа долга,
а не часам; до деплоя строки счётчика (миграция 000015) retention
держит fallback-круг раз в сутки. Контракт счётчика не расширяется —
обе стороны только читают (guard прохода доработки и catch-up retention
одним и тем же оператором).

### Поздний переиздатель: страховка потерянных задач (T-259)

Автомат рендер-состояния строки (спецификация — doc-комментарий
`internal/renderworker/worker.go`, ТЗ-fsm §3 ФТ-5: `новый эпизод → в
очереди → отрендерена | невозможна | ждёт фолбэка | ушла из-под
задачи`; бесколоночное «ждёт фолбэка» наблюдаемо балансом
`published = consumed + остаток q:render-fallback + buried`) имеет
слабое место: состояния «в очереди» и «новый эпизод» различимы только
вне строки — битом `render_pending` домена или сообщением стрима.
Потеря сообщения (MAXLEN-обрезка `q:render-fallback` до доставки,
T-025/T-238; сбой/потеря публикации `q:render`) оставляла запись
навсегда «вечно молодой»: без бита, без сообщений, неотличима от «не
пробовали» — её закрывала только перепроверка эпизода (месяцы).

Поздний переиздатель — фоновый проход `httpworker.RenderLateLoop`
(T-259, ФТ-5.3; живёт в http-worker рядом с проходом доработки, раз в
минуту, пачки по 1000 строк, курсор по PK — полный цикл по таблице
порядка месяца, быстрее `scheduler.recheck_interval`): записи
`rendered = false AND final_url IS NOT NULL AND render_failed_at IS
NULL` старше 6 ч, у домена без бита `render_pending` (долгом владеет
проход доработки — дубль изданий исключён делением владения) и без
непотреблённых сообщений `q:render`/`q:render-fallback` (интерлок
снимком стримов, образец `content/retentionpending.go`; адаптер —
`retentionPending` в `cmd/http-worker`, тот же, что у защиты retention)
— переиздаются в `q:render`. SPA-вердикт — повторный, по сохранённому
контенту (`DetectSPA`, как у прохода доработки; предикат возраста —
супермножество: не-SPA записи под колонки подходят неограниченно долго,
издание без вердикта залило бы очередь перепроверкой всех страниц);
алиасы наследуют вердикт оригинала (T-055) — от кандидата по телу ИЛИ
от уже отрендеренного оригинала (факт рендера доказывает SPA-класс:
публикации q:render идут только по SPA; контент такого оригинала — DOM
и вердикту по телу не соответствует — ревью T-259 P2-1), записи без
контента и без алиаса пропускаются (вердикт взять неоткуда — доработает
следующий эпизод перепроверки; старше окна retention контента нет —
ходить туда бессмысленно). Курсор двигается только за пачку,
отработанную целиком: полная очередь (Full) или ошибка публикации/снимка
оставляют его на месте — следующий тик повторит пачку, дубль ограничен
и гасится идемпотентностью потребителя (§3.4). Ошибка чтения снимка
стримов — консервативный пропуск прохода: переиздавать «наугад» дороже
тика (дубль живой задачи — именно то, что интерлок исключает).

Наблюдаемость: `crawler_render_late_republish_total` — стационарно не
растёт; рост после инцидента (обрезка стрима, потеря Redis) — дренаж
потерь, спад до нуля — дренаж завершён. Интеграционные тесты —
`test/integration/render_late_test.go` (потерянная запись → публикация;
запись в стриме или под битом → не трогается; CHECK-инвариант схемы).

Инвариант «отрендерена ⇒ без маркера» с T-259 держит и схема: CHECK
`subdomain_results_rendered_check (rendered = false OR
render_failed_at IS NULL)` — миграция 000018, добавлена `NOT VALID`
(без сканирования 40+ млн строк; новые и изменяемые записи проверяются
сразу, существующие не задеты — их инвариант всегда держали SQL-охраны
писателей). `VALIDATE CONSTRAINT` — отдельным шагом по регламенту
(`docs/schema.md` «CHECK-инварианты»): на секционированном родителе
PG16 валидация рекурсивна на все секции одним оператором, новые секции

### Воркер B фолбэка: сборка и темп потребления (T-240)

Воркер B — потребление `q:render-fallback` отдельной группой
`render-fallback-worker` (каноническая пара стрима, `queue.WorkingGroups`)
с потолком темпа `render.fallback.worker_rate` (ФТ-13): тот же бинарь
`render-worker` другой сборкой — переключатель `RENDER_WORKER_STREAM`
(параметр запуска, как `METRICS_ADDR`; стрим потребления — параметр
сборки воркера, не конфигурации, ТЗР §4.1 п.3). Успех — штатный путь
(DOM, `rendered = true`, q:analyze); движко-зависимый сбой на исчерпании
попыток — финализация с маркером `render_failed_at` (рекурсивный фолбэк
запрещён, ФТ-10: `publishFallback` не публикует со стрима фолбэка).

Темп — скользящее окно `renderworker.RateWindow` (1 мин): читатель цикла
`Run` перед каждым чтением урезает пачку до свободных слотов окна
(`Options.Rate` — общий параметр, без ветвлений по движку/стриму,
действует когда задан; основная сборка q:render читает без потолка),
исчерпанное окно держит паузу до выхода старейшей записи. Пустое чтение
бюджет не расходует — при пустой очереди воркер простаивает в блоке
XREADGROUP с полным потолком. Клейм RecoverLoop потолком не ограничен:
темп возврата зависших доставок — `redis.recover_*` (T-153), отдельная
ручка. Дефолт 100/мин ≈ полной мощности одного chromium (8 контекстов ×
~5 с/страница) — батч-режим «собрать и доработать» без наращивания
chromium-мощности (ТЗР §3 п.3); очередь копится сколько нужно (MAXLEN
T-237), калибровка потолка — стендовым прогоном (ТЗР §4.4 п.4). Воркер B
держит темп и при выключенном `render.fallback.enabled` — накопленное
дорабатывается до пуста (ФТ-14).

Развёртывание — по образцу существующих рендер-воркеров
([`deploy.md`](deploy.md) §2.3): docker-runtime — сервис `render-fallback`
профиля `runtime` (сегодняшний render-образ с собственным
headless-shell, без изменений; профиль —
`deploy/docker/config.render-fallback.yaml`), нативно — юнит
`crawler-render-fallback-worker.service` на общий chromium
(`crawler-chromium.service`): recycle-пара T-208 применима как есть —
`ExecStart` ресайкла перезапускает именно этот общий юнит, новых файлов
не нужно.

### Приоритет зон прохода доработки (T-184)

Реализация решения (а) T-176 (оператор 24.10: рендерим всё, ничего не
теряем; зоны с высоким DOM-вкладом — вперёд, парковочные `.рф` — по
остаточному принципу): непустой `render.requeue_deprioritized_zones`
(список имён зон в punycode, прод — `xn--p1ai`; конфиг — таблица раздела
`render` в [`configuration.md`](configuration.md)) делит выборку пачки
прохода на две ступени БЕЗ сортировки — сначала домены зон НЕ из списка
(`z.name <> ALL(…)`), при исчерпании первой ступени (пачка неполная —
LIMIT не сработал, seq scan дошёл до конца таблицы) остаток пачки
добирается зонами списка (`z.name = ANY(…)`). Обе ступени — в тех же
транзакциях закрепления плана (фильтр по имени зоны в JOIN с малым
справочником zones не меняет форму: seq scan по domains с ранним
остановом, индексные формы отключены), физическая локальность флагового
`.рф`-долга в начале кучи играет на пользу второй ступени. Очередь долга
не теряет записей: всё дорабатывается, зоны списка — последними; ворота
`q:render` (T-174) дозируют публикации — приоритет распоряжается
освободившейся ёмкостью. Публикация SPA-результатов живой проверки
(`renderSPAResults`) не приоритизируется — её дозируют те же ворота;
недоставленный хвост стрима дренируется FIFO как есть.

Порожний проход исчерпанной первой ступени — полный seq scan по domains
(та самая патология запроса №2 журнала медленных) — цикл прохода не
повторяет, пока счётчик рендер-долга сходится с ожиданием (значение на
момент доказательства исчерпания минус свои снятия). Возобновление — по
любому расхождению: рост счётчика (новая постановка бита **любой** зоны,
в т.ч. зоны списка — отличить приток по одному счётчику нельзя, и
перестраховка дешевле потерянной приоритетности; пачка новых флагов
между тиками амортизируется в один повтор) и убывание сверх своих
снятий (второй экземпляр прохода, ручной SQL — runbooks §6). Доказательство
снимается и без расхождения счётчика, если хоть один домен первой
ступени пачки остался с флагом (keep при нечитаемом контенте, ранний
выход Full/ошибка): выборка эти строки видела, но проход не доработал —
пропуск первой ступени зажал бы застрявший приоритетный долг навсегда.
Граница эффективности: при непрерывном притоке флагов зон списка (ворота
закрыты, .рф-эпизоды перепроверки) повторы пустой первой ступени идут
чуть ли не каждый тик — память экономит ровно на паузах притока; контроль
после деплоя — журнал медленных (T-177) по запросу `z.name <> ALL(...)`:
при регулярных полных сканах системный ответ — отдельный счётчик
приоритетных постановок бита (расширение T-175), не ослабление
корректности. Разовый `RequeueOnce` памяти не держит — обе ступени
исполняются честно.

Наблюдаемость — поле `deprioritized` строки «проход доработки рендера»
журнала http-worker (домены пачки из зон списка): `0` в окне дренажа —
приоритет работает, публикации идут зонами не из списка вперёд; рост —
первая ступень исчерпана, дренаж дошёл до отложенных зон (контроль
порядка без ручного SQL). После дренажа ru/com — повторный замер
`deploy/sql/t176-dom-share.sh` (закрыть неизвестный DOM-вклад
непарковочных классов); контрольная выборка переанализом — кандидаты
dom_only/needs_dom замера T-176, включая Livewire-сайт
`xn--80afc7aid1a.рф` (прямой тест ложного SPA-вердикта).

Спорных правил нет — `target` в `rules/laravel.yaml` однозначен.
Ключевой нюанс rendered-записей (T-067): рендер **перезаписывает**
`cookies` (весь jar браузера, включая httpOnly и выставленные JS) и
`headers` (итоговая навигация) — анализатор (`analyzeSelectSQL`) для
rendered-строки читает данные рендера, а не исходной HTTP-фазы.
Поэтому наличие H-сигнала у rendered-находки ≠ «находка была бы и без
рендера»: часть H-сигналов тоже может быть обязана рендеру (js-куки,
куки с XHR-эндпоинтов Sanctum). Замер снимает две наблюдаемые оценки,
каждая из которых может смещаться в обе стороны:

- **dom_only**: `is_laravel` ∧ `rendered` ∧ в `signals` нет ни одного
  H-правила — видимый состав находки чисто контентный. Может завышать
  обязанность рендера (server-rendered Livewire несёт `wire:*` в сыром
  теле — при ложном SPA-вердикте сигналы были и без рендера) и не
  ловит находки, чьи H-куки получены рендером;
- **needs_dom**: `is_laravel` ∧ `rendered` ∧ noisy-OR score только
  H-сигналов < порога 0.6 (`analyzer.laravel_min_score`, боевое
  значение) — контентные сигналы обязательны для прохождения порога по
  текущему составу `signals`. Включает dom_only (H-score = 0). Не ловит
  находки, ставшие находками только благодаря кукам рендера (H-score
  перевалил порог уже в H-части): их обязанность рендеру скрыта.

Оба смещения ограничены эмпирически (пограничный класс ниже): класс
js-куков/XHR-куков пренебрежим, а parking-куки доступны и в сырой
фазе. Оценки задают порядок величины, а не доверительный интервал.

  ограничены эмпирикой (класс js-куков пренебрежим, parking-куки
  измерены в сырой фазе у 86,4% не-rendered находок), но доверительным
  интервалом оценки не являются — только порядком величины.
- Замер «до/после рендера» для одной записи невозможен и по окну
  свежести: findings rendered-строки пишутся переанализом после рендера;
  на снапшоте строк без переанализа 0, но окно существует теоретически
  (запрос 7 скрипта).
- C-сигнал в принципе мог присутствовать и в сыром SPA-шелле
  (meta csrf в head, ссылки на vite-бандл) — dom_only таких строк
  без Livewire/Inertia-гидрации не содержит, но класс теоретически не
  пуст; наоборот, DetectSPA (T-057) — эвристика, «SPA»-вердикт мог быть
  ложным для server-rendered Livewire-страниц (тогда их dom_only-сигналы
  были и в сыром теле).
- Замер фиксирует **состоявшиеся** рендеры: 98–99% из них — `.рф`.
  Для классов, где рендеров почти не было (ru, com, длинный хвост —
  95,5% недоставленного долга), DOM-вклад **не измерим до рендеров**;
  вывод «порядка нуля» на них не переносится автоматически (хвост — не
  парковки, а реальные SPA: 97,7% записей без находок по сырой фазе).
  Первая rendered-находка прочих зон с обязательностью контента
  (needs_dom=1) появилась уже между срезами замера.
- Состав PEL и недоставленного хвоста q:render, сэмпл 14 доменов
  головной волны и сэмпл хвоста 476 записей — разовые проверки сессии
  замера (Redis XRANGE/XPENDING и точечные чтения по PK), в скрипт не
  входят; числа дрейфуют вместе с дренажом.
- Счётчики дрейфуют (живой конвейер): таблица результатов — один
  консистентный срез; частоты правил и ставки долга сняты в соседние
  моменты (расхождения ±единицы, для rendered прочих зон — десятки
  за часы дренажа).

### Вывод и рекомендация (решение — за оператором)

Парковочный класс `.рф`: DOM-вклад порядка нуля — наблюдаемые 0,45%
отрендеренных находок (dom_only; при ложных SPA-вердиктах Livewire —
вплоть до 0) и 2,5% (needs_dom; при счёте кук рендера — не меньше);
в слот-времени 0,002%. 90,9% находок `.рф` (4 379/4 819) существуют
без рендера, зачёт несут серверные куки сырой фазы. При этом `.рф` —
97,2% злых PEL-ретраев (тарпиты/cert-ошибки) и потребил 98–99% всех
состоявшихся рендеров с выходом 0,5% находок.

- **(б) — данные поддерживают**: не ставить рендер парковочному классу
  `.рф` вовсе (вердикт по HTTP-сигналам). Наблюдаемая потеря покрытия —
  2–11 строк из 4 819 (0,04–0,23% находок зоны; обе оценки смещаются в
  обе стороны, порядок — доли процента), все потерянные — реальные
  приложения, не парковки; освобождается PEL-хвост злых ретраев.
  Продукт-решение о покрытии — за оператором; отступление зафиксировать
  по образцу T-166 (docs/content.md, «Зафиксированные отступления»).
- **(а) — приоритизация долга** актуальна для остального долга:
  недоставленный хвост (95 тыс.) уже фактически отсортирован «не-`.рф`
  вперёд» (`.рф` в нём 0,2%); порядок RequeueRenderPending менять под
  него не требуется, пока решение (б) не принято — тогда источником
  `.рф`-спроса останутся только PEL и неопубликованный `render_pending`
  (состав последнего не измерен).
- Критерий приёмки при реализации шейпинга (из задачи): baseline этого
  замера — ~99% слот-времени рендера уходит на классы с DOM-вкладом
  ≈0 (`.рф` 0,45%); цель — снижение ≥ на порядок; находчивость не
  падает (контрольная выборка переанализом; кандидат — домены
  dom_only/needs_dom из этого замера, включая Livewire-сайт
  `xn--80afc7aid1a.рф` — прямой тест ложного SPA-вердикта). После
  дренажа хвоста ru/com замер повторить по тому же скрипту — закрыть
  неизвестный DOM-вклад непарковочных классов.

**Решение оператора (2026-10-24, вечер): вариант (а)** — приоритизация
долга по зонам, потери находок нет: выборка RequeueRenderPending вперёд
зонами с высоким DOM-вкладом, парковочные `.рф` — по остаточному
принципу. Реализация — задача T-184 (двухступенчатая выборка без
сортировки, координация с T-181 — обе перестраивают
renderSelectPending); вариант (б) (отказ от рендера `.рф` с фиксацией
отступления) не принят. После дренажа ru/com замер повторить по тому же
скрипту — решение пересматривается по фактическому DOM-вкладу
непарковочных классов.

## Live-тесты на стеке

Браузерные тесты (`browser_live_test.go`) по умолчанию пропускаются;
включаются переменной `CRAWLER_RENDER_TEST=1` против compose-сервиса
chromium (адрес: `CRAWLER_RENDER_REMOTE_URL`, затем `CHROMIUM_WS_URL`,
по умолчанию `ws://172.28.100.14:9222`):

```bash
docker compose --project-directory . -f deploy/docker/compose.yaml \
  run --use-aliases -e CRAWLER_RENDER_TEST=1 --rm tools \
  go test ./internal/render -run BrowserLive -v -count=1
```

`--use-aliases` включает DNS-алиасы сервиса tools (нужны live-тестам
блокировки трекеров — T-214 и per-engine срезу ниже, — остальным не
мешает).

Per-engine срез движков (T-254, `engines_live_test.go`): таблица
chromium/moli/lightpanda — один код × наборы переменных адресов
(`CHROMIUM_WS_URL`/`MOLI_WS_URL`/`LIGHTPANDA_WS_URL`, дефолты — адреса
compose-сервисов; общий оверрайд `CRAWLER_RENDER_REMOTE_URL` остальных
live-тестов срез не читает). На каждый движок — зонд `/json/version`
(недоступный движок при дефолтном адресе — SKIP с причиной, при явно
заданной переменной — отказ), затем срез инвариантов ТЗ 5.6 (ФТ-5 ТЗР
движков): изоляция контекста на задачу, navigate + съём DOM/JS- и
httpOnly-cookies/заголовков ответа, перехват Fetch по типам (T-062) и
трекер-доменам (T-214, общий дифференциал `blockLiveTrackerDomains`),
SSRF-контур (T-219: отказ задачи классом task; T-230: навигация на
приватный адрес testbed обрывается перехватом —
`net::ERR_BLOCKED_BY_CLIENT`; резолв контура в тесте — unbound стека
через шов `Options.LookupHost`: резолвер run-контейнера tools внешний,
тестовых зон не знает), UA-override (и в `navigator.userAgent`, и в
заголовке запроса на сервер фикстуры). moli/lightpanda поднимаются профилем
`render-engines`; состояние pinned-версий против среза — докомментарий
файла и процедура smoke ФТ-17 в
[`dev-environment.md`](dev-environment.md).

Страницы-задачи — HTTP-фикстуры: тест поднимает сервер в run-контейнере
(слушает 0.0.0.0, страницам отдаётся адрес контейнера в `crawler_net` —
хелперы `liveIPv4`/`liveServe` в `browser_live_test.go`), Chromium
достучится из соседнего контейнера. data:-страницы («дешёвая»
герметичность ранних live-тестов) невозможны после R-09:
`validateTaskURL` отвергает не-http схемы, тесты переведены на фикстуры
(T-216).

Состав: параллельный рендер страниц фикстур через пул (4 задачи на
2 контекста, счётчик страниц), изоляция профилей (cookie не переживает
смену контекста), подмена User-Agent. Блокировка ресурсов (T-062,
`block_live_test.go`): локальный HTTP-сервер со счётчиками — картинка и
шрифт не запрошены, CSS/скрипт/XHR запрошены; CSS при опции T-213 — не
запрошен вовсе; трекер-домены при опции T-214 — дифференциал двух
прогонов (зонды `c.clarity.ms`/`mc.yandex.ru` резолвятся DNS-алиасами
сервиса tools, для чего compose run зовётся с `--use-aliases`: контроль
без опции зонды догружает, с опцией — оборваны до отправки). Ожидание
готовности (T-063, `wait_live_test.go`): тихая страница фикстуры
заканчивается окном затишья, «шумная» (fetch на TEST-NET каждые 300 мс)
— потолком фазы затишья, страница с вечным скриптом — общим таймаутом с
ошибкой `task`/`DeadlineExceeded`. Съём результата T-064
(`extract_live_test.go`): точный `outerHTML` страницы фикстуры после
исполнения скрипта, JS-cookie `js_session` на внутренней странице
`spa-shell.crawl.test` и заголовки её ответа. Флаг доступен и в
worktree-агентах следующих задач (T-065…T-067).
