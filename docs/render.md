# Рендер: Chromium под управлением render-worker (ТЗ 5.6, §9)

Пакет `internal/render` (T-061) — управление **одним** Chromium на воркер и
параллельный рендер страниц в изолированных контекстах. Блокировка ресурсов
(T-062), ожидание «затишья» сети (T-063), съём итогового DOM/cookies
(T-064), перезапуск браузера (T-065) и цикл очередей (T-066/T-067)
строятся поверх описанного здесь API.

## Один браузер, два режима

`render.StartBrowser(ctx, opts)` — один процесс/соединение на воркер
(ТЗ 5.6 «один браузер»):

| Режим | Условие | Аллокатор |
|---|---|---|
| внешний Chromium | `render.remote_url` задан (`ws://host:9222`) | `chromedp/remote.NewAllocator` — WebSocket к готовому процессу |
| собственный процесс | `render.remote_url` пуст | `chromedp.NewExecAllocator` + headless-набор флагов и `--no-sandbox` |

Внешний режим — dev-стек: compose-сервис `chromium`
(`chromedp/headless-shell`, `mem_limit` 2 ГБ ≈ бюджет ТЗ 3.2, CDP на
`172.28.100.14:9222`). Собственный — боевой render-образ
(`deploy/docker/Dockerfile.render`: headless-shell + бинарник воркера,
`USER nobody` — отдельный непривилегированный пользователь по ТЗ §9).
Профиль браузерной сессии служебный (headless-shell без пользовательского
каталога): страницы задач в нём не рендерятся.

`ctx` стартового вызова — контекст жизненного цикла воркера: в chromedp
браузер живёт, пока жив контекст первого вызова, отмена ctx останавливает
и подключение/процесс, и незавершённую инициализацию.

## Изолированные контексты и отказ от сохранения состояния

`Browser.NewSession` — изолированный контекст CDP
(`Target.createBrowserContext`, опция chromedp `WithNewBrowserContext`):
инкогнито-профиль со **своими** cookies, кэшем и хранилищами (localStorage,
IndexedDB, service workers) и одна вкладка `about:blank`.

Сессия живёт ровно одну задачу: после страницы пул закрывает её
(`Target.disposeBrowserContext`), следующая задача получает новый профиль.
Пересоздание вместо выборочной очистки: dispose выкидывает все хранилища
профиля атомарно и без перечисления origin'ов (очистка потребовала бы
`Storage.clearDataForOrigin` по каждому встреченному origin и не покрывала
бы кэш), а стоимость — один `createBrowserContext` + `createTarget`,
незаметная на фоне таймаута страницы в секунды. Требование ТЗ §9 «без
сохранения состояния между страницами» выполняется конструкцией; изоляция
подтверждается live-тестом (cookie, положенная в профиль сессии, не видна
в следующей).

## Пул

`render.NewPool(browser)` — параллелизм `render.contexts` (рекомендация
ТЗ 5.6: 2–4): одновременно не больше N задач, каждая — в свежем
изолированном профиле. `Pool.Run(ctx, task)`:

- ждёт свободный слот (или отмену ctx / закрытие пула);
- одна попытка = новая сессия → задача → закрытие профиля при любом
  исходе;
- при ошибке класса `context` — один повтор на новом контексте;
- успешная страница инкрементирует `Browser.Pages()` — счётчик для
  перезапуска «каждые N страниц» (`render.restart_every_pages`, ТЗ 5.6);
  сам перезапуск и порог по памяти — T-065 (`Browser.NeedsRestart`).

`Pool.Close` — graceful shutdown по ТЗ 3.4: новые задачи отклоняются
(`ErrClosed` → повторная доставка уровнем очереди), текущие дорабатываются
(каждая ограничена `render.timeout`), затем останавливается браузер.

Задача и результат — `RenderTask{URL}` и `RenderOutput{FinalURL, Title}`
(пока минимальный съём T-061; итоговый DOM и все cookies добавит T-064
полями). User-Agent страниц — единый идентифицируемый UA краулера
`http.user_agent` (ТЗ §9; в секции render ТЗ 5.10 отдельного поля нет):
применяется к вкладке через `Emulation.setUserAgentOverride`.

## Классификация ошибок

Все ошибки пакета — `*render.Error` с классом (`render.ClassOf`):

| Класс | Причина | Реакция |
|---|---|---|
| `task` | таймаут страницы, отмена контекста задачи, `net::ERR_*` | повторная доставка — уровень очереди (T-066) |
| `context` | изолированный контекст умер (вкладка/рендер упали, профиль не отвечает) | `Pool` повторяет один раз на новом контексте |
| `browser` | Chromium недоступен / соединение потеряно | перезапуск браузера (T-065), пул не повторяет |

Классификация идёт по состоянию контекстов и соединения (не по текстам
ошибок): отмена контекста задачи и таймаут — по контекстам; смерть
браузера — `LostConnection`/отмена браузерного контекста; смерть вкладки —
отмена её контекста либо живой зонд (простейший `Evaluate`, chromedp не
отменяет контекст вкладки при её падении).

## Live-тесты на стеке

Браузерные тесты (`browser_live_test.go`) по умолчанию пропускаются;
включаются переменной `CRAWLER_RENDER_TEST=1` против compose-сервиса
chromium (адрес: `CRAWLER_RENDER_REMOTE_URL`, затем `CHROMIUM_WS_URL`,
по умолчанию `ws://172.28.100.14:9222`):

```bash
docker compose --project-directory . -f deploy/docker/compose.yaml \
  run -e CRAWLER_RENDER_TEST=1 --rm tools \
  go test ./internal/render -run BrowserLive -v -count=1
```

Состав: параллельный рендер data:-страниц через пул (4 задачи на
2 контекста, счётчик страниц), изоляция профилей (cookie не переживает
смену контекста), подмена User-Agent. Флаг доступен и в worktree-агентах
следующих задач (T-062…T-067).
