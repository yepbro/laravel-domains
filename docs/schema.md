# Схема PostgreSQL: таблицы zones, subdomains, domains

Решения по доменной части схемы (задача T-003, ТЗ §6 и §6.1). Таблицы
результатов (`subdomain_results`, `contents`, `laravel_*`, `ingest_files`) —
в задаче T-004. Механизм применения миграций — в
[`migrations.md`](migrations.md).

Контракт схемы закреплён интеграционным тестом `test/integration/schema_test.go`
(`make test-integration`): он накатывает миграции в изолированную схему
и проверяет все утверждения этой страницы.

## Обзор таблиц

| Таблица | Что это | Партиционирование |
|---|---|---|
| `zones` | справочник зон (TLD/публичных суффиксов), счётчики прогресса | нет — размер ≈ тысячи строк |
| `subdomains` | справочник проверяемых субдоменов, `id` = бит в `dns_mask` (0..62) | нет — максимум 63 строки (ТЗ 5.10) |
| `domains` | все домены всех зон, статус и состояние проверки | LIST по `zone_id` |

Принцип ТЗ §6 — партиционирование по `zone_id` — касается таблиц с колонкой
`domain_id`; справочники зон и субдоменов не партиционируются.

## Партиционирование domains

- `PARTITION BY LIST (zone_id)` — все строки зоны лежат в одной партиции;
  в каждой строке `zone_id` дублируется (составной первичный ключ
  `(zone_id, id)` и все индексы начинаются с `zone_id`).
- Сейчас существует только DEFAULT-партиция `domains_default` — она принимает
  все зоны. Выделенные партиции крупных зон и субпартиционирование по хэшу
  `id` (партиция ≈ 30–50 млн строк) — задача T-005.
- Новая партиция зоны создаётся до загрузки данных зоны (или с переносом
  из DEFAULT), обязательно с `WITH (fillfactor = 85)` — см. ниже.

## fillfactor = 85

Пониженный `fillfactor` оставляет ~15% каждой страницы свободной: новые версии
обновляемых строк кладутся на ту же страницу (ТЗ §6 — частые апдейты
статусов, HOT-апдейты).

Особенность PostgreSQL 16: **storage parameters нельзя задать на
партиционированном родителе** — ни `CREATE TABLE … WITH (fillfactor = …)`,
ни `ALTER TABLE … SET (fillfactor = …)` (ошибка «cannot specify storage
parameters for a partitioned table»). Поэтому `WITH (fillfactor = 85)` из
эскиза DDL §6.1 реализован на партициях:

- каждая существующая партиция создаётся со своим `WITH (fillfactor = 85)`
  (`domains_default` — в миграции 000001);
- **новые партиции (T-005) обязаны включать `fillfactor = 85`** — reloptions
  от родителя не наследуются; тест `TestSchema_DomainsPartitioning` падает,
  если у какой-то листовой партиции параметра нет.

## Индексы

На `domains` ровно три индекса (принцип «минимум индексов», ТЗ §6):

| Индекс | Назначение |
|---|---|
| `domains_pkey` (`zone_id, id`) | первичный ключ, путь до строки по идентификатору |
| `domains_zone_id_label_key` (`zone_id, label`) | поиск домена по имени без полного сканирования (ТЗ 5.11), идемпотентность ingest (ТЗ 5.1) |
| `domains_pending_idx` (`zone_id, id`) `WHERE check_state = 0` | частичный индекс планировщика: выборка `pending` пачками по зонам (ТЗ 5.3) |

У каждой партиции автоматически создаются дочерние индексы всех трёх.
Расширение набора индексов — осознанное решение с обновлением контракта
в `schema_test.go`: лишний индекс над обновляемыми колонками ломает
HOT-апдейты (см. ниже).

## sequence domain_id_seq

`domains.id` получает значения из единой sequence `domain_id_seq`
(`DEFAULT nextval('domain_id_seq')`) — идентификаторы сквозные по всем зонам
и партициям. Привязка `OWNED BY` не используется (как в эскизе §6.1):
таблица и sequence живут одинаково долго, отдельная связь не нужна.

## HOT-апдейты

При проверке домена обновляются `status`, `check_state`, `flags`,
`dns_mask`, `queued_at`, `last_checked_at`. Апдейт остаётся HOT (без записи
в индексы), пока обновляемая колонка не входит ни в один индекс — ни в ключ,
ни в предикат:

- `status`, `flags`, `dns_mask`, `queued_at`, `last_checked_at` **не входят
  ни в один индекс** — массовые апдейты результатов HOT; `last_checked_at`
  не индексируется явно по ТЗ §6. Проверено эмпирически по `pg_stat_user_tables`
  (`n_tup_hot_upd` растёт) и закреплено тестом `TestSchema_DomainsHOTColumns`.
- `check_state` входит в предикат `domains_pending_idx` — смены состояния
  `pending → queued → done` всегда non-HOT. Это неустранимый компромисс
  самого ТЗ: индекс выборки pending (§5.3) обязан фильтровать по
  `check_state`. Такой апдейт кладёт новую версию строки (fillfactor = 85
  оставляет место) и добавляет записи во все три индекса; на частоту смен
  состояний (две на цикл проверки домена) это влияние ограничено.
